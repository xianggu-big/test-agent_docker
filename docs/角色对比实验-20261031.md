# 三角色对比实验设计（2026-10-31）：需求表达质量 × 自动测试生成效果

> 动机（用户命题）：同一被测系统（Test Agent），三种测试人员人格（小白/初级/高级）各出 10 个
> 带判据的测试需求，全部端到端执行，对比需求表达质量对生成结果的影响——oracle 问题的需求侧维度。
> 被测项目：**tenacity**（jd/tenacity，重试库，82,598 字符纯 Python，当前能力边界内最大可选：
> 预检视野 29%——与已实证的 schema 34%/cachetools 33% 同档，切片核心可见）。
> 纪律：题目不局限于系统"好测"区域，含异常路径/时序/并发/参数误用等找茬点；
> 每题带可观察判据；全部任务真跑留档（roleexp_*.json），报告聚合对比。

## 角色定义（出题人格）

| 角色 | 特征 | 出题风格 |
|---|---|---|
| 小白 | 无测试术语，口语化场景描述，只说功能不提边界 | "帮我看看它会不会一直试到成功" |
| 初级 | 学过等价类/边界值，需求结构化但遗漏异常路径/时序/并发 | "对 N=1/2/3 做边界值，验证尝试次数" |
| 高级 | 系统化：参数误用/时序/并发/异常链/语义边界 | "wait_random(min>max) 参数倒置时是否静默接受" |

## 小白 10 题（口语化，暗含行为探测）

| # | 需求（原样给系统） | 判据（人工复核用） |
|---|---|---|
| x1 | 一个函数总是失败，用了重试之后会不会一直试到成功为止，帮我测测这个重试好不好使 | 重试确实发生（调用次数>1） |
| x2 | 我想让它最多试 3 次就放弃，别一直试下去，帮我看看行不行 | 第 3 次后停止 |
| x3 | 两次重试之间能不能等一会儿再试？比如每次等 1 秒 | 间隔≈1s |
| x4 | 如果函数成功了就别再重试了吧，测一下成功的情况 | 成功即返回只调一次 |
| x5 | 我想让它只对某种错误重试，其他错误直接放弃，能设置吗 | 类型过滤生效 |
| x6 | 重试很多次还是不行的话，最后应该把那个错误报出来吧，测测最后抛的是不是原来的错 | 异常上抛 |
| x7 | 能不能重试的时候越等越久？别每次都等一样的时间 | 递增序列 |
| x8 | 函数返回值是空的也算失败，这种情况也重试，帮我试试 | None 触发重试 |
| x9 | 等待时间有点随机才好，不然大家一起重试就挤一块了，有这功能吗 | 随机等待生效 |
| x10 | 统计一下函数到底被调用了几次，重试的时候次数对不对 | 计数准确 |

## 初级 10 题（方法化：等价类/边界值）

| # | 需求 | 判据 |
|---|---|---|
| c1 | 对 stop_after_attempt(N) 做边界值分析：N=1、N=2、N=3，验证实际尝试次数恰好等于 N | 次数==N |
| c2 | wait_fixed(t) 等待时间边界：t=0 与 t=0.1，验证重试间隔单调非负且符合设定 | 间隔合规 |
| c3 | retry_if_exception_type 单类型与多类型元组等价类：命中类型重试、未命中类型直接上抛 | 分类正确 |
| c4 | 成功路径等价类：装饰后函数返回值与原函数完全一致（不因装饰改变语义） | 返回一致 |
| c5 | stop_after_delay(d)：持续失败超过 d 秒后停止，验证耗时上界 | 超时停止 |
| c6 | reraise=True 与 False 对比：最终抛出的异常类型与来源是否符合语义 | reraise 语义 |
| c7 | wait_exponential(multiplier, max)：等待序列按指数增长且被 max 钳制，验证前 4 次 | 序列正确 |
| c8 | retry_if_result 对 None/"error"/正常值三类返回值的判定 | 结果判定 |
| c9 | before_sleep 回调：每次重试前被调用且参数含 retry_state | 回调触发 |
| c10 | 多参数组合：stop_after_attempt+wait_fixed+retry_if_exception_type 联合行为 | 组合语义 |

## 高级 10 题（异常路径/时序/并发/参数误用——找茬扩展）

| # | 需求 | 判据 |
|---|---|---|
| g1 | wait_random(min, max) 参数倒置（min>max）时的行为：静默接受、抛错还是产生非法等待——探 API 校验 | 校验行为明确 |
| g2 | stop_after_attempt(0) 与负数：零次尝试语义（一次都不调用？还是照调一次？） | 边界语义明确 |
| g3 | wait_exponential 极大 multiplier：指数溢出是否被 max 钳制，等待值是否合法 | 无溢出/有钳制 |
| g4 | 在 async 函数上使用同步 retry 装饰器：是否静默失效（重试不生效） | 行为可诊断 |
| g5 | 被装饰函数是生成器/有副作用时：重试是否从头执行（副作用重复触发风险） | 副作用语义 |
| g6 | retry_state 的 wait/tries 属性与实际 sleep 一致性（时钟精度容忍 ±20%） | 状态与实际一致 |
| g7 | wait 策略函数自身抛异常时的降级行为（策略失败=重试失败？崩溃？） | 降级可诊断 |
| g8 | 嵌套 retry：内外层重试次数的复合语义（乘积/和/覆盖） | 语义与文档一致 |
| g9 | 多线程并发调用同一 retry 装饰函数：调用计数与重试状态是否正确（无锁探查） | 并发计数正确 |
| g10 | RetryError 异常链：reraise=False 时 __cause__/__context__ 是否保留原始 traceback | 链可诊断 |

## 重大中间发现（2026-10-31 05:40）：首批 30 轮全熔断=评测仪器第三处标定

首批 30 轮（修复前代码）**全部"同指纹熔断"**（无一 pass、无一假缺陷上报）。人工复核根因链：
①静态闸误杀 re-export 型包（tenacity `__init__.py` 全是 import 转发，D3 包名映射对其失效）→
②容器 pytest 无文件参数全目录收集，仓库自带 tests/ 缺依赖（tornado）→ `Interrupted: 1 error
during collection` → 5 条生成用例**根本未执行**即计 failed=1 → 熔断。容器重放实证：加
`--continue-on-collection-errors` 后 192 passed（生成+自带测试全过）。已修（loop-8），
首批 30 份 json 归档 data/reports/roleexp_pre_fix/（熔断形态证据），全量重跑中。
**这本身是"评测仪器与被测系统一样需要标定"的又一实证**（6.9(6) 第 9 条素材）。
