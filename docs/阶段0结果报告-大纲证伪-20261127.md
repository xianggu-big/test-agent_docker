## 3. 尸检（为什么大纲没赢）

**留出项目（密码强度校验器，根因=长度恰为上限 64 被误判不合法）：**
- B 臂确实写出了正中根因的用例（b#4 `is_strong[长度64=max]`：断言 True 实得 False），但 **5 格里只有 1 格**写到；
- B 臂用例数暴涨到 48.8 条/格（4 倍），多出来的用例涌向了别的维度（非字符串输入、min−1 等），其中 b#3 断言了一个需求未定义的行为（非植入缺陷）；
- A 臂 11.6 条/格也只 1 格踩中。**根因不是"没想到边界"，是"想到了也不稳定地落到那条边界上"**——与需求显式化梯度的机制解释一致，且说明"多给清单"不等于"命中靶点"。

**干净项目误报暴涨（H2 的死因）：**
- B 臂 3/5 格把 coupon-api 报成"疑似产品缺陷"，失败用例全是大纲条目教出来的惯例断言（重复操作、不存在资源、区间端点类）——需求没写这些行为，模型按惯例断言并当作缺陷上报；
- 大纲里"每条断言写明预期来源"的纪律行没能拦住：预期文本里含需求词（如"创建"）就被判"可溯"，审计校准偏宽（诚实记：护栏审计的 leniency 也需复核）。

**结论的适用边界**：本实验证伪的是"把通用大纲拼进需求文本"这一种最便宜的形态；"账目化大纲+逐条映射到符号+预期依据硬闸"的完整形态没被测（它需要阶段 1 的基建）。但按预注册纪律，基建在证伪通过前不建。

## 5. 对重设计的影响

- **砍掉**：阶段 1 的"大纲库骨架"按原样不建（证伪未过）。
- **保留（未被本实验证伪，机制不同）**：诊断前移+模式库（对着"诊断不可达"，V8 小卡今晚跑）、工具自适应（对着"工具不匹配"）、体量预算（对着"读得少且截得机械"）。
- **回设计桌的教训进提案**：①大纲类资产必须以"逐条映射到目标符号+预期依据硬闸"为前提，纯文本拼接不可用；②任何扩断言面的机制必须同步收紧 oracle（防惯例断言变误报）——这两条写进提案 §10 的前提检验。
