## 0. 结论先行

1. **要改的是两处，不是一处。** 原设计稿只点了示例里的能力 id 简写（`gen_cases`）；示例里的参数提示
   `"args_hint": {"target": "div"}` 同样是错的——`test.gen.cases` 的真实参数是 `feedback`（必填）和 `targets`，
   校验器对它的原话是"缺少必填键 'feedback'"。
2. **"假 id 自伤幻觉率"这条理由作废。** 此前说示例里的假 id 会被记进幻觉率分子。对码：幻觉率的机器核对
   只数 `call` 步骤，从不读 finish 里的 `strategy.priorities[].capability_id`（`run_metrics.py:234-240`）。
   实测：30 格 84 条优先项全部写的是全名，简写出现 0 次。
3. **Q4 的性质因此降级**：它修的是一处**已被实证没有行为后果**的提示词不一致（示例与菜单自相矛盾），
   不是指标污染。仍然值得改——理由变成正确性、现场演示的可核对性、以及借机加一道机器闸——但它不紧急，
   不影响任何已产出的数字。
4. **改动面比原估计大**：示例之外还有三个同步点——版本锁测试（`tests/test_tool_loop.py:212` 硬写 `"v1"`）、
   黄金演示夹具（硬写 `"v1"`，且复制了示例的同一个错键）、汇总端点不分版。三者的暴露方式不同：
   版本锁漏改，全量回归会红；夹具漏改，回归全绿，到现场演示才看得见；汇总不分版，在库里出现第一条 v2 运行之前都不构成问题。
5. **执行前要回答一个问题**（§6）：中期前是否打算用 v1 补数来扩大指标表 v1？是，则先补数后执行本方案；否，随时可执行。
6. 顺带登记三条新的范围外发现（§10 F1–F3），不并入 Q4：`test.gen.cases.targets` 是空参数；演示夹具有与真实不符的数据；黄金演示脚本未入库。

## 3. 设计总则

1. **只改示例文本里的两处值，其余一字不动。** 提示词的结构、段落顺序、`AGENT_DECIDE_SYSTEM`、
   `AGENT_STRATEGY_FINISH_KEY`、三问判定锚、diagnose 段全部不动——让 v1→v2 的唯一变量就是那两处。
2. **提示词文本变了，版本戳必须变。** 沿用 `prompt_library.py:524` 的硬纪律。v1 已产出的数据不重跑、不改写。
3. **示例必须机器可核对。** "示例 ⊆ 菜单、示例参数 ⊆ schema"从此是一条测试，而不是口头纪律。
4. **先红后绿。** 新测试先在 v1 上跑出正确的红，再改示例。
5. **范围纪律。** §10 的范围外发现只登记不并入——并入会让 Q4 从"改示例"变成"改能力行为"，那需要独立的验证。
6. **示例不教模型填不生效的参数。** 见 §4.1 对 `targets` 的取舍。

def _menu_schemas():
    """真实菜单 {id: inputs_schema}——单一真源是 capabilities，不手抄。"""
    ctx = types.SimpleNamespace(primary_language="python", agent_mode="strategy")
    return {c.id: c.inputs_schema for c in caps._build_capabilities(ctx)}


def _example_priorities():
    """从 finish 示例常量里取出 priorities。对常量本身解析，不对系统提示词全文——
    全文里 '{"action": "finish"' 出现两次（模板行含 {mode_extra_key} 占位，不是合法 JSON）。"""
    idx = AGENT_STRATEGY_FINISH_EXAMPLE.index('{"action": "finish"')
    return json.loads(AGENT_STRATEGY_FINISH_EXAMPLE[idx:])["strategy"]["priorities"]


def test_strategy_finish_example_injected_verbatim():
    """示例原样注入 strategy 系统提示词，且不混入 diagnose（防断链、防模式串味）。"""
    assert AGENT_STRATEGY_FINISH_EXAMPLE in build_agent_decide_system("strategy")
    assert AGENT_STRATEGY_FINISH_EXAMPLE not in build_agent_decide_system("diagnose")


def test_strategy_finish_example_ids_exist_in_menu():
    """示例里的每个 capability_id 都是真实菜单 id（Q4 起因：示例写了简写 gen_cases）。"""
    schemas = _menu_schemas()
    for p in _example_priorities():
        assert p["capability_id"] in schemas, f"示例能力 id 不在菜单：{p['capability_id']}"


def test_strategy_finish_example_args_hints_pass_schema():
    """示例里每个 args_hint 都能过对应能力的 schema 校验——用策略闸同一个校验器。"""
    schemas = _menu_schemas()
    for p in _example_priorities():

        assert schema is not None, f"示例能力 id 不在菜单：{p['capability_id']}"
        err = _validate_args(schema, p["args_hint"])
        assert err is None, f"{p['capability_id']} 的示例参数不过 schema：{err}"

## 5. 配套项：汇总端点标注提示词版本

**问题**：`/api/metrics/summary`（`server.py:985`）从 `agent_runs` 取全部行计算，不看 `prompt_version`。
只要库里同时有 v1 和 v2 的运行，汇总就把两版混在一起算，而响应里没有任何字段能看出来。

**什么时候成为问题**：库里出现第一条 v2 运行之前都不构成问题（当前 30 行全是 v1）。本项**不阻塞 Q4**，但必须是跑任何 v2 批次之前的最后一个前置。

**最小设计**（不改任何既有数值字段）：

- 响应增加 `prompt_versions`：按运行数计的版本分布，如 `{"v1": 30}`。
- 分布里不止一个版本时，再增加 `mixed_prompt_versions: true` 与一句 `note`；单版本时不带这两个键。
- 当前只有 v1 的库：输出与现状一致，只多一个 `prompt_versions` 键。

**为什么是"标注"而不是"分版各算一套"**：指标表 v1 的全部数据就是这 30 格。分版重算在只有 v1 时是冗余，
在 v1+v2 时会把样本劈成两半。混没混要让读者看得见；要不要合并报告是论文口径的事，不该由接口替人决定。

**测试**（`tests/test_run_metrics.py`，2 例）：纯 v1 库输出 `{"v1": n}` 且无 `mixed_*` 键；人为混入一行 v2 后带标注。

**实现量**：约 20 行，零 API。

## 6. 可比性与执行时机

| 数据 | 提示词版本 | 处理 |
|---|---|---|
| 2×2 首夜及后续 AgentLoop 实验（归档库 49 个） | v0 与 v1 混合，无版本字段，按日期分（§2.2） | 归档库，不动 |

| 本方案执行后的新运行 | v2 | `agent_runs.prompt_version` 逐行自证 |

**两条规则**

- 同一批次内版本必须唯一（既有预注册纪律）。执行本方案会切断一个正在进行的 v1 批次，所以不要在批次中途执行。
- 跨版本合并报告需要等价性证据（v1 与 v2 同格对照）。"预期等价"的依据是 v1 下模型本来就没照抄示例（84/84），
  但这是先验。没有对照数据之前，v1 与 v2 分开报。
