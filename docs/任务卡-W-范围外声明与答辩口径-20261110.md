# 任务卡-W：范围外声明的论文与答辩口径（2026-11-10）

> 用户决定：探索式测试与生产测试"不是缺口，是已划定的范围外，只要论文里说清楚就不失分"——本卡把它们从"沉默的缺失"变成"**有出处的主动声明**"。
> 性质：**写作卡，不写代码**。产出 = 论文范围章节的标准表述 + 答辩问答卡 + 引用清单。
> 判据：评委听完应认为"你想清楚了边界"，而不是"你做不到"。

## 1. 三条范围外声明的标准表述（可直接改写进论文）

### 1.1 探索式测试（Q3 象限）

> 按敏捷测试四象限的分类[29]，探索式测试属于"业务面向、批判产品"象限（Q3），其核心特征是**测试设计与执行同时发生**、依赖测试者的领域知识与即时判断。本课题不将其纳入自动化范围，原因不是技术实现难度，而是**判据性质不可外化**：探索式测试的价值恰恰来自"人看到结果后产生的新假设"，这一过程无法预先写成可执行的断言，也无法交给以"生成—执行—判定"为循环的自动化系统。本课题与该象限的关系是**互补而非替代**：系统产出的结构化报告与审计台账可作为人工探索的起点（例如未覆盖的复杂度热点提示可指引探索方向），这一衔接列为后续工作。

**为什么这段能防守**：它承认了 Q3 的价值（不是贬低），指出的是"判据不可外化"这一**结构性原因**，并给出互补关系——这是学术上站得住的界线，而不是能力辩解。

### 1.2 非功能测试（Q4 象限：性能/安全）

> 性能与安全测试属于 Q4"技术面向、批判产品"象限[29]，其判定依据是**非功能指标**（响应时间分布、吞吐、资源占用、漏洞可利用性），与本课题"功能正确性"的判据体系不同：功能测试的 oracle 是"输出是否符合预期"，性能测试的 oracle 是"指标是否落在阈值内且随负载可预测地变化"，二者所需的采集设施（压测驱动、采样探针、漏洞扫描器）与方法论（负载模型、威胁建模）均不重叠。本课题明确将该象限排除在研究范围之外（见第 3 章范围界定），系统仅采集执行耗时与资源占用作为**输出指标**，不承诺提供负载/压力/安全测试能力。

**注意**：这里要明确区分"采集指标"与"测试能力"——你的 `container_jobs` 确实记了 CPU/内存/耗时，但那是指标采集，不是性能测试。论文里必须说清，否则会被追问"你既然记了耗时，为什么说没做性能测试"。

### 1.3 生产环境测试（shift-right）

> 生产环境测试（金丝雀发布、影子流量比对、混沌工程、合成监控）属于测试活动的右移延伸，其共同前提是**存在真实流量与可观测基础设施**——判据来自线上指标（错误率、延迟分位数、业务转化）而非预置断言。本课题的系统定位是**测试阶段的自动化**（在隔离沙箱中对被测代码执行测试），不与生产环境交互；相应地，本系统输出的结构化报告与审计台账可作为生产发布的前置门禁数据源（例如"本次改动的测试证据是否完整"可作为发布审批的输入），这一衔接属于工程集成方向，不在本课题研究范围内。

**为什么这句"可作为前置门禁"重要**：它把"我们不做生产测试"从"能力缺失"转成"我们在流水线里的位置不同"，并且暗示了集成价值。

## 2. 答辩问答卡（5 问 5 答，照着背）

| 评委可能问 | 回答 |
|---|---|
| 为什么不做探索式测试？ | 探索式的判据是"人看到结果后的即时判断"，无法预先写成可执行断言。我们不做是因为**判据不可外化**，不是因为做不了。相反，我们的未覆盖热点提示可以作为人工探索的起点——两者互补。 |
| 性能测试呢？你系统不是记录了耗时吗？ | 记录的耗时是**输出指标**（用来对比容器与宿主、评估预算消耗），不是性能测试能力。性能测试的 oracle 是"指标随负载的可预测变化"，需要负载模型与压测驱动，方法论完全不同。 |
| 安全测试呢？ | 同属 Q4 象限，判据是漏洞可利用性，需要威胁建模与专用扫描器。我们在静态闸里有基础的风险词扫描（如空 catch、危险调用），但那是**代码质量线索**，不构成安全测试。 |
| 你的系统能替代测试工程师吗？ | 不能，也不以此为目标。系统覆盖的是"判据可显式表达"的部分（Q1/Q2 象限），把人从重复劳动中释放出来去做 Q3（探索）与判断性工作。我们实测的抽检推翻率 9% 就是这个分工的证据——系统产出需要人复核。 |
| 边界划得这么窄，工作量够吗？ | 窄是刻意的：正因为收敛到"判据可表达"的单元/集成两级，才能把治理机制（归因、证人冻结、审计、盲测协议）做到可验证的深度。宽而浅的系统无法回答"你的结论可信吗"。 |
