# 第5章 系统实现

## 5.1 L1 单元测试双轨生成实现

### 5.1.1 黑盒轨：方法骨架提示词与模板库

黑盒轨的生成核心是方法骨架提示词：等价类划分、边界值分析、判定表、错误推测法四类黑盒方法的操作化定义被写为提示词段落，要求模型按方法逐类生成并在用例名中标注方法标签——将"测试设计必须基于显式方法论"的理论纪律转化为生成约束；语句与分支覆盖目标作为白盒轨在生成阶段的接入点一并注入（见 5.1.2）。每个用例同时输出六要素结构化字段（编号、名称、优先级、输入、步骤、预期结果）与预期值出处标注（expected_basis：需求明示/文档/源码推导/常识），使"断言先于执行"从纪律升级为可审计数据。

在此之上，系统实现了槽位模板库：对等价类划分、边界值、状态迁移与错误推测的缺陷模式提供确定性渲染器，判定表等组合逻辑方法经骨架提示词直接生成——模板以槽位填充方式生成用例骨架，仅语义部分交由大模型填充，并以独立段落追加防止示例污染主提示词；蜕变测试以蜕变关系提示词段落地（幂等、对称、单调、往返、无关变换不变五类模式）。状态迁移与蜕变两个扩展方法各以配置开关控制（默认关），属性测试以 Hypothesis 属性段实现并由独立开关控制，以保持消融实验能力。模板通道与自由生成通道遵循同一套生成协议：模型仅输出描述方法语义的槽位数据（函数名、等价类清单、边界点、条件规则等），渲染器将其确定性填充到预置的 pytest 代码骨架，产物再经过与自由生成完全相同的静态闸、可收集闸与落库流程。两条通道同闸同库带来两个直接收益：其一，渲染产物天然不存在语法与引用错误，闸门失败率显著下降；其二，通道间的运行指标（token 消耗、通过闸比例、检出贡献）在同一口径下可比，构成方法消融实验的基础。防止示例污染是模板通道的另一个设计要点：模板的槽位示例以独立段落注入提示词，与主提示词隔离——若示例混入自由生成的对照提示词，两组实验的差异将无法归因于模板本身。

针对"生成器不主动构造边界外输入"的实证短板，另设边界攻击纪律开关（强制每函数至少一条越界输入用例）。

### 5.1.2 白盒轨：覆盖反馈与结构感知

白盒轨将程序结构信息注入生成过程：**覆盖缺口回灌**——执行阶段解析 pytest 覆盖率输出的逐文件未覆盖行，注入下一轮生成提示词作为优先补测目标，使补测轮次"知道该往哪补"；**复杂度热点感知**——以 radon 计算圈复杂度，高复杂度函数作为热点显式提示生成器优先覆盖；**定向修复**——失败轮次后按归因分流：环境类修复环境重跑，用例类强信号（ImportError、AttributeError 等）剪除或带失败上下文重写（保留贴近程序逻辑的高价值种子[8]），断言失败按预期值来源分层处置——需求明示或文档依据的失败冻结为缺陷证人，源码推导类按用例缺陷修复。

### 5.1.3 生成三道闸

两道确定性闸的剔除粒度刻意不同。静态闸按单个用例剔除——语法或引用错误的用例只影响自身，其余用例保留；可收集闸按整个文件废案——收集失败通常源于文件级问题（同名用例互相覆盖、fixture 冲突、编码异常），此时无法判定是哪一条用例导致，整文件退回重新生成比保留带毒文件更安全。这一粒度差异的动因来自实测：文件级故障若按单案剔除处理，坏文件会反复通过闸门进入执行，把失败传染给后续每一轮。

AI 生成物经三道闸审查后方可进入执行：**静态闸**（AST 解析验证语法、from-import 符号在被测模块顶层存在性校验）；**可收集闸**（容器内 pytest --collect-only，文件级失败整体废案）；**交叉语义闸**（可选开关）——以独立审查者角色逐案审断言是否对应需求，不通过的用例单独重造一次，复审仍不通过则剔除，审查器故障时放行并留痕（辅助闸不因自身故障废整批）。

## 5.2 L2 集成测试双轨生成实现

### 5.2.1 端点提取降级链

集成层接口信息按框架探测降级链获取：被测服务自带 OpenAPI 规范时（FastAPI 默认提供）走确定性解析，展开 $ref 引用获得端点全集；无规范但有装饰器路由特征时（Flask）走 AST 静态提取；两者皆无则诚实降级并上报。降级链的三级不仅决定端点能否获取，也决定了端点数据的字段完整度：规范解析级可获得参数、请求体与响应体的完整模式，契约用例得以按字段级模式构造；静态提取级可获得方法与路径，模式信息缺失，契约用例退化为以状态码为主的弱断言；诚实降级级不产生任何端点行，集成级跳过并如实标注。字段完整度与断言强度的对应关系以端点来源字段显式记录，使评估阶段能按来源分层解释结果，也为消融实验提供了"来源"这一额外维度。

该链保证端点数据的可信来源，避免 LLM 猜测接口。

### 5.2.2 契约黑盒轨与调用链白盒轨

**契约黑盒轨**生成三类集成用例：契约用例（依据端点参数模式确定性构造合法/非法请求）、顺序场景用例（"创建→按 id 读取"等有状态业务流）、需求断言用例（LLM 依据需求文本生成，带表达式静态闸与状态码剥离过滤）。断言实施**两级校验**——契约级断言（状态码与响应结构符合接口契约）与需求级断言（业务语义符合需求陈述），前者确定性可判，后者允许 LLM 容错并留审计标记。外键关联的前置数据由系统自动构造，消除"订单引用不存在的用户"类假失败。

**调用链白盒轨**基于 AST 构建函数调用图，将接口操作（operationId）经最长前缀反查到处理函数，沿调用边生成顺序约束场景（确定"创建→使用"的先后关系），与契约轨的顺序场景用例互补——前者依据调用边定序，后者依据契约构造具体请求，使白盒可见性从函数级延伸到服务级。

上述链路在故意埋入"订单数据不持久化"缺陷的演示 FastAPI 服务上验证：顺序场景用例如实抓到该缺陷（契约违背证人语义），需求断言用例未观察到误报；无规范、无密钥、重跑幂等等降级与容错路径均验证通过。

## 5.3 L3/L4 半自动辅助实现

**L3 系统测试半自动**：场景生成遵循"生成有闸、判定分级"。大模型从需求生成业务流场景（API 调用序列），静态闸保证每个步骤的方法与路径必须命中集成级提取的端点清单，虚构接口直接剔除；冒烟脚本生成时将前序步骤的响应值注入后续步骤的路径参数与请求体外键（room_id/coupon_id 类字段按前缀创建资源注入占位符，负例的非法字面 id 不替换），形成"创建→按 id 读取/引用"式引用链；执行后冒烟通过的场景自动判定通过，失败场景转人工定性，确认状态（自动通过/人工确认/待定性）落库并参与指标计算，待定性场景不计入通过率分母。L3 子图由准备（依赖装配与服务启动）、场景生成、冒烟执行、报告四个节点构成，经级别编排器在集成级之后接力。上述链路已在包含下单业务流的演示服务上验证：生成的 5 个业务流场景全部通过静态闸，正常"创建→查询"场景经引用链替换后自动判定通过，其余场景如实转人工定性——判定权在人，流转与留痕在系统。

**L4 验收辅助与资产沉淀（已实现）**：验收条件先经 LLM 拆解为 Given-When-Then 场景（结构字段与端点静态闸同源，虚构接口剔除），人工确认三态（通过/缺陷/场景问题）落库；确认场景经确定性转化器渲染为可执行 pytest 回归脚本（复用 L2 引用链语义，AST 编译闸把关），转化失败自动退回轻量记录模式（确认状态与预期来源保留，不丢人工结论）。转化产物以独立框架标签入库并自增版本，重复转化不重复行。真机验证在演示服务上生成 21 条验收场景（覆盖 code 长度/percent 边界、金额门槛、重复用券等条件），人工确认 2 条后转化出 2 个 pytest 函数并通过编译；调用者权限拒绝与确认流转同步复核。该轮转化规模有限（n=1），更大规模验证随第 6 章 E8 报告。

## 5.4 质量保障链实现

**归因三分类**：按信号顺序将失败归为环境/用例/产品三类，分流为修环境、修用例、报缺陷三种处置；断言失败按预期值来源分层——需求明示或文档依据的失败冻结为证人，源码推导类按用例缺陷处置（与 4.2.2 的判定接口一致）。归因器经变异标定实验校验——向语料注入 14 个已知缺陷（含边界差一、条件反转、缺失校验等类型），首轮暴露的正则漏配（NameError 未列入用例缺陷信号）经标定发现并修复，修复后对该批缺陷全部正确识别（14/14；标定集与修复依据同源，该结果属重代入估计，独立缺陷类型的泛化验证列为未来工作，实验明细见第 6 章）。

**证人冻结与继续补测**：疑似产品缺陷的失败用例冻结保全，其失败不进入指纹熔断计数（有意保留不同于原地打转）；当仅剩证人失败时按覆盖率分流——未达标继续补测、达标则如实停机上报"发现 N 个疑似缺陷"。在本课题已完成的变异标定与真机验证中，证人语义零违反（违反机会的完整统计随第 6 章实验报告）。

指标采集确立单快照语义的动因是评估链的一个固有性质：评估工具自身的每次调用也会计入调用台账，若叙述、审查、图表三个环节各自重新采集指标，三份结果必然互不相同，且审查环节会依据这种"漂移"误判叙述造假。单快照语义把采集收敛为一次：评估节点采集一份指标包并沿参数链下传，三类产物全部派生自同一时点，彼此零漂移；与"之后重跑采集所得数字"的差异属台账自然增长，由审查提示词显式豁免，不判为不一致。

**报告双闸与受控重写**：评估指标包由确定性代码从数据库一次性采集（单快照语义，叙述/审查/图表三类产物同源零漂移）；规则闸先行（数字逐项比对、防造假红线：归因产品缺陷时禁止声称"已解决"），LLM 闸收窄聚焦一致性复核；报告被拒时以新快照受控重写一次并复审，无论结果必收敛（硬上限，不回测试环）。

**成本台账**：单元级主链路七个 LLM 调用点逐次记录阶段与 token 用量，级别子图的调用以级别前缀记入同一台账，支撑成本—质量联合分析。

**四级 RTM 跨级溯源**：以级别台账的接力键为链头，按"验收场景→系统场景→集成用例→单元用例→代码位置"确定性建链。场景步骤端点经模板归一关联集成用例；场景文本与测试条件的 2-gram 映射经 RTM 矩阵关联单元用例；调用图快照（含无出边 handler 的函数目录与定义位置）给出函数级代码位置候选。链路只读数据库与 AST 快照，零 LLM、零网络；缺环（无调用图/无 RTM 映射）如实列入缺口而非硬猜。历史任务真机数据验证：L3 失败场景可输出系统场景、集成用例、单元用例与处理函数位置；逐缺陷命中率实验（E7）已完成 n=3（修复评测仪器后口径 0.467±0.09，详见第 6 章）。

## 5.5 界面与可视化实现

Web 界面按"真数据"原则实现四类页面——所有展示项均来自数据库真实记录，不设演示假数据；以下按页面给出实现要点，页面截图见图 5-1 至图 5-4。

### 5.5.1 任务管理页

任务管理页承载一次测试任务的全生命周期入口：新建任务表单接收仓库地址（Git 或本地目录）与自然语言需求，可勾选自动准备环境；任务列表实时显示状态机所处阶段（排队、克隆、分析、生成、执行、报告），并配顶栏环境状态条——Docker 守护进程、执行镜像、工作区、API 密钥四项逐项探测，缺项时给出中文提示与一键补齐入口；未经人工确认的任务在列表中被标记，防止误下发。

## 5.6 本章小结

本章实现了单元级、集成级与系统级的双轨生成与质量保障：L1 以方法骨架加模板库实现黑盒轨、以覆盖反馈与结构感知实现白盒轨、以三道闸把关生成质量；L2 以端点降级链、契约与调用链双轨、两级断言实现集成层深做；L3 已实现并经真机验证，L4 已实现并经"场景确认→确定性转化"真机验证（转化规模有限，见 5.3）；质量保障链以归因标定、证人冻结、报告双闸、成本台账与四级跨级溯源支撑可信与可审计。下一章以八组研究问题（RQ1–RQ8，对应实验 E1–E8）为组织框架，报告系统的实验与结论。
