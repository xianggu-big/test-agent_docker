# 第1章 绪论

## 1.1 研究背景与意义

软件测试是保障软件质量的核心环节。经典的测试过程理论将测试活动划分为测试分析、测试设计、测试执行与测试评估四个阶段：分析阶段依据需求建立测试条件并冻结准出标准，设计阶段按系统化的用例设计方法产出用例规格，执行阶段在受控环境中运行用例并管理回归，评估阶段对照准出标准核对覆盖与缺陷证据。这一过程在工业标准（如 ISTQB CTFL v4.0）与国际文献中均有成熟定义，但其在实践中的执行高度依赖测试工程师的人力投入：测试条件需要人工从需求中拆解，用例需要人工按等价类划分、边界值分析等方法逐条设计，执行需要人工搭建与维护环境，评估需要人工核对覆盖与缺陷报告。对于迭代频繁的现代软件项目，回归测试的成本随规模线性增长，而覆盖不足导致的缺陷逃逸问题长期存在。

大语言模型（Large Language Model, LLM）的发展为上述痛点的自动化带来了新的可能。LLM 能够理解自然语言需求与程序源码，直接生成测试用例代码；Meta 公司的工程实践表明，LLM 生成的测试改进建议中约 73% 被工程师接受进入生产代码库。然而，将 LLM 直接应用于自动化测试仍面临三类尚未解决的问题。

其一，**测试预言（test oracle）失真**。最新的实证研究表明，LLM 测试生成器的断言倾向于"跟随实现行为"设计——生成器以"用例能通过"为隐式目标，不仅难以暴露缺陷，反而会把程序的错误行为接受为预期，甚至拒绝那些能够暴露缺陷的用例。换言之，如果没有独立于实现的预期值来源与约束机制，LLM 生成的测试可能沦为对现有行为的复述，而非对需求的检验。

其二，**执行环境不可复现**。生成的测试用例需要在真实环境中执行才能产生可信的结果，而依赖安装、环境差异与执行副作用会使"同一份用例、同一份被测代码"在不同环境下产生不同结论。没有隔离与可复现的执行沙箱，测试结论的可信度无从谈起。

其三，**方法组合缺乏量化对比**。现有工作大多针对单一环节（如仅生成、仅修复、仅覆盖率反馈）提出改进，缺少对"测试条件拆解、用例设计方法骨架、失败修复策略、报告审查"等组件的系统性消融实验——实践者无法回答"哪一种 Agent 测试方法组合更有效"这一基本问题。

本课题围绕上述三类问题展开：以大模型 Agent 按软件测试四阶段编排测试全流程，以容器技术承载隔离、可复现、资源受控的执行沙箱，以单元与集成两个层级为深度研究对象、系统与验收两个层级为半自动辅助对象，构建黑盒与白盒双轨的四级自动化测试框架；并通过三方盲测语料协议、控制变量实验矩阵与变异标定方法，量化评估各方法组件对缺陷检出率的贡献。

本课题的意义体现在两个方面。**工程意义**：将测试四阶段理论显式落地为一个端到端可运行的 Agent 系统，用容器技术保证执行结论的可信与可复现，用证据链机制保证"发现的缺陷不被系统自身掩盖"，为 LLM 测试生成的工程化提供一个完整参考实现。**方法论意义**：提出并验证一套面向 Agent 测试的实验评价方法——出题人、答题人、阅卷人三方隔离的盲测语料协议，配合变异测试标定与控制变量消融矩阵，使"方法的有效性"从经验陈述变为可测量、可复现、可被第三方检验的量化结论。

## 1.2 国内外研究现状

**搜索式自动化测试生成。** 在 LLM 出现之前，自动化单元测试生成以搜索式方法（SBST）为主线：EvoSuite 在 Java 平台上基于遗传算法生成断言完整的测试套件，成为该领域的工业级基线；Pynguin 将搜索式生成移植到 Python 生态。这类方法不依赖语义理解，从需求出发的针对性弱，且对复杂依赖的处理能力有限。

**LLM 驱动的测试生成与增强。** Meta 的 TestGen-LLM 是最具代表性的工业实践：它不对已有测试套件做全量重写，而是以"可构建、可靠通过、覆盖率提升"三道准入过滤器筛选 LLM 生成的测试类改进，实测 75% 的生成用例可构建、57% 可靠通过、25% 提升覆盖率，最终 73% 的推荐被工程师接受。该工作的核心启示在于**准入过滤**：不信任 LLM 的原始输出，用确定性过滤器保证"每一条被采纳的用例相对原套件有可度量的改进"。CoverUp 与 CodaMosa 则代表了覆盖率反馈驱动的生成路线：前者将覆盖率分析与代码上下文注入提示词迭代引导 LLM 提升行与分支覆盖（每模块中位覆盖达 80%，显著高于 CodaMosa 的 47%）；后者在传统搜索式生成覆盖率停滞时引入 LLM 生成种子以逃出平台期，确立了"混合驱动"路线。YATE（2025）进一步证明，对 LLM 生成的语法或语义错误用例做"带失败上下文的重写"优于直接丢弃——修复后的坏用例比纯 LLM 生成平均多覆盖 32.06% 的行，说明坏用例往往是贴近程序逻辑的高价值种子。

**批判性证据。** 与上述乐观结果并行，最新实证研究揭示了 LLM 测试生成器的结构性缺陷：以真实带缺陷代码为输入评估主流生成工具后发现，以"通过"为隐式目标的生成器不仅测不出缺陷，还会反向验证缺陷行为、拒绝暴露缺陷的用例。这一结论与本课题在自建语料上的观察一致——即使强制要求生成边界外输入用例，断言的预期值仍会迁就实现行为。该问题在理论上归属于测试预言问题（Oracle Problem）：Barr 等人的综述系统指出，预期值的获取是自动化测试的根本困难；若预期值本身来源于被测实现，则检验关系退化为循环论证。

**测试流程与工程基础设施。** ISTQB CTFL v4.0 为测试过程提供了权威基线，其中测试条件、需求追踪矩阵（RTM）、准出标准等概念是测试管理正统术语；需求追踪的开山工作（Gotel 与 Finkelstein，1994）确立了"需求—工件"双向可追溯的框架。容器化方面，Testcontainers 等框架代表行业"为被测代码提供真实依赖实例"的实践，与本课题"为 LLM 生成物提供隔离执行沙箱"的目的互补；容器性能研究表明容器化本身的开销在正确使用模式下可以忽略。国内研究方面，LLM 测试生成多集中于提示词工程与单点生成探索，以及 ChatUniTest 等工具型工作；覆盖"分析—设计—执行—评估"全流程闭环、且附带系统性消融实验的方案仍属空白。

**研究现状小结。** 现有工作在单点能力上已充分证明 LLM 的可用性，但存在三个系统性缺口：（1）缺少贯穿测试四阶段的闭环系统——生成、执行、归因、报告各环节孤立存在；（2）缺少针对"断言驯化"问题的机制化防线——expected 值的来源约束、失败用例的证据保全、报告的二次审查均未见系统化方案；（3）缺少面向方法组合的量化对比——"测试条件拆解是否有效""修复策略孰优孰劣"等实践问题缺乏受控实验证据。本课题正是针对这三个缺口展开。

## 1.3 研究内容与创新点

本课题的研究内容围绕"一个框架、两级深做、一套实验方法"组织：

（1）**四级双轨自动化测试框架**。以测试级别为应用对象——单元测试（L1）与集成测试（L2）深度自动化，系统测试（L3）半自动辅助、验收测试（L4）辅助并沉淀可执行回归资产；以黑盒与白盒为双轨方法族——黑盒轨覆盖等价类划分、边界值分析、判定表、状态迁移、蜕变测试、错误推测等方法，白盒轨覆盖语句/分支覆盖反馈、调用链分析、变异测试标定。框架以 LangGraph 固定图编排测试流程，以 Docker 容器承载执行沙箱，以 SQLite 数据库沉淀全链路审计台账。

（2）**面向测试预言失真的机制化防线**。针对断言驯化问题，构建"生成三道闸（AST 静态审查、容器内可收集性检查、LLM 交叉语义审查）＋ 失败归因三分类（环境/用例/产品）＋ 缺陷证人冻结（疑似产品缺陷的失败用例永不删除、永不为迁就而修改）＋ 报告二次审查双闸（数字比对规则闸先行、LLM 复核收窄聚焦）"的机制链，并要求每条 AI 生成用例标注预期值出处（expected_basis），使"断言先于执行"从纪律约束升级为可审计数据。

（3）**面向方法对比的量化实验方法论**。构建出题人、答题人、阅卷人三方隔离的盲测语料协议（植入已知缺陷并附答案键，含占位项三分类以修正召回率分母），设计控制变量消融矩阵（每次实验只改变一个方法开关），以 mutmut 变异测试标定归因器混淆矩阵，并以 LLM 调用台账支撑成本—质量联合分析。

（4）**容器化执行沙箱**。常驻容器加 exec 驱动的执行模型、按需构建的镜像注册表、任务级资源限额与超时重建，配合预构建镜像实验量化容器化代价。

其中，（2）与（3）构成本课题的主要创新点：前者是对"LLM 生成器为通过而设计断言"这一实证缺陷的系统性工程回应；后者提供了一套可被第三方复现的 Agent 测试评价方法。

## 1.4 论文组织结构

本文除引言外共分六章。第 1 章绪论，介绍研究背景、研究现状与研究内容。第 2 章相关理论与关键技术，综述软件测试过程理论、用例设计方法族、大模型 Agent 技术、容器化技术、测试预言问题与变异测试，并给出开发环境与技术选型。第 3 章系统需求分析，论证系统可行性，梳理四级双轨业务流转与功能、非功能需求。第 4 章系统设计，给出五层总体架构、编排引擎、容器沙箱与数据层的设计。第 5 章系统实现，阐述单元级与集成级双轨生成、系统级与验收级半自动辅助、质量保障链与界面实现。第 6 章系统测试与实验分析，报告性能对比、修复链路对比、轮次轨迹、变异标定、报告审查与控制变量消融等实验及其结论。最后为结论、致谢与参考文献。
