# 第3章 系统需求分析

## 3.1 系统可行性分析

**技术可行性**。系统全部构建在成熟的开源技术栈之上：流程编排采用 LangGraph 的状态图框架，容器执行采用 Docker 标准接口，大模型能力通过 DeepSeek 的 OpenAI 兼容接口接入。三个组件均有稳定的公开接口与文档。关键组合的可行性已在前期预研中验证：固定图编排可复现地驱动"生成—执行—归因—补测"闭环，容器沙箱可在秒级完成环境准备，LLM 可在方法骨架提示词约束下稳定产出结构化用例。

**经济可行性**。系统仅依赖一台具备 Docker 的开发机与大模型 API：执行侧零额外成本；生成侧成本与大模型调用量线性相关，系统内置的调用台账（按阶段记录提示词/补全/总 token 数）使成本可观测、可控。相比人工测试的人力成本，自动化测试在回归场景下的边际成本显著更低。

**操作可行性**。系统提供 Web 界面：测试人员以"项目地址 + 自然语言需求"发起任务，经 AI 生成、脚本工作台人工确认、下发执行、报告查看等环节完成一次测试；环境自检与自动补齐（拉起 Docker、构建缺失镜像）降低了部署门槛；一键演示脚本支持完整流程复现。

## 3.2 业务流转分析

系统业务流转遵循测试四阶段，并以测试级别组织为四级接力（下文以 L1、L2、L3、L4 分别记单元、集成、系统、验收四个测试级别），总体流转如图 3-1 所示：

**L1 单元测试（全自动闭环）**：用户输入仓库地址与自然语言需求后，系统依次执行克隆与语言占比分析、需求拆解（生成测试条件并落需求追踪矩阵）、容器环境供给、双轨用例生成（黑盒方法骨架 + 白盒覆盖反馈）、容器内执行、失败归因与补测闭环、报告生成与二次审查。全程无需人工介入，仅在任务下发前设人工确认门。

**L2 集成测试（全自动接力）**：L1 结束后由级别编排器自动接力。系统从被测服务提取接口端点（框架探测降级链：OpenAPI 规范确定性解析 → 装饰器路由静态提取 → 诚实降级），构建函数调用图，双轨生成集成用例——契约黑盒轨依据接口契约生成参数与断言，调用链白盒轨依据"创建→使用"顺序构造业务流场景；执行后按级别评估（端点覆盖、契约违背、需求级失败）。

**L3 系统测试（半自动）**：对无法全自动判定的端到端场景，系统生成场景脚本与执行指引，由人工确认实际结果，确认状态回库参与评估。

**L4 验收测试（辅助 + 资产沉淀）**：验收场景确认后，系统尝试将其转化为可执行的回归脚本进入回归基线（转化失败自动退回轻量记录模式），使验收测试的投入沉淀为可持续复用的资产。

两族方法的作用对象随级别递进——单元级作用于函数签名与需求，集成级作用于接口契约与调用图，系统级作用于业务流程，验收级作用于验收准则。据此形成本框架的四级×双轨策略矩阵（表 3-1）。

| 级别 | 黑盒轨（规格驱动） | 白盒轨（结构驱动） | 自动化深度 |
|---|---|---|---|
| 单元级 | 等价类划分、边界值分析、判定表、状态迁移、蜕变测试、属性测试（槽位模板化） | 语句/分支覆盖反馈、覆盖缺口回灌、圈复杂度热点、变异标定 | 深度自动化（全自动闭环） |
| 集成级 | 接口契约用例：参数边界、类型违背、必填缺失、畸形输入与契约断言 | 调用链分析：端点到处理函数映射、顺序约束场景 | 深度自动化（全自动接力） |
| 系统级 | 业务流场景：需求到端到端调用序列、关键路径冒烟 | 辅助造数：按各级覆盖缺口生成场景数据 | 半自动（失败人工介入） |
| 验收级 | 验收场景清单：Given/When/Then 结构化生成 | —（不适用） | 辅助（人工确认，沉淀回归资产） |

表 3-1 四级×双轨自动化策略矩阵

在角色维度，系统设管理员、开发者、调用者三类用户：管理员负责用户与权限管理；开发者负责仓库接入、需求输入、确认门放行与任务操作；调用者可下发任务、查阅报告并进行人工标注。人工确认门与人工标注通道分别是执行前与评估后两个人机协作点。

贯穿四级的是同一条质量保障链：AI 生成物经三道闸审查后方可执行（前两道为确定性闸，第三道为可开关的语义辅助闸），失败按环境/用例/产品三类归因，疑似产品缺陷的失败用例作为"证人"冻结保全，报告由规则闸与大模型闸双重审查。

## 3.3 系统功能需求

**（1）L1 单元测试功能需求**：仓库接入（Git 与本地目录）；语言占比探测与分级策略；需求拆解与测试条件落库；基于黑盒方法骨架（等价类、边界值、判定表、状态迁移、蜕变、错误推测、属性测试，载体见表 2-2）的用例生成，支持模板库、复杂度热点提示、覆盖缺口回灌；生成物三道闸审查；容器内执行与覆盖率采集；失败归因三分类；定向修复（剪除/重写）与补测轮次控制；准出标准判定与轮次轨迹落库。

**（2）L2 集成测试功能需求**：服务容器化启动与健康检查；接口端点提取与调用图构建；契约用例、顺序场景用例、需求断言用例三类生成；契约断言与需求断言两级校验；外键前置数据自动构造；按级指标评估并入任务报告。

**（3）L3/L4 功能需求**：系统级场景生成与人工确认流转；验收场景向可执行回归脚本的转化及失败兜底；确认状态与转化产物落库。

**（4）公共功能需求**：任务管理（新建/确认/下发/停止/列表）；报告页（指标条、需求追踪矩阵、用例六要素表、图表内嵌、叙述与审查徽章）；Agent 会话轨迹查看；镜像与环境管理（状态检测、自动构建）；用户与角色权限（管理员/开发者/调用者）；LLM 调用成本台账。

## 3.4 系统非功能需求

**可复现性**：工具链版本固化于镜像，流程由固定图约束，同一输入在任意时刻重跑产生一致的流程与判定口径——流程结构与判定口径确定可复现；大模型生成内容存在方差，由确定性闸门与固定评估口径吸收，不承诺逐字复现。**可审计性**：所有 AI 生成、执行、评审动作落库留痕（用例库、调用台账、轮次轨迹、会话消息），报告数字全部由确定性代码从数据库计算，LLM 仅负责叙述。**防造假性**：疑似产品缺陷的失败用例冻结保全，禁止为通过而修改断言；报告审查含防造假红线（归因为产品缺陷时禁止声称"已解决"）。**资源安全**：容器任务实施 CPU/内存限额与超时回收，超时后强制重建容器。**诚实降级**：任一能力的前置条件不满足时（无规范、无密钥、无清单），系统显式降级并如实报告，静默失败视为缺陷。**可扩展性**：镜像注册表、技能注册表与方法开关均按注册式设计，新增语言、设计方法或测试级别时只需增量注册，不改动编排骨架。**数据安全**：被测仓库源码与需求文本需发送至大模型服务完成生成与审查，系统仅传输测试必需的最小内容，API 密钥经环境变量注入、不落库不进日志；私有代码场景的本地模型接入列为扩展方向（生成接口已按 OpenAI 兼容协议抽象，供应商可替换）。

## 3.5 本章小结

本章从技术、经济、操作三方面论证了系统可行性，给出了四级接力的业务流转模型，按测试级别与公共能力梳理了功能需求，并明确了可复现、可审计、防造假、资源安全、诚实降级、可扩展与数据安全七项非功能需求。这些需求将转化为下一章的架构设计与模块划分。
