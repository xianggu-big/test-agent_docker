# 第4章 系统设计

## 4.1 总体架构设计

系统采用五层架构（图 4-1），各层职责单一、通过明确接口协作：

**（1）界面层**：Web 应用（FastAPI + 原生前端），提供任务管理、脚本工作台、报告查看、镜像管理四类页面。界面层的核心纪律是"真数据"——所有展示项均来自数据库真实记录，禁止演示假数据；人工确认门、任务级环境守卫在界面层强制执行。

**（2）编排层**：以 LangGraph 状态图实现测试流程编排。主图包含九个节点：克隆→分析→计划（需求拆解与测试条件落库）→环境供给→用例生成→执行→评估→报告→审查。图结构固定，流程可复现；LLM 的规划与判断作为节点产物在确定位置发生。集成测试以子图实现七个节点，由级别编排器在单元级结束后串行接力（各级执行记录以跨级追溯字段链接），避免子图嵌套带来的状态管理复杂度。

**（3）技能层**：所有外部动作（依赖安装、测试执行、用例生成、指标采集、报告生成、审查、绘图）封装为注册表管理的技能（Skill）。每次调用自动落审计台账（调用参数、状态、耗时），高风险技能（执行测试）设人工确认门——确认门在工具层以"未确认即拒绝"的失败封闭方式实施，不依赖界面约束。

**（4）沙箱层**：容器执行器管理常驻容器与 exec 驱动，提供目录快照注入、容器内命令执行（带超时）、容器回收与镜像自动构建。

**（5）数据层**：SQLite 数据库（WAL 模式、外键约束、幂等迁移）沉淀全链路数据，共 22 张表，覆盖任务域、用例域、执行域、评估域与成本域（见 4.3 节）。

架构遵循四条设计原则：**固定图编排**——LLM 做规划但不决定流程走向；**数字确定性**——一切评估数字由确定性代码从数据库计算，LLM 只做叙述；**防造假优先**——宁可误报不可造假，机制上禁止系统掩盖真实缺陷；**诚实降级**——前置条件不满足时显式降级并如实上报，不静默失败。

### 4.2.1 主图流转与条件边

主图节点与测试四阶段的映射为：克隆与分析承担测试前置（环境与被测物分析），计划对应测试分析（需求到测试条件），生成对应测试设计与实现，环境供给与执行对应测试执行，评估、报告与审查对应测试评估与完成。各节点职责如下：**克隆**接入仓库（支持 Git 地址或本地目录）、重建工作区并从库重建人工插入用例；**分析**统计语言占比、确定主语言与分级策略、将准出标准冻结进任务行、落复杂度热点；**计划**调用 LLM 将需求拆解为测试条件（含优先级与方法建议），以删除重插保证重跑幂等；**环境供给**按级别准备镜像与容器、安装被测项目依赖（支持 requirements/pyproject/setup.py 三类清单）；**生成**按策略先做失败用例定向修复（剪除或带失败上下文重写），再生成新用例，生成物经三道闸后写入工作区并回灌容器；**执行**在容器内运行 pytest 并采集覆盖率；**评估**解析结果、归因分类、将本轮轨迹落库并依据轮次预算与指纹熔断作出判定；**报告**落测试报告与叙述；**审查**生成指标包、需求追踪矩阵、叙述报告并执行双闸审查。

各节点的输入输出通过共享状态传递，状态中的关键字段与数据层表一一对应：分析节点写入语言占比与模块分级，计划节点写入测试条件集与冻结后的准出标准，备环境节点写入镜像名与容器标识，生成与执行节点写入用例与脚本版本，评估节点逐轮写入轮次轨迹。这一"节点产物落库"的约定使任何一个中间结论都有表可查——报告层的每个数字最终都能沿"条件→用例→脚本→报告→矩阵"的实体链回溯到产生它的节点，也为跨会话的任务恢复与实验复算提供了基础。

条件边承载控制流：分析节点发现主语言不受支持时诚实短路至报告；执行节点在被测语言的执行链路未接入时（如 Java 镜像就绪但链路未开放）诚实终止并如实说明；评估节点按判定分流——通过/停止进报告，环境失败重供给，用例失败回生成；审查节点对报告拒绝执行受控重写（新快照重写一次、复审一次后必收敛）。

### 4.2.2 失败归因与补测闭环

评估节点将失败归因三类，判定按信号顺序进行：先匹配**环境失败**信号（依赖缺失、容器瞬态丢失等），修复环境重跑；再匹配**用例缺陷**强信号（导入错误、语法错误等），剪除或重写该用例，通过用例保留；最后对断言失败按预期值来源分层处置——预期值出处为需求明示或文档依据的失败用例冻结为"证人"，永不删除、永不为迁就而修改，证据链写入缺陷清单并计入疑似缺陷上报；预期值出处为源码推导的失败属循环断言，不具备指证缺陷的资格，按用例缺陷处置。补测闭环受三重停止条件约束：准出标准达成即收敛；同一失败指纹累计重复两次即熔断、防止原地打转（证人失败不进入指纹计数——有意保留不同于原地打转）；补测轮次预算耗尽即如实上报（默认三轮，各实验格的具体取值见第 6 章实验设置）。归因的判定依据按证据强度分层：最强证据是预期值来源标注——预期值出自需求明示或文档约定的失败，直接指向产品；次强是异常堆栈位置——异常最深帧落在产品源码内指向产品，落在测试文件或导入期指向用例；再次是同点互证——同一函数的其他用例通过而仅该用例失败，指向用例缺陷，多个独立用例在同一行为点失败，指向产品。对于信号模糊的失败，系统以大模型独立复审补充一次判断（审查者不接触原断言，独立推导预期值后比对），仍无法定夺时维持保守默认：宁可把用例缺陷误报为疑似产品缺陷，不可把产品缺陷当用例缺陷改断言——前者的代价是人工过滤一条误报，后者的代价是系统亲手掩盖一个缺陷，两者的错误代价不对称，这一不对称性正是保守默认的依据。

当仅剩证人失败时按覆盖率分流：未达标继续对其余缺口补测，达标则如实停机上报"发现 N 个疑似缺陷"，预算耗尽仍兜底停止。轮次轨迹（每轮通过/失败/覆盖率/判定）由评估节点逐轮落库，作为"学习环"证据与趋势图数据源。

### 4.2.3 各级子图与级间接力

集成级（L2）子图共七个节点，复用"分析—设计—执行—评估"骨架，其中四个专属环节为：**接口端点提取**（优先解析项目自带的 OpenAPI 规范并展开引用；无规范时按框架路由做确定性静态提取；两者皆无则诚实降级上报）、**调用链分析**（以 AST 构建静态调用图，以路由处理函数为根）、**契约用例生成**（契约断言与需求断言两级）与**前置数据构造**（外键关联数据自动准备），其余节点承担服务供给、用例执行与本级评估，执行环节的被测服务托管方案见 4.4 节。

系统级（L3）子图共四个节点——**准备**（装配被测服务依赖并启动服务）、**场景生成**、**冒烟执行**与**报告**，遵循"冒烟自动判定、仅失败人工介入"的半自动语义：场景由大模型生成，但静态闸保证每个步骤的方法与路径必须命中集成级提取的端点清单，虚构接口直接剔除；冒烟脚本将前序步骤的响应值注入后续步骤的路径参数，形成"创建→按 id 读取"式引用链；执行后通过场景自动判定，失败场景转人工定性，人工确认状态落库并参与指标计算。验收级（L4）按设计不设执行节点，由场景清单生成与人工确认构成，确认后的场景可转化为可执行回归资产（实现见 5.3 节，当前为设计态）。

级别间由**级别编排器**串行接力：每个"任务×级别"在台账表中一行，记录级别策略（完整执行/半自动/辅助/降级）、状态、终判与指标摘要；上一级的台账行标识作为追溯键写入下一级，形成"验收←系统←集成←单元"的跨级追溯链头。级别间接力遵循"记录不传播"原则：每一级的判定独立作出、独立终止——单元级因证人停机不会阻止集成级启动，集成级的契约违背也不会改写单元级已冻结的终判；跨级传递的只有两类信息，其一是接力台账行（级别策略、终态与指标摘要），其二是追溯键。这样设计的原因与评估节点的单快照语义一致：判定权集中在本级，跨级的只有事实而非结论，避免任何一级"替"另一级改判，也使"验收级失败沿链定位到单元级"的反向查询永远成立。

级别开关默认关闭时系统行为与单元级单级模式保持一致，保证向后兼容。

## 4.3 数据模型设计

数据层 22 张表按域组织：

**任务域**：用户、项目（语言占比）、测试任务（状态机、确认门、冻结的准出标准）、测试级别台账（任务×级别的执行记录与跨级追溯键）、接口端点与调用边（集成级白盒数据）、测试条件（RTM 条件层）、RTM 快照（评估期矩阵）。

**用例域**：测试脚本（版本化）、测试用例（来源三分类：内置/AI/人工导入；六要素结构化：编号、名称、优先级、输入、步骤、预期；预期值出处 expected_basis；启用状态）、场景用例（系统级与验收级的业务流场景：步骤序列、Given/When/Then 预留结构与人工确认三态）。

**执行域**：容器任务台账（镜像、限额、起止）、技能调用台账（全量审计）、会话与消息（Agent 交互轨迹）。

**评估域**：测试报告（通过/失败/覆盖、逐文件覆盖明细、疑似缺陷、叙述正文、审查结论）、评估轮次（每轮轨迹的唯一真源）、复杂度热点快照、反馈标注（误报/漏报人工标注闭环）。

**成本域**：LLM 调用台账（阶段、提示词/补全/总 token），单元级主链路共七个调用点（计划、生成、补生成、重写、矩阵映射、报告叙述、报告审查），级别子图的调用以级别前缀记入同一台账，支撑成本—质量联合分析。

全链路的证据实体构成一条可回溯的路径：需求经计划节点固化为测试条件，条件经生成节点物化为六要素用例，用例经版本化脚本进入沙箱执行，执行结果经评估节点沉淀为轮次轨迹与报告，最终由矩阵快照把"需求—条件—用例—结果"四层连接起来。沿这条路径的每一步都可从报告反向走到需求，也可从需求正向检查覆盖，这是第 3 章可追溯性非功能需求的落点。写入语义按数据性质分为两型：状态随评估变化的数据（矩阵快照、热点快照、轮次轨迹、计划条件）采用删除重插、以本轮为准；过程累积的数据（技能调用、大模型调用、会话消息）采用只追加不删改——前者保证任务重跑不留脏数据，后者保证成本与审计口径天然累积，两型各得其所。

数据层以幂等迁移保证老库自动升级；全部新表采用"追加不删改"或"删除重插"的显式幂等语义，使任务重跑不产生脏数据。22 张表的完整清单如表 4-1 所示。

## 4.4 容器沙箱设计

沙箱层采用**常驻容器 + exec 驱动**模型：容器以休眠命令常驻，每次测试通过 exec 在容器内执行，多轮补测复用同一容器保留依赖缓存；任务结束统一回收。四项机制保证执行质量：

（1）**镜像注册表与自适应准备**：按语言维护镜像注册表（Python/Java），任务级环境检测发现缺失镜像时自动构建（支持国内镜像源参数），构建失败如实上报；（2）**干净环境保证**：任务下发前预清理残留容器；执行超时（死锁、资源争抢）后强制重建容器，避免旧进程污染新一轮判定；（3）**资源限额**：CPU/内存限额在容器启动参数实施，配合执行超时实现任务级资源安全；（4）**依赖三清单支持**：requirements.txt 走清单安装，pyproject.toml/setup.py 项目走项目构建安装，无清单项目诚实跳过并说明。

执行环境的准备分为三个阶段：**镜像预构建**阶段把与项目无关的工具链（解释器、pytest 及覆盖、复杂度、变异分析插件）锁死版本打入镜像，是可复现性的基础；**按需构建**阶段依据分析得出的主语言从注册表选择镜像，本地缺失时以注册表中的构建上下文现场构建；**任务内安装**阶段处理与项目相关的依赖，按三类清单在容器内安装。三个阶段分离的意义在于把"变的部分"（项目依赖）与"不变的部分"（工具链）分开治理——前者逐任务安装、允许网络波动重试，后者一次构建、跨任务复用。运行期的自愈机制处理两类异常：单步执行超时或容器僵死时强制重建容器，防止上一轮的残留进程污染下一轮判定；任务异常退出留下的孤儿容器由定期清扫回收。

集成级与系统级需要被测服务在沙箱内运行：当前采用单容器内启动服务的方案，自动探测应用模块并以 OpenAPI 规范文件作为服务就绪的健康检查；容器网络互通的双容器模型列为后续演进。该降级路径在设计中显式声明，而非静默处理。

容器内以非特权用户执行，工作目录归属测试用户；执行与判定分离——容器只运行测试，所有判读在宿主侧基于结构化输出完成，容器内不持有任何判定逻辑。

## 4.5 本章小结

本章给出了系统的五层总体架构与四条设计原则，设计了九节点主图加级别接力的编排引擎（含失败归因三分类、三重停止条件与审查受控重写），规划了 22 张表的数据模型（覆盖任务、用例、执行、评估、成本五域），并阐述了常驻容器加 exec 驱动的沙箱设计。下一章将在此架构上详述四级双轨的用例生成方法、质量保障机制与界面实现。
