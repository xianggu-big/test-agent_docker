# 第2章 相关理论与关键技术

## 2.1 软件测试过程理论

### 2.1.1 测试四阶段过程

国际软件测试资格委员会（ISTQB）的基础级大纲（CTFL v4.0）将测试过程划分为七个活动：测试计划、测试监控与控制、测试分析、测试设计、测试实现、测试执行与测试完成。工程实践中通常将其归纳为四个阶段：**测试分析阶段**基于需求与性能要求制定测试条件、建立需求追踪矩阵（RTM）、确定准出标准（exit criteria）并选择测试内容与资源；**测试设计阶段**依据系统化的用例设计方法产出用例规格，其规格包含编号、测试标题、重要级别、测试输入、操作步骤与预期结果六要素；**测试执行阶段**按优先级在受控环境中运行用例并组织回归；**测试评估阶段**对照分析阶段冻结的准出标准核对量化覆盖与缺陷证据，形成测试报告。

本课题采用上述四阶段作为 Agent 编排的顶层结构，并继承其中三条关键纪律。第一，**准出标准在分析阶段冻结**：行覆盖率阈值与补测预算在测试开始前确定，评估阶段只对照该标准判定收敛，避免"先看结果再定标准"的事后合理化。第二，**需求可追溯**：每条测试条件记录其需求来源（requirement_ref），使需求变更时能够反向定位受影响的测试条件与用例。第三，**测试会磨损**（tests wear out）：重复执行同一批测试对新增缺陷的检出力递减，这一原则为"失败后重生成用例"的补测闭环提供了理论依据——简单地重跑旧用例不构成有效补测。

### 2.1.2 需求追踪矩阵

需求追踪矩阵（Requirements Traceability Matrix, RTM）由 Gotel 与 Finkelstein 于 1994 年提出，用于维护"需求—下游工件"的双向可追溯关系。在测试语境下，RTM 的作用有二：正向保证每条需求都有测试条件与用例覆盖；反向在需求变更或缺陷暴露时，能够从失败结果回溯到需求条款与实现位置。本课题将 RTM 落地为三级实体链——需求→测试条件（test_conditions）→测试用例（test_cases），并在评估阶段生成矩阵快照以计算条件覆盖率与缺口。

## 2.2 测试用例设计方法族

### 2.2.1 黑盒方法

黑盒方法依据需求规格而非内部结构设计用例，本课题覆盖其中七种：

（1）**等价类划分**：将输入域划分为有效与无效等价类，每类取代表值，以少量用例覆盖大量输入组合。（2）**边界值分析**：缺陷集中于输入域的边界，取 min-1、min、min+1、max-1、max、max+1 等边界邻域值构造用例；实证表明数值型缺陷中边界类占比最高。（3）**判定表**：对多条件组合逻辑列出条件全组合或化简后的主要组合，每组合一条用例。（4）**状态迁移测试**：面向有状态对象，覆盖状态机的迁移路径与非法迁移的拒绝行为。（5）**蜕变测试**：不依赖精确预期值，而是验证"输入变换后输出应满足的 relation"，适用于预期值难以独立确定的场景，是缓解测试预言失真的经典手段。（6）**错误推测法**：基于常见缺陷模式（None、空串、零值、负数、极大值、类型错配、除零、重复调用）做攻击性设计，ISTQB 将其归入经验类技术。（7）**随机测试与属性测试（PBT）**：前者随机生成输入做广谱探测，后者（以 Hypothesis 为代表）从性质/不变量出发生成输入并收缩反例，断言天然先于执行。

### 2.2.2 白盒方法

白盒方法依据程序内部结构设计或评估用例：（1）**语句/分支覆盖**：基于控制流图度量每条语句、每个分支是否被执行，是覆盖率准出标准的基础；（2）**调用链分析**：从模块间调用关系定位集成层用例应覆盖的路径；（3）**数据流分析**：追踪变量的定义—使用链以发现引用异常；（4）**变异测试**：向被测代码注入人工缺陷（变异体），检验用例集能否杀死变异体，以此度量用例集的"缺陷检出能力"——覆盖率度量"测试执行了什么"，变异得分度量"测试查出了什么"，二者互补。

## 2.3 大模型与 Agent 技术

### 2.3.1 大语言模型的测试生成能力与局限

LLM 在代码理解与生成上表现出接近初级工程师的能力，可以从自然语言需求与源码直接产出测试用例。但其结构性局限同样明确：**幻觉**——生成不存在的接口引用或文献引用；**断言驯化**——以通过为隐式目标，预期值迁就实现行为（见 1.2 节）；**输出不稳定**——同一提示词多次调用产出在格式与内容上存在方差。这些局限决定了工程方案必须"不信任原始输出"：以确定性过滤器（静态审查、可收集性检查、数字比对）先行把关，LLM 仅承担语义理解与叙述类职责。

### 2.3.2 Agent 编排模式

LLM Agent 是"以 LLM 为决策核心、以工具调用为执行手段"的系统。编排模式可分为两类：**自由 Agent 模式**由 LLM 在运行时自主决定下一步动作（如 ReAct 范式的"思考—行动—观察"循环），灵活但不可复现、难以画图与审计；**固定图模式**以预先定义的状态图约束流程，LLM 的规划与判断作为图节点的产物在确定的位置发生，流程本身确定、可复现、可审计。对于测试这类过程规范成熟、步骤可预先定义的领域，固定图模式与 ISTQB 过程理论天然同构，本课题据此选择固定图编排，并将"LLM 做 plan"落位为两个节点的产物——分析阶段的需求拆解节点（产出测试条件）与设计阶段的用例生成节点（按方法骨架产出用例），而非让 LLM 自主决定流程走向。

## 2.4 容器化技术

操作系统级虚拟化（容器）通过命名空间与控制组（cgroup）为进程提供隔离的文件系统、网络与资源视图。Docker 是其事实标准实现。本课题使用容器的三个特性：（1）**隔离性**——被测代码与其依赖在容器内安装运行，宿主机不暴露于测试副作用；（2）**可复现性**——工具链版本固化在镜像中，"同一镜像 + 同一代码"在不同机器上产生一致结论，满足实验可复现要求；（3）**资源可控性**——通过 --cpus/--memory 参数实施任务级资源限额，防止单个测试任务耗尽宿主资源。性能方面，既有研究表明容器化在正确使用模式下的开销可以忽略；本课题的预构建镜像实验亦独立证实了这一点（见第 5 章）。执行模型采用**常驻容器 + exec 驱动**：容器以 sleep infinity 常驻，每次测试通过 docker exec 在容器内执行，多轮补测复用同一容器以保留依赖安装缓存，任务结束统一回收。

## 2.5 测试预言问题与变异测试

**测试预言问题**（Oracle Problem）指"为测试判定正确与否而获取预期值"的根本困难。Barr 等人的综述将其系统化分类，并指出预言的来源（人工规约、模型、实现自身、元变关系）决定了测试能够发现何种缺陷：若预期值来源于被测实现本身，则无论用例多少，检验关系都是循环的。这一理论为本课题的两项设计提供了依据：其一，要求 AI 生成用例标注预期值出处（expected_basis：需求明示/文档/源码推导/常识），"源码推导"类的失败用例不具备指证缺陷的资格；其二，蜕变测试等"弱预言"方法作为预期值缺失场景的补充。

**变异测试**由 DeMillo 等人提出、Jia 与 Harman 系统综述：向被测代码注入人工缺陷（变异体），若测试套件能导致变异体上的测试失败（杀死变异体），则证明该套件具备暴露此类缺陷的能力；存活变异体则指示测试套件的盲区。变异得分（杀死比例）因此成为"测试有效性"的成熟度量。本课题将变异测试用于两个目的：一是作为**标定仪器**——向语料注入已知缺陷，测量归因器的混淆矩阵，回答"归因器本身有多准"；二是度量"有效用例率"，交叉验证覆盖率指标的不足（高覆盖率可能伴随低检出力）。

## 2.7 本章小结

本章建立了论文的理论坐标系与技术底座——四阶段过程定义了 Agent 编排的顶层结构，用例设计方法族构成双轨方法池，Agent 与容器技术提供实现手段，测试预言问题与变异测试为"防造假"与"有效性度量"提供理论工具，开发环境与技术选型则给出工程实现的基础。后续三章将把这些理论要素组装为一个可运行的系统。
