# 第2章 相关理论与关键技术

## 2.1 软件测试过程理论

### 2.1.1 测试四阶段过程

国际软件测试资格委员会（ISTQB）的基础级大纲（CTFL v4.0）将测试过程划分为七个活动：测试计划、测试监控与控制、测试分析、测试设计、测试实现、测试执行与测试完成。工程实践中通常将其归纳为四个阶段：**测试分析阶段**基于需求制定测试条件、建立需求追踪矩阵（RTM）、确定准出标准（exit criteria）并选择测试内容与资源；**测试设计阶段**依据系统化的用例设计方法产出用例规格，其规格包含编号、名称、优先级、输入、步骤与预期结果六要素（对应 ISTQB 用例规格的标题、重要级别等字段，本文统一采用前一种称谓）；**测试执行阶段**按优先级在受控环境中运行用例并组织回归；**测试评估阶段**对照分析阶段冻结的准出标准核对量化覆盖与缺陷证据，形成测试报告。

本课题采用上述四阶段作为 Agent 编排的顶层结构，并继承其中三条关键纪律。第一，**准出标准在分析阶段冻结**：行覆盖率阈值与补测预算在测试开始前确定，评估阶段只对照该标准判定收敛，避免"先看结果再定标准"的事后合理化。第二，**需求可追溯**：每条测试条件记录其需求来源（requirement_ref），使需求变更时能够反向定位受影响的测试条件与用例。第三，**测试会磨损**（tests wear out）：重复执行同一批测试对新增缺陷的检出力递减，这一原则为"失败后重生成用例"的补测闭环提供了理论依据——简单地重跑旧用例不构成有效补测。

### 2.1.2 需求追踪矩阵

需求追踪矩阵（Requirements Traceability Matrix, RTM）由 Gotel 与 Finkelstein 于 1994 年提出[11]，用于维护"需求—下游工件"的双向可追溯关系。在测试语境下，RTM 的作用有二：正向保证每条需求都有测试条件与用例覆盖；反向在需求变更或缺陷暴露时，能够从失败结果回溯到需求条款与实现位置。本课题将 RTM 落地为三级实体链——需求→测试条件（test_conditions）→测试用例（test_cases），并在评估阶段生成矩阵快照以计算条件覆盖率与缺口。

### 2.1.3 测试级别与分层策略

测试级别刻画"测试在什么粒度上展开"。ISTQB 基础级大纲将测试级别划分为组件（单元）、组件集成、系统、系统集成与验收五级，各对应不同的被测对象、测试依据与缺陷类型。级别之间的对应关系在 V 模型中表述得最为清晰：需求分析对应验收测试、系统设计对应系统测试、概要设计对应集成测试、详细设计与编码对应单元测试——开发每推进一步，测试都有一级与之对位。V 模型的意义在于揭示了"缺陷越晚发现，修复成本越高"，测试层级因此不是随意的分类，而是与开发阶段的对应承诺。

分层的实践依据是测试金字塔：底层的单元测试应远多于穿过界面层的高层测试，以形成均衡的自动化组合[28]。金字塔的经济学直觉很直接——单元测试执行快、定位准、维护便宜，而高层测试慢、脆、依赖环境；把自动化重心放在基座，才能支撑高频回归。ISTQB 基础级大纲已将测试金字塔纳入正文（§5.1.6），与用例优先级、四象限并列。

在金字塔之外，敏捷测试四象限从"面向谁"与"评价还是支撑"两个维度给出补充分类[29]：Q1（技术面向、支撑开发）为单元与组件测试；Q2（业务面向、支撑开发）为功能与验收示例；Q3（业务面向、批判产品）为探索式测试与场景验证；Q4（技术面向、批判产品）为非功能测试（性能、安全）。这一分类的价值在于它明确区分了"验证已知"与"探索未知"：前两象限适合自动化，后两象限依赖人的判断与经验。

本课题据此确定级别策略：**单元与集成两级实现深度自动化**——两者的测试依据（需求条件、模块接口）可被显式表达，判据可被确定性断言承载，正是金字塔基座与 Q1/Q2 象限的主场；**系统与验收两级实现半自动化辅助**——系统级仅做业务流冒烟（验证链路可跑通，不做界面自动化），验收级以 Given-When-Then 清单形式辅助人工确认，因为这两级的判据涉及业务语义与用户可接受度，超出本文范围。Q3、Q4 两象限（探索式测试、性能与安全测试）不在本课题研究范围内，第 3 章范围界定与之呼应。

这一级别策略同时解释了第 4 章四级递进设计的由来：四级并非并列铺开，而是按"判据可表达性"递减地分配自动化深度——这是有限工程预算下的分层取舍，而非能力缺失。

## 2.2 测试用例设计方法族

### 2.2.1 黑盒方法

黑盒方法依据需求规格而非内部结构设计用例，本课题围绕其中七种展开（各方法的系统载体与实现状态见表 2-2）：

（1）**等价类划分**：将输入域划分为有效与无效等价类，每类取代表值，以少量用例覆盖大量输入组合，其学术形式化为 Ostrand 与 Balcer 的类别划分方法[16]。（2）**边界值分析**：缺陷集中于输入域的边界，取 min-1、min、min+1、max-1、max、max+1 等边界邻域值构造用例；经验表明数值型缺陷中边界类占比最高。（3）**判定表**：对多条件组合逻辑列出条件全组合或化简后的主要组合，每组合一条用例。（4）**状态迁移测试**：面向有状态对象，覆盖状态机的迁移路径与非法迁移的拒绝行为，其理论模型源于有限状态机测试[17]。（5）**蜕变测试**：不依赖精确预期值，而是验证"输入变换后输出应满足的 relation"（Chen 等人的综述系统总结了该方法[18]），适用于预期值难以独立确定的场景，是缓解测试预言失真的经典手段。（6）**错误推测法**：基于常见缺陷模式（None、空串、零值、负数、极大值、类型错配、除零、重复调用）做攻击性设计，ISTQB 将其归入经验类技术。（7）**随机测试与属性测试（PBT）**：前者源于程序随机测试与定向随机测试的谱系[20]，后者源于 QuickCheck[19]、以 Hypothesis 为 Python 生态代表，从性质/不变量出发生成输入并收缩反例，断言天然先于执行；其性质仍来源于需求规格，故按本框架归入黑盒轨。

### 2.2.2 白盒方法

白盒方法依据程序内部结构设计或评估用例：（1）**语句/分支覆盖**：基于控制流图度量每条语句、每个分支是否被执行，是覆盖率准出标准的基础；（2）**调用链分析**：从模块间调用关系定位集成层用例应覆盖的路径；（2a）**圈复杂度分析**：以 McCabe 复杂度度量控制流复杂度，高复杂度函数构成优先测试的热点；（3）**数据流分析**：追踪变量的定义—使用链以发现引用异常[21]；（4）**变异测试**：向被测代码注入人工缺陷（变异体），检验用例集能否杀死变异体[22]，以此度量用例集的"缺陷检出能力"——覆盖率度量"测试执行了什么"，变异得分度量"测试查出了什么"，二者互补。

### 2.2.3 风险驱动的测试资源分配与路线选择

**风险驱动测试**主张测试投入应按风险而非均匀分配。风险可形式化为"失效概率 × 失效影响"：失效概率高的模块（复杂、变更频繁、历史缺陷集中）与失效影响大的模块（被广泛依赖、承载核心业务）应优先获得测试资源。这一思路在工程实践中有多种表述[30]，ISTQB 基础级大纲亦将其列为测试计划阶段的核心活动（§5.2 基于风险的测试）。

本课题将风险的三个代理指标确定性化：**控制流复杂度**（McCabe 圈复杂度，见 2.2.2）、**扇入度**（模块被其他模块引用的次数，反映影响面）、**变更频率**（版本历史中该路径的改动次数）。三者均可由静态分析与版本历史计算，不依赖人工判断，因而可作为自动化系统的输入。第 5 章的复杂度热点分析即这一思路在单模块粒度上的落地；更细的模块级资源画像与分配策略属后续工作。

在方法族之上还存在一层"路线"概念需要澄清：**测试路线 = 观察方式 × 判据类型**。观察方式指以何种入口取得被测对象的可观察行为（进程内调用、HTTP 请求、界面操作、命令行执行、数据库查询、源码静态分析）；判据类型指以何物判定结果正确（显式断言、契约符合、状态不变量、参照物差分、静态规则、覆盖缺口）。同一方法族的用例可以沿不同观察方式实现——例如等价类划分既可写成进程内单元测试，也可写成对 HTTP 接口的请求；而同一观察方式可以承载不同判据——例如界面操作既可断言元素可见（显式断言），也可断言"连续点击后列表条目数不变"（状态不变量）。

需要与之区分的是**自动化实现架构**，它回答"脚本如何组织与复用"（2.3.3 节），属于工程实现层，与方法层正交。本课题将测试路线落在方法层，把具体工具链（pytest、Playwright、httptest、gRPC 客户端等）视为路线的实现后端——这一区分使"同一路线跨语言复用"成为可论证的命题：语言只决定后端，不改变路线本身。

路线选择遵循两条纪律。其一，**前置条件必须由确定性代码判定**：某条路线是否适用（例如界面路线要求存在可交互的页面元素、契约路线要求服务可启动并暴露接口）应由文件特征与运行探测决定，而非由大模型"自由选择"——否则路线选择本身就成了幻觉来源。其二，**每条候选路线必须留下"选/不选 + 理由"**：被剔除的路线同样记录剔除原因，使路线决策可审计、可复盘。这两条纪律同时为大模型时代的"上下文驱动"[32]提供了工程化形态：承认没有普适最优策略，但把"依上下文而定"落实为可复现的确定性判据与可追溯的决策记录。

## 2.3 大模型与 Agent 技术

### 2.3.1 大语言模型的测试生成能力与局限

LLM 在代码理解与生成上表现出接近初级工程师的能力，可以从自然语言需求与源码直接产出测试用例。但其结构性局限同样明确：**幻觉**——生成不存在的接口引用或文献引用；**断言驯化**——以通过为隐式目标，预期值迁就实现行为（见 1.2 节）；**输出不稳定**——同一提示词多次调用产出在格式与内容上存在方差。这些局限决定了工程方案必须"不信任原始输出"：以确定性过滤器（静态审查、可收集性检查等，报告层另有数字比对规则闸）先行把关，LLM 仅承担语义理解与叙述类职责。

### 2.3.2 Agent 编排模式

LLM Agent 是"以 LLM 为决策核心、以工具调用为执行手段"的系统。编排模式可分为两类：**自由 Agent 模式**由 LLM 在运行时自主决定下一步动作（如 ReAct 范式的"思考—行动—观察"循环[23]；SWE-agent 等软件工程 agent 即取此路线[24]），灵活但不可复现、难以画图与审计；**固定图模式**以预先定义的状态图约束流程，LLM 的规划与判断作为图节点的产物在确定的位置发生，流程本身确定、可复现、可审计。对于测试这类过程规范成熟、步骤可预先定义的领域，固定图模式与 ISTQB 过程理论天然同构，本课题据此选择固定图编排，并将"LLM 做 plan"落位为两个节点的产物——分析阶段的需求拆解节点（产出测试条件）与设计阶段的用例生成节点（按方法骨架产出用例），而非让 LLM 自主决定流程走向。

### 2.3.3 自动化架构谱系与关键字驱动的现代形态

测试自动化并非只有"写脚本"一种形态。Fewster 与 Graham 系统总结了自动化架构的演化谱系[31]：**线性脚本与录制回放**（脚本与数据混杂，维护成本最高）→ **模块化**（抽取公共函数）→ **库架构**（共享库与工具层）→ **数据驱动**（脚本与数据分离，同一脚本由数据表驱动多次执行）→ **关键字驱动**（数据中承载"动作关键字"，由解释器翻译为具体操作，形成"测试设计者—解释器—驱动器"三层结构）→ **混合架构**（数据驱动与关键字驱动结合）→ **页面对象**（以页面对象封装元素定位与操作，降低界面测试的维护成本）。这一谱系后来被 ISTQB 高级大纲的通用测试自动化架构（gTAA）吸收为标准术语。

本课题的**槽位模板机制**可视为关键字驱动架构在 LLM 时代的一种现代形态。二者的结构对应关系是直接的：关键字驱动把"要执行什么动作"从脚本中抽离为数据表中的关键字，由解释器负责翻译；槽位模板把"用例的结构骨架"预先固化为代码模板（等价类参数化、边界六点、判定表、状态迁移、缺陷模式五类），把"本次要用哪些输入值、什么预期值"抽离为大模型填充的槽位数据。差别仅在于解释器的实现方式：关键字驱动用确定性解释器翻译关键字，槽位模板用确定性渲染器把槽位数据代入模板。

这一对应关系解释了两个实验观察。第一，**模板通道的产物通过率更高**：结构骨架由确定性代码保证（参数化声明、断言形式、函数命名均固定），大模型只在槽位层出错，而槽位错误（类型不符、缺少预期值）可被槽位校验器确定性拦截；相比之下自由生成通道中"结构错误"与"内容错误"混在一起，任何一处出错都导致整案废弃。第二，**模板通道的单位产出成本更低**：大模型无需重复输出参数化装饰器、循环结构等样板代码，输出 token 集中于输入值与预期值，因而在相同检出水平下消耗更少。

页面对象架构本课题未采用：界面路线以"可达性树 + 选择器三形态校验"替代页面对象封装，在一次性生成场景下避免了引入需长期维护的页面对象层；相应地，界面用例的可维护性弱于页面对象架构，这一取舍列入后续工作。验收级的 Given-When-Then 清单则与行为驱动开发（BDD）的规格形式同源，本课题只取其"可执行规格"的表达方式，不引入完整的 BDD 工具链。

## 2.4 容器化技术

操作系统级虚拟化（容器）通过命名空间与控制组（cgroup）为进程提供隔离的文件系统、网络与资源视图。Docker 是其事实标准实现[14]。本课题使用容器的三个特性：（1）**隔离性**——被测代码与其依赖在容器内安装运行，宿主机不暴露于测试副作用；（2）**可复现性**——工具链版本固化在镜像中，"同一镜像 + 同一代码"在不同机器上产生一致结论，满足实验可复现要求；（3）**资源可控性**——通过 --cpus/--memory 参数实施任务级资源限额，防止单个测试任务耗尽宿主资源。性能方面，既有研究表明容器化在正确使用模式下的开销可以忽略；本课题的预构建镜像实验亦独立证实了这一点（实验见第 6 章）。执行模型采用**常驻容器 + exec 驱动**：容器以 sleep infinity 常驻，每次测试通过 docker exec 在容器内执行，多轮补测复用同一容器以保留依赖安装缓存，任务结束统一回收。

## 2.5 测试预言问题与变异测试

**测试预言问题**（Oracle Problem）指"为测试判定正确与否而获取预期值"的根本困难。Barr 等人的综述将预言来源系统化分类（人工规约、模型推导、隐式关系等）：预期值的来源决定了测试能够发现何种缺陷——若预期值取自被测实现自身，则无论用例多少，检验关系都是循环的。这一理论为本课题的两项设计提供了依据：其一，要求 AI 生成用例标注预期值出处（expected_basis：需求明示/文档/源码推导/常识），"源码推导"类的失败用例不具备指证缺陷的资格；其二，蜕变测试等"弱预言"方法作为预期值缺失场景的补充。

**变异测试**由 DeMillo 等人提出、Jia 与 Harman 系统综述：向被测代码注入人工缺陷（变异体），若测试套件能导致变异体上的测试失败（杀死变异体），则证明该套件具备暴露此类缺陷的能力；存活变异体则指示测试套件的盲区。变异得分（杀死比例）因此成为"测试有效性"的成熟度量。本课题将变异测试用于两个目的：一是作为**标定仪器**——向语料注入已知缺陷，测量归因器的混淆矩阵，回答"归因器本身有多准"；二是度量"有效用例率"，交叉验证覆盖率指标的不足（高覆盖率可能伴随低检出力）。

## 2.6 开发环境与技术选型

系统开发环境与主要技术选型如表 2-1 所示。选型遵循三条原则：一是成熟稳定，全部采用有大规模使用基础的开源组件与标准接口；二是可复现，工具链版本锁死于预构建镜像，实验环境可精确重建；三是可审计，各组件的调用均能落入统一的审计台账。

表 2-1 开发环境与主要技术选型

| 类别 | 选型 | 用途 |
|---|---|---|
| 开发语言 | Python 3.12 | 系统实现语言，同时是深度支持的被测语言 |
| Web 框架 | FastAPI + Uvicorn | 界面层 HTTP 服务 |
| 流程编排 | LangGraph | 固定状态图编排与条件边 |

## 2.7 本章小结

本章建立了论文的理论坐标系与技术底座——四阶段过程定义了 Agent 编排的顶层结构，用例设计方法族构成双轨方法池，Agent 与容器技术提供实现手段，测试预言问题与变异测试为"防造假"与"有效性度量"提供理论工具，开发环境与技术选型则给出工程实现的基础。同时，测试级别与分层策略（2.1.3）界定了四级递进的取舍依据，风险驱动与路线选择（2.2.3）给出了资源分配与路线决策的理论约束，自动化架构谱系（2.3.3）则把槽位模板定位为关键字驱动架构的现代形态——三节共同构成了"方法—级别—实现"三层之间的理论衔接。第 3 章将把这些理论要素转化为明确的系统需求，第 4、5 章将其组装为一个可运行的系统。
