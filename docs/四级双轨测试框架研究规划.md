## 0. 一页结论

1. **框架命题**：以 ISTQB 四级测试级别（单元/集成/系统/验收）为骨架，黑盒（规格驱动）+ 白盒（结构驱动）双轨方法族作用于每一级，形成"分析→生成→执行→覆盖反馈→补盲→回归"的分层闭环；深度递进——L1 单元深做（已闭环）/ L2 集成深做（新建主战场）/ L3 系统半自动 / L4 验收人工辅助。
2. **不是推倒重来**：现有单元层系统整体成为 L1 子图（框架最厚的一层、唯一有完整实证数据的一层），底座五件（LangGraph 编排/Docker 沙箱/SQLite+RTM/评估工具/llm_calls 台账）全部复用只加"层级"维度。
3. **创新点三个**（§5）：层级×双轨二维组合框架与跨级评价矩阵、四级 RTM 跨级缺陷溯源（原被砍的切口②复活）、层间+轨间双维自适应调度。
4. **理论主线一句话**：黑盒/白盒是**设计技术**（级别无关），同一族技术在不同级别的**作用对象**不同（L1=函数签名+需求 → L2=接口 schema+调用图 → L3=业务流程 → L4=验收准则）——"方法族 × 级别"的二维组合就是框架的理论贡献，也是"不是扩范围而是深化"的论据。
5. **硬节点倒排**：开题 2026-11-06 → 初稿+中期 2027-02-25（系统可运行+论文初稿，口径=L1 完整+L2 可演示）→ 定稿 2027-04-09 → 答辩 2027-04-24。

## 3. 分层架构设计

### 3.1 编排：外层级别调度 + 各级子图

```
analyze_repo → level_plan → ┌ L1 子图（=现有 9 节点主图原样）─┐
                            ├ L2 子图（新建）────────────────┤ → 跨级汇聚评估 → 四级 RTM 汇总 → 总报告+总审查
                            ├ L3 生成+冒烟（半自动）─────────┤
                            └ L4 场景清单生成（人工确认）────┘
```

- **口径延续**："固定图做骨架，LLM 的 plan 是节点产物"——`level_plan` 节点产物 = 各级测试计划（启用哪些级别、各级策略权重、各级别条件拆解），不是自由流程控制。
- 级别间支持串行（默认）与按配置裁剪（只跑 L1 = 现状零变化，向后兼容）。
- 各级子图内部复用现有节点形态：clone/analyze → plan → provision → generate → run → evaluate → report → review。

### 3.2 L2 集成层设计（新建主战场）

| 环节 | 设计 |
|---|---|
| 输入 | repo + 需求 + OpenAPI spec（有则解析；无则 LLM+AST 从 FastAPI/Flask 路由源码静态提取端点表——白盒轨副产品） |
| 黑盒轨 | 契约用例生成：参数边界/类型违背/必填缺失/畸形 payload；断言两级=契约断言（status/schema）+ 需求断言（业务语义） |
| 白盒轨 | call graph 静态分析（AST 起步）→ 端点→服务→函数映射 → 顺序约束场景（先创建后查询类） |
| 执行 | **双容器模型**：被测服务容器 + 测试执行容器网络互通（docker network，健康检查等待就绪）——沙箱主要新工程点 |
| oracle | OpenAPI schema = 独立于实现的预期来源（oracle 语义干净，非源码推导循环断言）；契约违背≠bug，先进归因三分类（env/case/product 语义沿用） |
| 评估 | 端点覆盖率、契约违背检出数、顺序场景通过率；数字全由确定性代码算 |

### 3.3 L3 系统层（半自动）与 L4 验收层（辅助）

- **L3**：需求 → LLM 生成业务流场景（API 调用序列，**不做浏览器 UI**）→ 关键路径冒烟执行 → 场景通过率。白盒辅助 = 场景造数参考 L1/L2 覆盖缺口。
- **L4**：验收条件（来自需求 plan 拆解）→ Given/When/Then 场景清单 → 人工确认界面（复用 L1 确认门交互）→ 确认后沉淀为 L3 场景的验收断言与回归基线。不自动执行。

### 3.4 数据模型扩展（18 表 → 加层级维度 + 新表草案）

| 改动 | 内容 |
|---|---|
| 级别维度 | test_tasks 加 level 计划（或新 test_levels 表：任务×级别×策略×状态） |
| 四级 RTM 链 | rtm_maps 保留条件↔用例映射；新增跨级追溯链：acceptance_scenario → system_scenario → integration_case → unit_case → code_location（trace_chain） |
| 新表草案 | interface_endpoints（端点清单）、call_edges（调用边）、scenario_cases（L3/L4 场景，含 G/W/T 结构）——DDL 落地时定稿 |
| 指标契约 | collect_metrics 按级出指标包：L1=coverage/kill（已有）；L2=端点覆盖/契约违背检出；L3=场景通过率；L4=确认率 |
| 台账 | llm_calls 的 phase 加级别前缀（如 `L2.gen_tests`），成本-质量曲线按级画；evaluation_rounds 按任务-级别联合键 |

### 3.5 沙箱扩展

- L1 不动（单容器+快照+R-Loop 常驻）。
- L2 双容器：服务容器（py-service 镜像变体，入镜像注册表）+ 测试容器；`docker network` 互通、健康检查等待、任务级清理（沿用孤儿容器清扫经验）。
- 降级路径：v0 先"单容器内起服务+localhost 端口"跑通全链路，网络模型后置（§9 风险表）。

## 5. 创新点（论文切口重构）

1. **层级×双轨二维组合框架 + 跨级评价矩阵**：每级算"黑盒正确度（需求/契约缺陷检出）×白盒完备度（覆盖/端点覆盖）"两个确定性指标，4×2 评分矩阵替代单一覆盖率叙事；全由 SQL 算、LLM 只叙述（口径不变）。
2. **四级 RTM 跨级缺陷溯源**：注入缺陷后，L3/L2 失败可沿追溯链定位到 L1 用例与代码行——"端到端失败定位到代码行"是工业界痛点，且 rtm_maps 表结构可直接扩展（原被单元口径砍掉的切口②，复活且有基础设施）。
3. **层间+轨间双维自适应调度**：确定性信号驱动资源分配——L1 覆盖饱和但 L2 契约违背多 → 预算切 L2；某级黑盒失败集中 → 切白盒定位。v1 做规则版（确定性阈值），LLM 参与版列消融对照（符合"固定图骨架"口径）。
