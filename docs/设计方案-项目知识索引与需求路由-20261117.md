# 设计方案：项目知识索引 + 需求路由器（2026-11-17，交执行人）

> 回答用户之问：「我说测某板块 LLM 能找到位置吗？测接口能全量找到吗？能不能全库
> 扫描打标签一劳永逸，未知的再细找？」
> **现状核对结论：零件已有、系统未组装**——模块切分✓（只画像不路由）、接口解析✓
> （只在 L2 用）、需求→板块路由✗（LLM 拿的是预算截断的全库文件，说"测用户模块"
> 时 user 模块可能根本没进提示词）、持久索引✗（每任务重扫）。
> 本方案=把零件组装成"扫描一次打标签 → 需求词命中秒定位 → 未命中回退全库细找"。

## 一、总体架构（三层）

```
[analyze 节点] 首次/指纹变化时 → build_index()（零 LLM，确定性）
    产出 data/index/project_<pid>.json：{modules[], symbols[], endpoints[]}
[plan 节点前] match_requirement(index, 需求文本)
    ├─ 命中模块名 → scope_paths=[该模块] → 源码收集只收该模块（秒定位）
    ├─ 命中"接口/API" → endpoint_registry 全量注入+总数对账（接口一个不漏）
    └─ 未命中 → 现行全库收集 + [index] 未命中留痕（细细找）
[gen_tests] 提示词带 scope/registry → 用例对准板块或逐端点
```

## 三、明确不做（边界）

- 不让 LLM 定模块边界（沿 module_profile 纪律：切分确定性）；
- 不做跨项目语义检索/向量库（别名表 25 词够毕设口径，扩词=改一张表）；
- 索引不做增量 diff（指纹变了整重建，典型项目 <1s）。

## 五、主备双层机制定稿（2026-11-18，用户拍板：主方法不变，借鉴机制作辅助/急救层）

主方法（索引+别名路由七步）不变——设计目标是简单、可审计、失败可回退，不追求一次打准。
借鉴业界三种机制作为辅助/急救层，全部踩在已有设施上：

| 级 | 触发条件 | 动作 | 借鉴来源 | 依赖的已有设施 |
|---|---|---|---|---|
| L1 依赖闭包扩展（辅助） | 路由命中模块后自动加依赖/被依赖 1-2 跳 | 防漏测被调用函数 | diff-cover 测试选择 | callgraph.py 调用边现成 |
| L2 覆盖率闭环兜底（急救） | 路由格跑完且需求条件在锁定模块零覆盖 | 自动扩圈重跑一次；仍零覆盖→放弃路由回退全库 | CODAMOSA 覆盖率引导 | per_file/coverage_line 台账现成 |
| L3 失败语料自学习（长期） | multi60/Wave 失败聚类 top 簇 | 自动反哺别名表（词表从真实失败长出来） | 缺陷聚类自反馈 | build_trapkb_v2.py 现成 |

明确不引入：embedding 语义检索（不可审计，与可审计测试目标冲突，第三代机制仅作论文讨论章对照）。

分层纪律：L1 默认开（确定性零风险）；L2 每路由格自动校验（跑完即查）；L3 人工审簇后进表。
三层全落盘留痕（扩展依据/校验结果/词表变更），审计链与主方法同规格。
主方法失败预注册：需求条件在锁定模块零覆盖且扩圈后仍零覆盖→放弃路由回退全库（急救失败的诚实出口）。

对七步改动清单的影响：第 1 步 build_index 增 callgraph 邻接输出（L1 数据源）；第 4 步
scope_paths 自动带闭包（L1 默认开）；新增 L2 校验钩子约 40 行（evaluate 后置检查）；其余五步不变。
