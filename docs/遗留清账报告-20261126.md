### #7 1968 ts-jest 崩溃——复现→定性→修复（8209b84）

- **复现**（零 API）：`mta-test:node20-jest` 容器挂 task_1968 工作区跑裸 jest → `Jest: 'ts-node' is required for the TypeScript configuration files` @ `jest-config/build/index.js:147` ——**与 11-18 账本崩点逐字一致**（workspace 保留完好，node_modules 缺失）。
- **定性**：`jest.config.ts`（Nx 异步工厂 `getJestProjectsAsync()`）在容器里加载不了——全局 jest 无 ts-node，**任何 .ts 配置都读不了**；项目自带 ts-node 也救不了（Nx 工厂需 nx 上下文）。落入 `_js_needs_inline` 第三档"有配置不限定→走项目配置"=零行为变化档的机制缺口。

- 诚实边界：本修复不解决 pnpm workspace 依赖安装（NM=missing 是另一已知边界）；内联 testMatch 只认 `*.test.*`（平台生成物命名，项目自带 `*.spec.ts` 基线不进首轮——既有口径）。

### F8 答辩卡 6 条（why 卡草稿）

1. **为什么两阶段**（确认→执行停等）：需求确认错一次=整批白跑；停等点把"人错在先"变成"人纠在先"。
2. **为什么执行队列单 worker**：SQLite 写锁+容器名约定下，串行是正确性优先的 deliberately choice；并发实验（C）证明 5 路伸缩平坦后才在驱动器侧放开。
3. **为什么 recipe 白名单禁管道**：环境自适应命令是注入面；白名单+逐字段 evidence 让"自动改环境"可审计。
4. **为什么代审剥断言**：AI 代审若能改断言=oracle 自证；只许 approve/delete/regenerate/insert，断言预期只能人改。
5. **为什么三源 C 先行**：RTM/场景/契约三源里契约最客观（spec 机读），先契约后场景让人工介入点落在歧义最大的层。
6. **为什么归因三闸默认关**：闸的判定会改写 failure_kind（影响读数口径）；先以关闭态产主读数，闸开态作为对照批（任务四 P1b）——避免"治理机制污染基线数据"。

### F9 讨论章三故事素材段（合成大故事：瓶颈在 oracle 侧）

- **故事一（源码视野>需求写法）**：三角色×新项目（E9 A4）跨角色读数差异远小于预期——给不给源码、怎么写需求，对 LLM 测试生成的边际贡献都小于"oracle 在哪"。素材：A4 臂 120 格分布（混档注明）。
- **故事二（虚高的直接测量）**：E7 命中率 0.467 vs 表面 0.6 的差值=检出国审虚高的直接测量——不校正口径，方法对比全是噪声。素材：E7 n=6 均值 0.43±0.08 与 0.6 的差值链。
- **故事三（断言驯化系统性）**：corpus-002 全格 0.00（9 格复现）——LLM 生成的断言系统性迁就当前行为；369 家族+Wave2 D 臂连缺陷带都摸不到是同源现象。
