## 一、五族根因定性（13 格熔断逐格归因）

### 族 1：嵌套项目根（10 格：java×7 + php×2 + ts×4 中 1261-1263/1291-1293）
**同族根因：工作区根没有构建清单，真正的项目根在一层子目录里**——下游 install/run/
collect/预热全部以 /work 根跑命令。

| 语言 | 格 | 清单位置 | 死因链 |
|---|---|---|---|
| java petclinic×3 | 1272-1277（+1254-1256 同构） | `spring-petclinic-*-main/pom.xml` | mvn 在根跑 → MissingProjectException → collect 整案废案 → 0 收集 → repair_env rebuild（修不了布局）→ 三轮熔断 |
| php demo-main/laravel | 1286/1287 | `demo-main/composer.json` 等 | probe_deps_manifest 只看根 → None → "未发现依赖清单，跳过安装" → vendor 缺失 → phpunit 前置闸诚实拦停（卡 2-1115 修复的报错正常工作）→ 0 收集熔断 |
| ts nestjs 族 | 1261-1263/1291-1293 | `nestjs-rest-sample-master/package.json` 等 | 误判 ts_loose（有 .ts 源无清单）→ 只补 ts-jest 工具链不装项目依赖 → TS2307 Cannot find module '@nestjs/common' → collect 整案废案熔断 |

**修复（commit 6ef599d）**：clone 落位后 `nested_root.lift_nested_project_root` 把唯一含
清单的一层子目录**整体上提到工作区根**——6 处命令拼 cd 的方案被否（漏一处即复发），
上提后下游全部零改动；歧义布局（≥2 子目录含清单，如 gson 无根 pom 形态）不猜不上提；
同名冲突逐项跳过留痕；SKIP_DIRS（node_modules 等）不计清单宿主。单测 9 例。

### 族 2：缓存预热谎报（java×7 连带层）
`warm_build_cache` 旧版 `| tail -3` 管道让 sh 退出码变成 tail 的 0——mvn
MissingProjectException 被吞成「预热完成」落进留痕消息（1272-1278 全部谎报）。
**修复（同 commit）**：去管道、宿主侧截尾、失败消息带输出尾部（MissingProjectException
从此可见）。顺带：修复后预热失败本身还会成为嵌套根问题的**早期信号**。

### 族 3：LLM 输出截断/附录（gson 1278 + python-schema 1297 首轮）
llm_parse_fail 留档三份实证（1278）+ 新鲜留档两份（1297，跑批进行中产生）：
- 形态①（005545/005738）：JSON 本体完整但尾部带 ```java 辅助类附录 / 二次 ```json 块
  ——主路径贪婪 `\{.*\}` 抓到附录里的 `}` 报 Extra data 整批判死；
- 形态②（005906）：gen 构造不传 max_tokens → DeepSeek 默认 ≈4K → cases 数组 25-30KB
  处硬截断（冗长 Java 静态夹具类单轮可达 25KB+）。

**修复（commit ad09793）**：`_salvage_json_output` 两级降级（仅标准路径全败后调用）——
①raw_decode 解首个完整对象（附录天然排除）②从尾向头找对象边界截尾+闭合（以能否解析
做安全验证，切进字符串字面量必失败天然防误切）；诚实纪律=只提取真实输出的完整条目。
**实证验收：三份真实留档救回 27/25/47 条真用例，1297 新鲜留档救回 5+7 条。**
源头上 `config.LLM_GEN_MAX_TOKENS=8192` 显式传满（截断频率下降）。单测 5 例。

### 族 4：TS lib 落后连坐（ts-ky 1295）+ tsc 闸正确拦截（js-uuid 1285）
- **1295（ky 仓，已修 71196d2）**：根目录有自家 tsconfig，但 tsc 闸带文件参数时按 TS
  语义忽略项目 tsconfig → 闸的旧 `--target es2020` 默认 lib 对项目源码里的
  `Object.hasOwn`（ES2022）恒报 TS2550 → 生成物被 SUT 源码连坐。修=闸升 es2022+显式
  lib，拦截力不变。
- **1285（uuid 仓，tsc 闸正确拦截=诚实边界非故障，并行取证 d7b306b 确认）**：生成
  代码 TS2554/TS2578（Unused '@ts-expect-error'）——生成物自带类型错用例被闸如实
  整案拦截；另有项目自带测试 13 败真执行（0过/13败）。**无需修**（闸工作=设计行为）；
  es2022 lib 升级后重跑观察。
- 拍板点（未修项）：是否为 GitHub 库类项目加「只用项目 tsconfig lib 允许的 API」
  提示词纪律（demo 类项目 tsconfig 现代不受影响）。

### 族 5：宿主 Docker 不稳（python-thealgorithms 1296 + 散发 409）
409 Client Error/NotFound——容器运行中死亡，exec_in 已硬化为结构化 env 错误（11-15
修复正常工作）。**非平台代码**，宿主 Docker Desktop 资源/版本问题（1138 族同款）。
重跑即可恢复；反复出现则需宿主侧排查。

## 二、口径澄清（对账 related）

- **cell done ≠ task done**：390 done 格 → 库内 done 35/failed 355（证人 stop、覆盖率
  未达、budget 停在任务口径都是合法 failed）——已进 aggregate_e9 常驻对账节（b3ee17e）。
- **php84 版本自选已验证生效**：1286/1287 换镜像消息在（"composer 要求 PHP≥8.4——执行
  镜像换用 mta-test:php84"）；死因是嵌套根非版本。
- **gen-0 轮的 repair 分类缺口（存疑待拍板）**：generate 0 条时 evaluate 只有 0/0/0 →
  归 env → rebuild 容器——但 LLM 输出问题 rebuild 修不了。该轮应走 repair_gen
  （重生成）。涉及全部 0 收集熔断格的修复效率（rebuild 白烧 2 轮）。拍板点：改分类
  会影响与历史格的可比性（multi60 前半用旧口径跑完）。
