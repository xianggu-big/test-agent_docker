# 本地 LLM 上下文容量研究与方案（2026-11-09）

> 触发：用户决择单第 5 项——"上下文和是否能承担大量上下文，好好查查并研究，想如何做（流程写具体清楚）"。
> 定位：研究文档 + 具体流程；实现部分独立成任务卡-H。本文所有数字要么实测、要么给出处。

## 1. 实测现状（本机 + 本项目数据）

### 1.1 硬件与模型边界（实测）

| 项 | 实测值 | 含义 |
|---|---|---|
| GPU | RTX 3050 Ti Laptop，4GB 显存 | 权重与 KV 缓存共享这 4GB |
| 模型 | qwen3:4b-instruct，Q4_K_M，**原生上下文 262,144**（ollama show 实测） | 模型本身不是瓶颈——Ollama 的 num_ctx 配置和 KV 显存才是 |
| 权重占用 | ~2.5GB | 剩 ~1.4GB 给 KV 缓存 |

KV 缓存每 token 占用（qwen3-4b：36 层 × 8 KV 头 × 128 维，f16）≈ **144 KB/token**：

| num_ctx | f16 KV | q8_0 KV | q4_0 KV | 4GB 卡可行性 |
|---|---|---|---|---|
| 8k | 1.15GB | 0.58GB | 0.29GB | ✅ 全 GPU（当前状态，~16 tok/s） |
| 16k | 2.3GB | 1.15GB | 0.58GB | ❌f16 溢出 CPU（实测掉速 5 倍）；✅q8_0 勉强；✅q4_0 舒适 |
| 32k | 4.6GB | 2.3GB | 1.15GB | 全部溢出或吃满显存，速度不可接受 |

**铁律（此前实测）**：KV 一旦溢出到 CPU，生成速度从 ~16 tok/s 掉到 ~3 tok/s。

### 1.2 本项目真实提示词分布（llm_calls 2816 条实测）

| 区间 | 数量 | 占比 |
|---|---|---|
| ≤8k | 2644 | 94% |
| >8k | 172 | 6% |
| >16k | 6 | 0.2% |
| 最大 | **40,634**（gen_tests/gen_feedback 大源码任务） | |

**结论：尾部极小但真实存在**。96%+ 的调用 8k 就够；6% 落在 8k~40k。

## 2. 问题定义

本地备胎/本地主线在两类场景会败给上下文：
1. **静默截断**：Ollama 按 num_ctx 截断提示词（实测 truncated=1），模型收到半截提示 → 输出废案，且**无人知道是截断**（当时只看到"输出不可解析"）；
2. **速度崩塌**：为塞长上下文调大 num_ctx → KV 溢出 CPU → 5 倍掉速，任务"能跑但像死机"。

## 3. 三层解法（按成本递增）

### L1 零代码：显存换上下文（一行环境变量）

Ollama 原生支持（`ollama serve --help` 实测存在）：

```
OLLAMA_FLASH_ATTENTION=1          # FA 是 KV 量化的前置
OLLAMA_KV_CACHE_TYPE=q8_0         # KV 减半，质量损失极小；q4_0 再减半（质量损失可感，不推荐首选）
```

效果：16k ctx 在 q8_0 下塞回 GPU。**预期覆盖 99.8% 的历史调用形态**。验收=重跑 probe_local_llm.py 对比 8k/16k 的速度与质量（速度损失应 <10%）。

### L2 确定性预算管理器（任务卡-H 主体）

原则：**截断必须变成显式告警，不能静默**。llm_calls 表已记 prompt_tokens——对账是免费的。

1. **截断对账闸**：每次本地模型调用后，若 `prompt_tokens ≥ num_ctx × 0.95` → 在台账与消息中打 `context_truncated` 标记（确定性代码，零 LLM）；
2. **提示词预算表**：按 profile 能力声明 `ctx_budget`（local=16k，云端=不限），`build_user_prompt` 按预算**降采样源码**（现有 MAX_SOURCE_CHARS 机制的参数化升级：按 token 而非字符算，排序=复杂度热点+入口文件优先——radon 已有）；
3. **段落裁剪顺序**（预算不足时按序砍）：方法骨架示例段 → 覆盖缺口明细 → 条件清单尾部 → 源码尾部。每段保留"已裁剪 N 字"的显式声明进提示词（模型知道上下文不完整，比静默半截好）。

### L3 分治生成（结构性解法，依赖任务卡-E 模块画像）

40k 的尾部提示词 = 大源码仓 + 全量五方法骨架。分治后每个提示词只装**一个模块**的源码 + 该模块的条件——天然回到 3k~8k 区间。模块切分与画像（任务卡-E）是它的前置。**这也是"上下文问题"与"模块级测试"两条线在架构上汇合的点**。

### 不推荐的路（写明原因）

- 直接 num_ctx=32k+：KV 全溢出 CPU，实测速度不可用；
- 换 14B 长上下文模型：4GB 显存放不下权重本身；
- 提示词压缩算法（LLMLingua 等）：引入新依赖与质量风险，收益不如 L2/L3 直接。

## 4. 质量红线（诚实边界，进论文）

1. 长上下文下 4B 模型的有效理解力会衰减（lost-in-the-middle）：塞得下 ≠ 用得好——验收必须带"长上下文 vs 分治小上下文"的检出质量对照；
2. 本地模型定位仍是**演示兜底**，不是数据生产引擎（实验可比性红线不变）；
3. 云端模型（DeepSeek 128k）无此约束——上下文问题是**本地档专属**，论文叙事时别把它写成全系统缺陷。

## 5. 实施流程（具体步骤，任务卡-H 按此执行）

```
步骤1（30min）：设置 FA+KV q8_0 环境变量重启 serve → probe_local_llm 复跑
         → 记录 8k/16k 两档的速度与输出质量 → 选定 local profile 的 ctx=16k（预期）
步骤2（半天）：截断对账闸——make_chat 本地路径加 prompt_tokens 对账 + context_truncated 打标（+单测）
步骤3（半天）：llm_profile 增 ctx_budget 字段；build_user_prompt 支持预算降采样
         （源码按 radon 热点+入口排序，token 估算=chars/2.5 起步，实测校准）（+单测）
步骤4（半天）：段落裁剪顺序实现 + "已裁剪"显式声明（+单测）
步骤5（1h）：真机——构造一个 >16k 提示词的大源码任务，验证对账闸告警与降采样生效
步骤6：真机数据回填本文 §1.2 表格与 AGENTS.md；论文素材=§4 诚实边界 + L1/L2/L3 分层叙事
```

## 6. 与其他任务卡的关系

- 任务卡-E（模块画像）→ L3 分治的前置；
- 任务卡-B（每节点路由）→ 路由表里每个 profile 都要带 ctx_budget 字段（同一次 schema 演进做完）；
- llm_calls 台账 → 截断对账的数据源，无需新表。
