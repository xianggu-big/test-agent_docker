## 0. 一屏结论

1. 学院进度文档质量高：逐条核实的 12 项论断**无一误报**。
2. 但它的 P2 前提"优先复用已有 24 格 Agent Loop 实验回算指标"有一半走不通——实验账本不在生产库，而在系统临时目录的 49 个临时库里；且模型决策原文从未落库。

## 2. 文档没发现的 5 件事

- **设计原则**
  1. **账本是旁路**：只多写两张表，不改提示词、不改图、不改任何现有输出。
  2. **防双轨**：`agent_steps` 只存"决策与链接"，token/耗时/执行结果仍以 `llm_calls`、`skill_invocations` 为真源，用外键指过去。
  3. **指标可重算**：四项指标全部由纯函数从库里算出，不依赖模型自报。
  4. **历史不伪造**：没有 run_id 的历史数据只出"近似值"并打 `approx` 标。
  5. **终态快照**：运行结束时把本轮的轮次轨迹/报告关键数字冻结进 `summary_json`——因为重跑会 delete-first 清掉任务级表，不冻结的话旧运行无法回放。

## 5. 指标契约草案（T1 把它变成经对码确认的正式文档）

### 5.0 样本单位

- **run**：一次图执行入口（`run_task` / `run_task_prep` / `run_task_exec` / auto 的 D1 会话）。与一条 `agent_sessions` 行 1:1。
- **attempt（目标尝试）**：用户的一个目标从提出到出结果。`attempt_no` 规则：
  - kind ∈ {single, prep, d1_review}：开启新尝试 = 该任务最大 attempt_no + 1；
  - kind = exec：归入该任务最新的尝试；
  - 反馈轮（`run_feedback_round`）不是 run，它是评审阶段的多轮对话，证据在 `agent_messages`。
- 报告时以 **attempt** 为主单位；run 级数字作附表。

### 5.1 任务完成率

核心认识：**本系统 `status='failed'` 不等于任务失败**——检出产品缺陷、API 黑盒诚实出口都是 failed。完成与否按 failure_kind 与出口类别判，不按 status。

| outcome | 判定（按顺序，先中先得） |
|---|---|
| `not_completed_user` | 用户取消 / 管理员强制停止 |
| `not_completed_env` | 零有效执行（本运行 `test_case_results` 无 passed/failed 行）且原因为环境类 |
| `not_completed_agent` | 零有效执行且非环境原因（出题 0 条、不可解析、脚手架坏、预算耗尽）；或无报告行（图异常） |
| `completed` | 有有效执行 + 报告落库 + 终态属正常出口（pass / 检出产品缺陷） |
| `completed_with_limitation` | 有有效执行 + 报告落库 + 终态属诚实出口（黑盒出口、静态草稿、覆盖目标未达但已如实上报等） |

"有效执行"= 至少 1 条用例结果为 passed/failed（防假绿铁律：用例数 > 0 且断言真执行）。出口集合的成员由 T1 从 `nodes.py` evaluate 的全部 stop 分支枚举得到，每个 stop_reason 必须落进且只落进一类。

```
分母 D = completed + completed_with_limitation + not_completed_agent + not_completed_env
完成率(严格)     = completed / D
完成率(含降级)   = (completed + completed_with_limitation) / D
有效完成率(排环境) = completed / (D − not_completed_env)
环境失败率       = not_completed_env / D
```

四个数并报，防止"排除环境失败抬数字"的质疑。`not_completed_user` 只报计数。

**工作流完成率**（另一件事）= 图执行走到终态节点、无异常上抛的运行占比。"流程跑完"不等于"目标达成"，两个名字不许混用。

### 5.2 工具调用成功率

- 统计对象：**Agent 决策循环内发起的能力调用**。图节点里固定调用的 gen_tests / run_tests 不算——那是工作流，不是 Agent 决策。
- 每次发起的结局：`ok` / `failed` / `timeout` / `denied_policy`（策略闸拒）/ `denied_registry`（注册表闸拒：停用、schema、确认门）/ `parse_error` / `not_executed`（执行前被预算或重复闸停）。

```
调用成功率(主)   = ok / 全部发起          ← 分母含 failed / timeout / denied
执行成功率(辅)   = ok / (ok + failed + timeout)
拒绝率、超时率   = 对应计数 / 全部发起
```

- 汇总：按 run 等权的宏平均 + 池化全部调用的微平均，两者并报；零调用的 run 不进分母，但要报"零调用 run 数"。
- **与现有指标分名**：`evaluate.py:126` 的 `tool_success_rate` 保留，改名口径为"技能调用成功率（任务级，含工作流技能）"；新指标叫"Agent 工具调用成功率"。

### 5.3 幻觉率

只统计 **Agent 自由产出的断言**，平台确定性生成的数据不算。

| 类型 | 内容 | 核对方法 |
|---|---|---|
| C1 引用断言 | `diagnosis.evidence_refs` 的 step 序号、引用的文件路径与符号名 | 机器核对：序号 ∈ 本次循环证据列表；路径 ∈ 工作区；符号 ∈ 索引 |
| C2 工具断言 | `capability` id、`args` 键与类型 | 机器核对：∈ 菜单、符合 schema（即策略闸的存在闸与 schema 闸拒绝） |
| C3 事实断言 | finish 的 `summary`、`strategy.priorities[].why`、`diagnosis.reason` 里关于代码行为/需求/环境/失败原因的陈述 | 复核标注：supported / contradicted / unverifiable |

不计：`evidence_plan`、`fallback`——那是计划，不是断言。

```
可核对幻觉率(确定性) = (C1 无效引用 + C2 无效调用) / (C1 引用总数 + C2 调用总数)
事实断言幻觉率(人工) = contradicted 的 C3 / 已标注的 C3        （unverifiable 单列，不进分子）
```

- 复核流程：执行者预标（每条带证据指针）→ 用户抽检 ≥20% → 分歧仲裁 → 标注表定稿。未经用户确认的只能叫"预标值"。
- 与 5.2 的关系：同一次"编造能力"既是调用被拒（5.2）又是工具幻觉（C2）。报告时给出"denied 中因编造所致的比例"。

### 5.4 响应时间

库里所有时间戳都是 `datetime('now')`：**秒级、UTC**。

```
T1 用户确认     test_tasks.confirmed_at
T2 入队         exec_queue.enqueued_at
T3 开跑         exec_queue.started_at
T4 图开始       agent_sessions.started_at
T5 图结束       agent_sessions.ended_at
```

```
排队耗时 = T3 − T2
执行耗时 = T5 − T4
Agent 响应时间(主指标) = attempt 内全部运行的 (排队 + 执行) 之和     ← 人工审查等待不计
含人工等待的墙钟时长     = 最后一个 T5 − T1                           （参考值，单列）
```

- 汇总：按项目/语言分组，报 n、mean±std、P50、P95。
- 缺时间戳的样本不进该指标统计，**缺失率如实报告**（当前生产库 203/2301 会话无 ended_at）。
- 新数据用 epoch 毫秒（`agent_runs.started_ms/ended_ms`、`agent_steps.decision_ms/exec_ms`），历史数据保持秒级并标注。

### 5.5 配置快照

每个 run 记一行 `config_json`：各 phase 的模型、`prompt_version`、`agent_loop_enabled`、相关 `MTA_*` 旗标、镜像、代码版本（`git rev-parse --short HEAD`）。没有这个，不同批次的指标不可比。

## 6. 运行账本设计

### 6.1 DDL 草案（追加到 `docs/layer5-data-schema.sql`，37 → 39 表）

```sql
-- 38) 智能体运行账本：一次图执行一行，与 agent_sessions 1:1
CREATE TABLE IF NOT EXISTS agent_runs (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  task_id        INTEGER NOT NULL REFERENCES test_tasks(id),
  session_id     INTEGER REFERENCES agent_sessions(id),
  attempt_no     INTEGER NOT NULL DEFAULT 1,
  kind           TEXT NOT NULL CHECK (kind IN ('single','prep','exec','d1_review')),
  queue_id       INTEGER REFERENCES exec_queue(id),
  goal_text      TEXT,
  started_ms     INTEGER,
  ended_ms       INTEGER,
  status         TEXT NOT NULL DEFAULT 'running'
                 CHECK (status IN ('running','done','failed','cancelled','orphan')),
  stop_reason    TEXT,
  outcome        TEXT,          -- 5.1 的五类，由指标层回填
  prompt_version TEXT,
  config_json    TEXT,
  summary_json   TEXT,          -- 终态快照：轮次轨迹/报告关键数字/循环汇总
  metrics_json   TEXT,          -- 计算缓存；真源永远是重算函数
  created_at     TEXT NOT NULL DEFAULT (datetime('now'))
);
CREATE INDEX IF NOT EXISTS idx_agent_runs_task ON agent_runs(task_id, attempt_no);

-- 39) 智能体步骤账本：决策循环逐步一行，只存决策与链接
CREATE TABLE IF NOT EXISTS agent_steps (
  id             INTEGER PRIMARY KEY AUTOINCREMENT,
  run_id         INTEGER NOT NULL REFERENCES agent_runs(id),
  mode           TEXT NOT NULL,            -- strategy / diagnose
  loop_no        INTEGER NOT NULL DEFAULT 1,
  step_no        INTEGER NOT NULL,
```

- **放量闸**：循环点②已收敛 + 当前是低价窗 + 冒烟格的账本四表齐全。规模未另行指定时按 B 案。

## 13. 常驻循环与预算（v2 新增，2026-11-24 深夜）

依据：用户令"可以调用 DeepSeek 去做任务；需要它一直工作，然后复检，再把检查出来的修复，然后重复"。行为规则以总入口为准，这里说明设计理由。

### 13.1 为什么在三个"循环点"循环，而不是每张卡后面都循环

真机抽验要花钱、要起容器。每张卡后面都跑真机，钱花在半成品上。所以只在三个节点进入循环：

| 循环点 | 位置 | 为什么在这里 |
|---|---|---|
| ① | T0–T4 之后 | 账本、采集、计算刚接完，最需要真机确认"步骤行能 JOIN 回原表" |
| ② | T5–T9 之后 | 页面、演示脚本、代表 Skill 都齐了；它同时是测量批的放量闸——仪器没校准之前不放量 |
| ③ | T10 之后 | 拿真实批量的数据反向检查仪器：行数对不对得上、指标能不能重算、页面和库是否一致 |

### 13.2 一轮循环的七步

复检 → 登记 → 三问分诊 → 修复 → 复验 → 回归 → 记账。要点：

- **复检要有本轮证据**。上一轮的结论不算数，验收条目要重新执行，不是重读。
- **三问准入**（沿用 11-15 闲时找 bug 循环的先例）：能证实吗 / 在范围内吗 / 触及硬边界吗。三问全过才修。
- **修了没复验 = 没修**。修复必须重跑受影响的维度。
- **换视角**。自检的盲区是"按自己的实现思路去检查自己的实现"。每轮至少两条：只看产物不看实现；换一条独立路径算同一个数；派没看过实现的审查者；可选调 DeepSeek 当独立审查员（它的意见也要先复现才算数）。

### 13.3 收敛、熔断与停手

- 收敛：八个维度连续两轮零新发现，且本段验收条目都有本轮证据，且台账没有打开的问题。
- 熔断：同一问题 3 轮未解决 → 登记卡点，不许试第 4 次，继续做不依赖它的工作；只有阻塞主线才整体停手。同一循环点超过 8 轮不收敛 → 卡点报告。
- 这两条是应变协议 §4 在循环模式下的落地：既不许无限循环，也不因为一个局部问题把整条主线停掉。

### 13.4 预算规则

放开调用不等于放开预算。钱仍是硬边界，所以给了四层约束：

| 层 | 规则 |
|---|---|
| 总量 | 总停车线 = min(¥5, 余额 − ¥1) |
| 分项 | 复检抽验 ¥1.5（每轮 ≤ 2 格、≤ ¥0.15/格）；黄金演示 live ¥0.5（≤ 3 次）；测量批 ¥3（B 案）或 ¥1.5（A 案）；独立审查 ¥0.3（可选） |
| 时段 | 批量只在低价窗；高峰段只做不花钱的工作，单格小验每轮 ≤ 1 格 |
| 顺序 | 先冒烟后放量；钱紧时先保测量批（至少 A 案），其次演示 live，最后才是额外抽验 |

单格 ¥0.15 的依据：2×2 实测 ¥0.0735/格，留一倍余量给 Agent Loop 的额外步数。触线后停掉该项付费动作、继续不花钱的工作，被钱卡住的关键步骤写请示卡。**这些数字是按 11-24 的余额 ≈¥6.3 定的默认值，用户可改。**

### 13.5 执行台账

`docs/学院达标-执行台账.md`：断点 / 花费账 / 问题台账 / 验收证据表 / 未决请示卡。三个作用：会话中断后能续跑（已终态的不重花钱）；上下文被压缩后状态还在（与 `AGENTS.md` 顶部状态行互为备份）；用户随时打开就能看到进行到哪、花了多少。

### 13.6 真机验证的三种形态

| 形态 | 用在哪 | 注意 |
|---|---|---|
| 进程内临时库（参照 `run_2x2.py`） | 日常复检抽验 | 不动生产 server，不污染生产库 |
| 验证 server + 夹具库或临时库（参照 `run_nav_check.py`） | 要看页面的复检 | 另起端口 |
| 生产 server 带旗标重启 | 只用于 T10 | 先确认无在途任务；验完恢复无旗标启动 |

共同前提：`MTA_AGENT_LOOP=1` 与 `MTA_RUN_LEDGER=1` 同时在场（`GET /api/runs` 自检 `ledger_enabled`）；放格前确认没有同名容器。
