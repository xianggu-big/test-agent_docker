## 1. webapp-testing（Playwright 界面测试）

**装机动机**：L1 前端 E2E 补强。**测试方式**：按技能规程对 L1 做完整登录→导航 E2E。

**执行记录**：
- 按技能「侦察→动作」模式：首跑用泛用选择器 `input[type=text]` 超时失败 → 侦察脚本发现 L1 是单页应用、所有面板元素常驻 DOM（登录框专用 id `#login-user/#login-pass/#login-btn`）→ 改精确 id 后重跑。
- 结果 **4/4 步通过**：登录页渲染 ✓、错误口令被拒（负例）✓、admin/admin123 登录成功 ✓、5 个侧边栏菜单（新建测试/脚本工作台/任务列表/报告/设置）全部可导航且渲染非空 ✓。
- console 仅 1 条 401（登录前会话探测，预期行为）；8 张全页截图留证。

**优点**：
1. 「侦察→动作」规程直接纠正了我的选择器想当然——先 dump DOM 再写动作，这一步在任何 SPA 上都是必需的；
2. 纯 Python sync API、headless 开箱即用，无 node 构建链，与本项目 Python 单栈完全匹配；
3. 自带 console 错误捕获思路，负例（错误口令）与正例同覆盖。

**缺点**：
1. 一次性安装成本高：pip 包 + 118MB 浏览器下载，且本机残留旧版浏览器（chromium-1208）与新版包（要 v1248）不匹配，首跑报错需读懂报错再补装；
2. 对 SPA 的 strict-mode 陷阱（多个同型元素匹配导致 fill 等待超时）没有显式提示，只能靠踩坑+侦察自行解决；
3. 技能定位是"现场写一次性脚本"，要转成可维护的回归套件需自己补工程化（服务启动管理、账号fixture、断言沉淀）。

**结论：有用，正是装机动机的场景。** 建议把 `l1_e2e.py` 工程化为 `scripts/ui_smoke.py`（自检服务是否在跑、双账号用例），作为第四套回归（pytest/smoke/adversarial 之外）纳入阶段收尾清单。

## 2. systematic-debugging（无根因不修复）

**装机动机**：复盘 P1×3 的修复纪律。**测试方式**：对已知 P1「test_conditions 重跑翻倍」走完整四阶段诊断（按范围决策只诊断不修复，修复权留给 P1 修复队列，避免并发会话同文件冲突）。

**执行记录（四阶段）**：
- **Phase 1 根因调查**：证据链 ①全仓唯一写入点 nodes.py:345 裸 INSERT 循环、无任何 DELETE；②DDL 无 UNIQUE 约束；③builder 入口 clone→analyze→plan 无条件重入（重跑必过 plan）。确定性复现：临时库按真实 schema 重放同一段 INSERT 循环两轮 → **第 1 轮 2 行、第 2 轮 4 行，翻倍实锤**（未耗一次 DeepSeek 调用——LLM 只决定 conds 内容，翻倍取决于持久化循环）。
- **Phase 2 模式对比**：同仓 analyze 节点对 modules 表用 `ON CONFLICT DO UPDATE` 幂等 upsert，注释明写"重跑时模块行必须幂等"（nodes.py:148）——正确模式已存在，plan 节点没得到同样处理。
- **Phase 3 假设验证**：根因陈述=「plan 节点写入缺幂等保障 + DDL 无 UNIQUE 兜底 + A4 允许重跑」，已被最小复现证实。
- **Phase 4（未执行，有意跳过）**：修法一行——INSERT 循环前 `DELETE FROM test_conditions WHERE task_id=?`；配套回归测试=复现脚本转 tests/（红→绿）。连带影响：evaluate.py:143 的 map_requirements 读条件表，重复行直接污染 RTM 矩阵。

**优点**：
1. 铁律「无根因不修复」实际拦住的是我自己——代码读一眼就觉得"显然是缺 delete-first"，规程逼着先拿出三条证据+确定性复现，全程零 LLM 调用；
2. Phase 2（找同仓正确模式）是本项目最值的一步：修复方案从"发明"变成"对齐既有惯例"，一致性免费获得；
3. 四阶段对"症状→机制→修法"的映射清晰，产出可直接贴进 P1 修复队列工单。

**缺点**：
1. 对小 bug 流程偏重（本 bug 从 eyeball 到复现完成约 10 分钟，其中规程开销约一半——但换来的确定性复现脚本同时就是回归测试底稿，算回本）；
2. 没有覆盖"只诊断不移交修复"的场景（诊断结论如何交接、复现脚本放哪），本次是自行裁量的；
3. 全英文、支持文件（root-cause-tracing.md 等）本轮未用到。

**结论：有用，P1×3 修复队列动工时的标准作业程序。** 复现脚本已留 `data/reports/skill_test/repro_p1_conditions.py`，修复时红→绿即可。

**优点**：
1. 立竿见影：第一次正式使用就抓到真实漂移（85→87）。若拿过期基线写进论文或下一轮状态更新，错误会继续传染；
2. 门槛函数（识别命令→跑→读全输出→才允许声称）成本极低、无需工具，纯纪律；

**缺点**：
1. 全量复验有真金成本（本轮三项约 40 秒+；E1-E5 实验数字需 DeepSeek 余额+数小时，**本轮未复核，报告如实标注**）；

**结论：有用，且是四个里性价比最高的。** 建议固化为：AGENTS.md 每次更新「当前状态」前，可复核声称必须当日重验；不可复核的明确标"未复核+原因"。

## 4. writing-for-agents（面向 agent 写文档）

**装机动机**：gen_tests/审查闸等 L3 提示词优化方法论。**测试方式**：用技能的杠杆（禁令配对/单一真源/完成标准/前导词/上下文负载）评审 `skills/prompt_library.py` 当前版（含 V6 后）。

**执行记录（三条实发现+两条确认）**：
1. **【实验效度风险】V2 对照组被输出 schema 污染**：`build_user_prompt` 的「输出格式」JSON 示例是无条件拼接的——`include_methods=False`（V2 自由发挥对照组）时，示例仍写死 `"name": "test_xxx_等价类划分"、"method": "等价类划分"`，等于从 schema 侧把方法先验泄漏进对照组。X2 格（无骨架 0.47 最高）的"检出驱动=需求条件显式化"结论方向不受影响（schema 泄漏的是方法标签不是条件），但**V7/语料 v2 复跑前必须把示例改成随 include_methods 切换**。
2. **【单一真源违例】五法名单写了两份**：`METHODS` 列表之外，`build_plan_prompt` 第 54 行硬编码"等价类划分/边界值分析/判定表/语句分支覆盖/错误推测法"字符串——METHODS 一改 plan 提示词就漂移，应从 METHODS 派生。
3. **【完成标准缺口】无总量下限**：全 prompt 只有"每方法≥1 条"（V2 下此约束也不存在），LLM 可合法地只回 2-3 条；建议补一条可查的全局需求（如"cases 总数≥被测公开函数数"）。
4. 【确认优点】禁令配对纪律现状良好：所有"禁止/不要"（输出格式、发明用例、实现返现即断言）均配有正向表述先行，符合技能的 negation 规范；
5. 【确认优点】五法名即前导词——预训练概念免费招募模型先验，且 method 标签落库进 test_cases.method 供论文统计，命名一致性有机制保障。

**优点（技能本身）**：
1. 杠杆可操作性强：三条实发现全部由"单一真源/分支一致性/完成标准"三个具体杠杆机械导出，不是玄学评审；
2. 双负载模型（context load≈每次调用的 token 成本）对 L3 提示词直接适用——`MAX_SOURCE_CHARS=8000` 的取舍本质就是 context load 预算问题。

**缺点**：
1. 抽象密度高（前导词/两负载/信息阶梯），首次阅读需慢读，不适合当 checklist 扫一眼；
2. 以常驻文档（AGENTS.md/skill）为主要靶子，对"每次调用即弃"的 LLM 提示词只有部分杠杆平移可用，需自行取舍；
3. 完全没提"实验冻结中的文档怎么办"——本项目提示词是预注册实验变量，任何优化必须与下一轮实验（V7/语料 v2）绑定提交，这个约束是我自行补充的。

**结论：有用，但产出形态是"编辑清单"而非"立即改"。** 三条编辑建议留档本报告，V7 动工时逐条执行；现在改反而破坏实验可比性。
