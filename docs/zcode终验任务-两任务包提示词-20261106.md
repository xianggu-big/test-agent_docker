# zcode 终验任务：两任务包全量验收提示词（2026-11-06）

> 使用时机：**每日开发任务**（见《zcode闲时开发任务-两任务包提示词-20261106.md》）把执行序 1-9
> 全部标记完成后，另开一轮闲时任务跑本提示词做终验。终验进度同样断点续跑，可跨多天额度。
> 核心原则：**不信任台账与任务包勾选，一切以代码与真机命令输出为准**；发现没做完的 → 返工重做 → 再验，直到做完为止。

## 一、可直接粘贴的主提示词（模型 GLM-5.3，项目目录 D:\test agent_docker）

```text
你是独立终验工程师，对仓库 D:\test agent_docker 的两个任务包做全量终验，验收与返工一肩挑：
A. docs/黑盒能力补齐任务包-20261106.md
B. docs/多语言工具链接入任务包-20261106.md
背景：前序开发任务声称已全部完成。你的职责是证伪这个声称——逐条真机复验，
没做完的重新做完，循环直到全部通过为止。

【第一步：建立真值基线（约 15 分钟）】
1. 读 .autonomous-loop/dev-ledger-20261106.md 与两份任务包的勾选状态——这些只是"声称"，
   禁止当事实。
2. git status 必须干净；git log --oneline -40 浏览全部提交，与两包阶段清单做首次对照。
3. 跑基线：python -m pytest -q 全绿 + python scripts/module_check.py 无失败。
   基线不绿：这是最高优先级缺口，进入返工闭环先修它。
4. 读取/创建终验矩阵：.autonomous-loop/final-check-20261106.md（格式见文末模板），
   每天从矩阵接续，已完成条目不重复验。

【第二步：反作弊静态核查（约 20 分钟）】
对每个"声称完成"的阶段做存在性核查，任何一条缺失即记缺口：
- 黑包阶段1：layer5-data-schema.sql 含 app_logs 表；skills/log_analyze.py 存在且经
  SkillRegistry 注册；runner 有日志分流代码路径；API 端点 GET /api/tasks/{tid}/logs 存在。
- 黑包阶段2：recipe 支持 db_services；db_assert skill 存在；sqlglot 只读闸有测试覆盖。
- 黑包阶段3：Playwright 镜像在 IMAGE_BUILD_CTX；DOM 快照采集代码存在。
- 黑包阶段4：proto 提取在端点提取降级链中；grpcurl 调用封装存在。
- 黑包阶段5：若降级为边界声明 → 文档中确实有该声明；若实施 → mitmproxy/HAR 解析存在。
- 白包阶段1：stack_detect 识别 tsconfig.json；静态闸含 tsc --noEmit；
  覆盖率 source map 回映射有测试或验证证据。
- 白包阶段2：java_adapter 存在（surefire XML→统一文本）；JUnit5 渲染模板存在。
- 白包阶段3：go_adapter 存在（go test -json 解析）；go build 编译闸存在；
  编译失败→重生成 token 成本记录已写进白包任务卡。
- 白包阶段4：php_adapter 存在且复用 JUnit XML 解析；php -l 闸存在。
- 白包阶段5：.NET demo 走 Tier3 的 static_scan 兜底表现确认记录存在（或明显误报已修）。
- 收口物：README 语言支持表已按实况更新；两个检查点产物存在
  （检查点一：TS+Java 全链路证据；检查点二：归因准确率复验结论+数据）。
- 检查黑包阶段2 前置调研：Testcontainers 调研结论已写回任务卡（任务包明文要求）。
同时做反向核查（防"为过测试改断言"）：git log -p 抽查 tests/ 目录，
出现断言弱化/测试删除/跳过标记即记 P0 缺口并恢复原断言。

【第二步附：黑包测试矩阵核查（对照黑包"测试矩阵"一节逐项）】
黑包各阶段【验收】之外还规定了自动化测试清单（单测锁闸门/解析器），逐项核查：
1. 存在性：矩阵列出的每条单测（四语言日志正则、sqlglot 只读闸正负例、selector 真值闸
   负例、proto 解析与虚构 method 负例、HAR 解析等）在 tests/ 有对应测试且随全量通过；
   缺一条记缺口（补测试，不是补实现）。
2. 变异抽查（防"测试存在但锁不住"）：抽 3 个核心闸门（sqlglot 只读闸、selector 真值闸、
   gRPC method 闸）临时改坏实现（本地改动不 commit），确认对应负例测试变红，随即还原；
   改坏不红 = 测试无效，记缺口并要求补强断言。
3. 集成项：app_logs/db_assert 落库幂等测试存在且覆盖重跑场景。

【第三步：真机验收矩阵（核心，逐阶段逐条）】
按执行序（黑1→白1→白2→黑2→黑3→白3→黑4→白4→收尾）打开任务包对应阶段的【验收】条目，
逐条构造真机验证。验收=真实执行出结果，读代码不算验收：
范围说明：白包"可选加强项·新语言迁移性小格验证"明确标注[可选]且不阻塞收口——
它不在本矩阵范围内，不因缺它记缺口、不因缺它阻止终验通过（该验证由用户开实验窗口执行）。
- 需要 demo 项目的（如 TS/Java/Go/PHP 全链路）→ 构造最小 demo（含一个可被测出的埋缺陷）
  放临时目录，走 CLI/脚本真跑全链路。
- 需要故障注入的（如端口占用被日志捕获、越权 SQL 被闸剔除、虚构 method 被剔除、
  虚构 UI 元素被剔除）→ 真实注入并确认被拦截且留痕。
- 每条结论三选一：通过（附命令+输出路径）/ 不通过（附失败证据，进缺口清单）/
  外部阻塞（附原因与所需条件，如 docker 拉镜像失败）。
- 每验完一条立即写终验矩阵，防止额度中断丢进度。

【第四步：缺口返工闭环（"没做完就重做到完"）】
1. 对每个"不通过"条目，按任务包该阶段方案重新实现：先失败测试 → 最小修复/补实现 →
   测试三连（新测试过 + pytest -q 全绿 + module_check 无失败）→ 重跑该验收条目。
2. 循环直到该条通过。单条目返工不设上限，但每轮必须先分析根因再动手，禁止盲改。
3. 唯一允许的例外：确认属外部阻塞（网络/镜像源/需人工决策/权限）→ 矩阵记"阻塞"，
   附解除条件，继续下一个缺口；禁止把能力不足伪装成外部阻塞。
4. 一次只处理一个缺口，完成后 commit（路径范围化），再取下一个。

【硬约束（全程有效）】
不写真实库 data/test_agent.db；不清理 data/workspaces；不杀运行中的服务进程；
不跑真实任务链（run_task/run_task_levels/run_e7_corpus003.py/run_grid.py/
grade_corpus.py/mutation_kill.py）；不改实验数字/论文结论；不删不禁用失败测试；
不顺手重构；语言接入只动六个确定性位置（镜像/探测正则/recipe/渲染模板/adapter/堆栈正则）。
工作树互斥：开工前与返工前探测 E9/E10 实验波次是否在运行（wave.log 尾部时间戳/进程），
在跑则本轮只做只读验收、写操作（返工/commit）挂起到台账，等下一轮。

【终验通过的唯一判定（缺一不可）】
1. 矩阵中全部验收条目=通过（阻塞条目附明确解除条件清单）；
2. python -m pytest -q 全绿 + python scripts/module_check.py 无失败；
3. git status 干净，返工 commit 全部完成；
4. 产出终验报告 docs/终验报告-两任务包-20261106.md：
   ①验收矩阵总表（阶段×条目×结论×证据路径）②反作弊核查结果 ③缺口与返工记录
   ④阻塞清单与解除条件 ⑤诚实边界（确实没做/做不到的，直说）。
在矩阵未全绿前，对话与报告里禁止出现"任务完成/全部搞定"字样，只允许报告：
已验 X 条（通过 Y/缺口 Z/阻塞 W）→ 下一条目是什么。

【额度管理】
每 30 分钟自查：不够走完一个完整"验收或返工"单元时，在条目边界收尾——
更新矩阵、commit、报告进度。禁止开了验一半不记录。

【终验矩阵模板（.autonomous-loop/final-check-20261106.md）】

现在开始：执行【第一步】。
```

## 二、你怎么确认终验真的通过了

1. 看 `.autonomous-loop/final-check-20261106.md` 矩阵：**每条**"通过"都必须有证据路径，
   逐条点开抽查 2-3 条（真机输出文件确实存在、内容对得上）。
2. 亲自复跑：`python -m pytest -q` + `python scripts/module_check.py`（最终防线）。
3. 对照任务包验收栏与终验矩阵交叉核对：任务包勾了但矩阵没验的 = 漏网，打回。
4. `git log -p -- tests/` 抽查有没有断言被改弱（防作弊第二道）。
5. 终验报告第五节"诚实边界"是必读项：真正的收口允许有"阻塞清单"，但**不允许**有
   "做了但没验证"的模糊项。
6. 全部确认后：删掉每日开发任务与终验任务两个 zcode 定时项，台账与矩阵归档。

## 三、节奏建议

- 终验总量约等于把 9 个阶段各走一遍真机验收，预计 3-5 天额度。
- 建议每日开发任务跑完后**不要立即**开终验，先自己花 10 分钟按每日文档第三节的 5 步抽查一遍，
  明显烂尾（如某阶段台账无证据）就先让每日任务补，再开终验——避免终验轮整天在给别人擦屁股。
- 终验发现的缺口若超过 5 个，说明开发轮质量失控：停下终验，回到每日任务模式修复，再回来终验。
