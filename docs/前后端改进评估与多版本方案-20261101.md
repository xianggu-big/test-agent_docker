# 前后端改进评估与多版本方案（2026-11-01 深夜）

> 依据：用户实测反馈史（"难看死了/点了没反应/增补的用例我看不到/跑哪都不知道/概览和 RTM 生成不出来"）+
> 本轮任务卡修复中发现的残留问题 + 真实库快照取证（280 任务 / 35 API 端点 / 六页截图归档
> data/reports/screenshots/audit_current/）。任务卡 A/B/C 已修复的问题不重复列。

## 一、总评

前端：功能已经全（两阶段/代审/判决卡/实时看板都有了），**差的是信息架构与视觉层级**——
六个视图平铺、每屏塞满卡片、状态信息分散在三处，新用户第一眼不知道"我现在该干什么"。
后端：核心链路可靠（435 单测/守卫 136），**差的是规模化管理能力**——无队列、无分页、
项目不去重、失败重跑成本高；这些都是 280 个任务量级下才暴露的。

## 三、前端三版方案（设计稿见会话内三版轮播：V1 指挥台 / V2 流程向导 / V3 清单精修）

| | V1 指挥台 | V2 流程向导 | V3 清单精修 |
|---|---|---|---|
| 一句话 | 三栏控制台：左导航+中央执行实时+右待办流 | 三步向导为主页骨架（填需求→审用例→看报告）+任务时间线 | 保留现有项目分组表格心智，重做视觉/筛选/行内操作 |
| 解决 | F1+F2+F7（一眼看到在跑什么、该审什么） | F1+F4（新用户/答辩演示路径最短） | F2+F5+F7（改动面最小、老习惯不变） |
| 改造成本 | 高（新增主页+重组导航，~4-5 天） | 中（一个主页替换 #new 为默认，~2-3 天） | 低（CSS/局部重渲，~1-2 天） |
| 适合 | 你日常自己用、任务多时管理 | 给导师/答辩演示、给新用户 | 求稳、时间紧 |
| 建议 | **推荐 V2 为主 + V3 的表格精修合并**：主页=向导+时间线（演示与引导最强），任务页用 V3 的筛选/状态/操作分组。V1 的实时执行大卡下沉到详情页（已有）。 |
| 不推荐 | V1 单独全做（信息密度对你一个人好用，但演示时噪声大） | — | 单独 V3 治标不治 F1 |

三版共同底座（无论选哪版都先做，~0.5 天）：状态色四体系一（执行蓝/待审查橙/完成绿/失败红）、
空态统一带下一步指引、判决卡/徽章组件化复用。

## 五、后端三版计划

### 方案一「稳健收敛」（~3-4 天，答辩前做）
1. B2 项目归一：repo_url 规范化键（本地路径取绝对路径+顶层名；远程去 .git 尾缀）+ 老库合并迁移（保留任务行归属，备份先行）——0.5 天
2. B3 分页：/tasks?limit&offset&status、/logs?tail_n（默认尾部 200 行）+ 前端适配——1 天
3. B1 执行队列：单 worker 串行消费 queued 任务（container_jobs 状态机升级为真队列，reject 并发下发为排队而非报错）——1.5 天
4. B5 LLM 退避：llm_usage 加统一 retry 装饰（402 直接友好停等，不再烧轮次）——0.5 天
5. 验收：分页单测/队列并发单测（双任务排队断言）/真实库迁移 dry-run 报告

### 方案二「能力扩展」（方案一 + ~2 周，中期检查后）
1. 任务F：环境自适应 recipe MVP（docs/环境自适应调研与设计.md §6 范围，~5 天）
2. B6：JS 项目接 L2（endpoint_extract/callgraph 对 jest 项目适配）——3 天
3. 逐用例结果接 L2/L3 leg（store_case_results 已留 level 参数）——1 天
4. B4 失败任务"从失败阶段续跑"（阶段产物复用：clone/plan 结果不弃）——2 天
5. B7 clone 预算（复用任务B 快照预算语义）——0.5 天

### 方案三「演示优先」（~1 周，时间不够时的降级）
只做：方案一的 2（分页，列表不卡）+ 前端 V2 向导落地 + demo 一键脚本（demo.py 扩展：造 1 成功 + 1 缺陷 + 1 待审查三个样本任务）+ 论文截图包重拍。
冻结其余一切。风险：并发问题答辩现场若只跑单任务不暴露——可接受。

### 推荐
**方案一先行**（B2/B3 是列表体验的根因，正好配合前端改版）；**前端选 V2+V3 合并**；
方案二等你对任务F 设计点头后启动（环境自适应是"按项目拉环境"的正解）。
