# AI 代审（代理人工确认/审查）设计（2026-10-31 晚，用户提出，待实施）

## 用户诉求（原话要点）
1. 人工确认的阀门**可选地交给 AI 全权代理**——批量大量测试任务时开启；
2. AI 代审必须**实现人工的思考**：为什么添加、为什么删除、为什么要求再生成——
   决策理由要像人写审查意见一样落下来、显示出来；
3. 阀门结构本身不变（fail-closed 保持），变的是"谁来满足这个门"。

## 核心设计：审查员角色的 Agent 化，不是绕过阀门

### 1. 问责链不变
`confirmed_by` 从用户 id 扩为 `agent:reviewer-<session>`——谁/什么满足的门，台账永久可查。
审计链完整：出问题能追溯到"这是 AI 代审的决策，其理由是……"。

### 2. 代审的三个决策点（对应既有阀门）
| 决策点 | 阀门 | AI 代审做什么 |
|---|---|---|
| D1 准入 | 人工确认（confirmed 0→1） | 读需求+项目上下文，写审查意见书（为什么值得测/风险点），带理由确认 |
| D2 用例集审查（核心，两阶段设计的"待审查"停等点） | 阶段一→阶段二放行 | 逐条/整组决策：通过（引用覆盖的条件号）/删除（重复/弱断言/迁就嫌疑）/再生成（缺口→写反馈文本喂增补管线）/插入（主动提出缺失用例并生成） |
| D3 L3/L4 场景确认 | confirm 三选一 | 同模式（v2 可扩展） |

### 3. 决策必须结构化+可解释（用户点名的核心）
新第 23 张表 review_decisions：
`(task_id, decision[approve/reject/regenerate/insert], target, reasoning, evidence, reviewer_role[ai_proxy/human], round, created_at)`
- **reasoning 必须引用证据**（条件编号/断言类型/覆盖缺口）——提示词强制，静态闸校验理由非空
  且引用的 condition_id 真实存在（防 vibes 审查）；
- UI 呈现为"审查意见书"卡片：决策+对象+理由+置信度——AI 的思考过程对人可见可追责；
- **论文金矿**：人工审查 vs AI 代审 vs 无审查 三臂对比实验（决策质量/成本/检出率变化），
  review_decisions 就是现成数据源。

### 4. 角色分离红线（与 V9 同源）
代审提示词 ≠ 生成提示词（同模型角色分离先例）；理想=跨模型（列展望）。
**证人冻结语义对 AI 代审同样生效**：product_defect 证人用例 AI 无权删除（宁可误报不可造假）。

### 5. 三种模式与触发
| 模式 | 行为 | 场景 |
|---|---|---|
| off（默认） | 现行为，等人审 | 单任务/演示 |
| hybrid | AI 先审+决策落库标记"待人工抽检"→人按 20% 抽查（复用 spot_check 思路），**推翻也落库**（对齐信号） | 日常 |
| auto | 全权代理：代审→若决策含 regenerate 自动调 feedback 端点→再审→收敛或达预算（5 轮）→自动放行进阶段二 | 批量大量任务 |

- 批量入口：batch API / 脚本对 N 任务批量开 auto；
- 停车线：token 预算（沿用三角色实验先例）；
- **fail-closed 兜底**：代审 LLM 调用失败/输出不可解析 → 停在待审查等人工，绝不自动放行。

### 6. 与两阶段流程的接口（docs/两阶段人机协作流程设计-20261031.md）
阶段一结束停在"待审查" → ai_reviewer=auto 时钩子自动触发 D2 代审 → 决策落库 →
regenerate 决策自动调 POST /tasks/{tid}/feedback（AI 写的反馈文本，与人工对话框同一端点）→
再审循环 → 放行阶段二。human 模式则等人。**代审只是"待审查"停等点的另一个满足者。**

## 风险与注意
- 代审成本：每任务一次代审调用（方案链+用例集约 8-15k token）——批量 n 任务 ×15k，停车线必须先行
- 决策漂移：同模型自审偏置（MT-Bench 自偏好）→ 角色分离+hybrid 抽检对齐；跨模型列展望
- 与 L3/L4 确认的关系：v1 只做 D1/D2，D3（场景确认）v2 扩展
- 消融格预留：X-D（AI 代审 on/off 对检出与效率的影响）
