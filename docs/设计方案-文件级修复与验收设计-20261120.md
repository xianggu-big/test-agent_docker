## 1. 设计总则

1. **推进顺序 = Qoder 推荐的四包**：A 正确性修复（P0 零 API）→ B 索引与审计加固（P1 零 API）→ C 实验账本修复（P1 零 API）→ D 安全边界（P2，接不可信仓库前必做）。**四包全部零 API**，跑数（A 轨/配对实验）在 C 包账本修好+小样验证后才另行拍板。
2. **每项先红后绿**：先写能复现当前错误的测试（对照 evidence 列），修复后全绿；回归全量跑通 + module_check 守卫 OK 才 commit。
3. **旗标纪律**：凡改执行图/闸行为的新逻辑，默认值必须保持现网行为不变（沿用 DEFENSE_V2_ENABLED 式旗标惯例）——但本包四项（A1-A4）均为**修错误行为**而非新能力，修复后行为即正确行为，不设旗标直接修，用测试锁死两态语义。
4. **诚实出口优先**：所有新分支宁可如实留痕降级（no_data/not_verified/blocked），绝不伪装成功。

## 2. 包 A：正确性修复包（P0，零 API）

### A1 审查失败禁止自动放行

**最小契约**：`_auto_review_loop` 返回结构化结果 `{"outcome": "converged" | "fail_closed", "reason": str}`；两个自动入口**只消费 outcome**，不再用任务状态猜审查结论。

**文件改动**：
- `test_agent/graph/builder.py`
  - `_auto_review_loop`：六个出口分别 return `converged`（仅 :590-594 无增补分支）或 `fail_closed`（:573 停车线/:585 异常/:588 不可解析/:600 增补失败/:606 增补零条/:608 预算耗尽），fail_closed 附 reason；
  - `post_prep_review_hook` :541-546：改为 `result = _auto_review_loop(...); if result["outcome"] == "converged" and 状态仍 ready_for_review: enqueue`；fail_closed 时**不入队**，`_reviewer_msg` 已留痕无需重复；
  - `run_task_auto` :656-660：同样先判 outcome，`fail_closed` → `return {"stage": "D2", "stopped": "fail_closed"}`（现状语义保留），`converged` → `run_task_exec`。
- 状态检查保留为双保险（防并发第三方改状态），但**不再是放行的唯一依据**。

**状态转移**：converged → ready_for_review →（自动入队 exec）→ 执行；fail_closed → ready_for_review 停等人工（终态不变，仅放行决策变）。

**测试矩阵**（`tests/test_auto_review_gate.py`，先红后绿）：
1. 六个 fail-closed 分支 × 2 入口 = 12 例：mock run_review_once/预算触发，断言 `enqueue` **零调用** / `run_task_exec` **零调用**；
2. 收敛分支：断言恰好入队/执行 **一次**；
3. 回放 Qoder 复现场景：日志含"停在待审查交人工"的任务不得出现在 exec_queue。

**验收**：`grep -c "enqueue"` 类断言零执行；正常收敛路径 E2E 不回归（现有 auto 单测全绿）。

### A2 验证任务真正冻结（用例写入口全拦）

**最小契约**：验证任务带 `verify_mode=1` 贯穿 任务行 → TaskState → 执行图路由；执行图对 verify 任务**永不进入 generate**——evaluate 非 pass/stop → 直接 report，verdict 如实标注 `blocked`/`not_verified`（覆盖不足不补题）。

**回应 Qoder 残片边界 1**（"必须保护所有用例写入口，不能只禁止生成节点"）——写入口清单与拦截层：

| 写入口 | 现状触发路径 | 拦截方式 |
|---|---|---|
| generate 节点主生成 | evaluate→generate（builder.py:134）/ review repair_gen→generate（:139） | **图级路由拦截**（见下）——verify 任务的 conditional edge 不指向 generate |
| feedback 增补轮（fbN） | run_feedback_round | verify 任务无 review 交互入口，天然不可达；断言单测锁死 |
| 剪除/重写 | evaluate 后 repair_gen 分支内 | 图级拦截后不可达；单测断言 |
| 生成资产删除 | gen_tests delete-first | 同上 |
| 用例集复制/启用集变更 | create_verify_task 本身 | 创建时一次定型，之后只读 |

**文件改动**：
- `test_agent/store/db.py` + 迁移：`ALTER TABLE test_tasks ADD COLUMN verify_mode INTEGER DEFAULT 0`（SQLite 加列轻量无 CHECK 重建风险；老任务兼容 fallback：requirement 前缀 `[回归验证 of task N]` 判定——**防御性双通道**，防历史 verify 任务漏标）；
- `test_agent/skills/verify_fix.py` create_verify_task：INSERT 列表加 `verify_mode=1`；
- `test_agent/graph/builder.py` build_exec_graph：
  - provision 条件边：verify 任务 done 判定不变；
  - **evaluate 条件边**：`verify_mode=1 且 verdict 非 pass/stop → "report"`（替换现 :132-135 的 repair_env/generate 分流；stop_reason 如实写"验证任务冻结用例，不补题不重跑"）；
  - **review 条件边**：verify 任务 repair_gen → END（不回炉）；
  - TaskState 加 `verify_mode` 键（nodes.py 透传 out，防 366 式跨节点丢弃）。
- `test_agent/skills/verify_fix.py` verify_verdict：新增 `not_verified` 处理——本轮执行被环境/用例问题打断时如实报 `not_verified`，**不得并入 fixed_verified**（审计口径）。
- 审计证据：验证任务执行前后对用例集算 `sha1(内容+enabled 集合)` 落 test_reports（可复核，不代替写入拦截）。

**测试矩阵**（`tests/test_verify_freeze.py`）：
1. verify 任务 + 低覆盖 → generate 调用零次、用例内容/启用集哈希不变；
2. verify 任务 + 收集失败 → 同上，终态含 not_verified/blocked；
3. verify 任务 + 用例错误 → 同上；
4. repair_gen verdict 在 verify 任务上 → 不进 generate；
5. 非 verify 任务 → 现 repair 行为逐字节不变（回归锁）；
6. 历史前缀任务（无 verify_mode 列值）→ fallback 判定生效。

### A4 取消竞态收敛（认领与取消同一事务规则）

**回应 Qoder 残片边界 2**（"取消与队列认领必须在同一套事务规则下判定谁先成功，不能靠事后补状态"）：

**最小契约**：**认领 = 单事务内两个条件更新**——`exec_queue: queued→running` 与 `test_tasks: queued→cloning`（prep/auto 类；exec 类任务在放行后本就非 queued，无此窗口）必须同事务先后成功；任一失败（任务已 cancelled）→ 整体放弃认领，队列行如实标 cancelled。**取消生效点唯一定义**：任务行 `status='queued'` 且队列行 `status='queued'`（两行同事务改 cancelled）；认领成功后的停止请求如实报 `stopped:false`（v1 不支持运行中中断，不谎报）。

**文件改动**：
- `test_agent/store/queue.py` _step :188-201：
  ```python
  # 认领=同一事务两步条件更新（谁先成功谁生效；A4 设计 docs/设计方案-文件级修复与验收设计-20261120.md）
  conn.execute("UPDATE exec_queue SET status='running', started_at=datetime('now')"
               " WHERE id=? AND status='queued'", (row["id"],))
  cur = conn.execute("UPDATE test_tasks SET status='cloning', updated_at=datetime('now')"
                     " WHERE id=? AND status='queued'", (row["task_id"],))
  if cur.rowcount == 0:   # 任务已取消——认领失败，队列行回写 cancelled，跳过执行
      conn.execute("UPDATE exec_queue SET status='cancelled', ... WHERE id=?", (row["id"],))
      conn.commit(); return True
  conn.commit()
  ```
  （exec/auto kind 的任务状态条件更新按各自入口语义适配——exec 类任务非 queued 态，认领时跳过任务行更新、执行入口锁兜底，见下）
- `test_agent/graph/builder.py` run_task_prep :287-290 与 run_task :158-165：乐观锁排除表**加 `'cancelled'`**（双保险：即使未来出现新的认领路径，cancelled 也不得进入执行链）；run_task_exec 同查。
- `test_agent/api/server.py` api_stop :412-422：保持只拦任务 `queued`（认领事务化后该窗口关闭）；**补一条诚实分支**——任务 `queued` 但队列行已 `running`（理论不可达，防御）→ 返回 `stopped:false + reason`，不谎报。

**测试矩阵**（`tests/test_cancel_claim_race.py`）：
1. 认领前 stop → 任务 cancelled + 队列行 cancelled + **执行零次**；
2. 认领后 stop（同步屏障探针：mock 认领完成瞬间插入 stop）→ `stopped:false` 不谎报 + 执行正常完成（认领者胜）；
3. 任务 cancelled 后 worker 认领 → 队列行标 cancelled、`run_task_prep` **零调用**；
4. cancelled 任务直调 run_task_prep/run_task → 乐观锁拒绝（双保险锁死）；
5. 正常认领→执行→终态回写：与现状逐字节一致（回归锁）。
