## 0. 开场（30 秒，可直接念）

> 老师好，我的题目是《基于大模型 Agent 的黑盒白盒测试研究》。
> 一句话概括：以黑盒（依据需求规格设计用例）与白盒（依据代码结构度量）两族测试方法为方法主线，让大模型 Agent 按照测试的四个阶段——分析、设计、执行、评估——自动完成测试全流程闭环，在单元、集成、系统、验收四个测试级别上递进应用（单元与集成深度自动化、系统与验收半自动辅助），用容器技术保证执行环境隔离、可复现、可审计，最后用控制变量实验量化"哪种方法组合最有效"。

## 1. 选题（2 分钟）

**背景三句话**：
1. 软件测试是质量保障的核心环节，但用例设计和执行高度依赖人力，覆盖不足、回归成本高。
2. 大模型已经能从自然语言需求直接生成测试用例，但现有方法有三个已知问题——
   - 断言"跟着实现走"：实证研究（arXiv:2412.14137）表明这类生成器测不出缺陷，反而会把缺陷行为验证成"预期"；
   - 生成物缺乏可信执行环境，过程不可复现、不可审计；
   - 缺乏"哪种 Agent 测试方法更有效"的可量化对比。
3. 国内研究多集中在提示词工程和单点生成，缺一套覆盖"分析—设计—执行—评估"全流程的系统化方案。

**研究目标一句话**：构建一个可控、可审计、可复现的测试 Agent 系统，研究黑盒白盒两族方法在四个测试级别上的组合应用策略，并通过控制变量实验找出最适合 Agent 测试的方法组合。

**为什么以黑盒白盒为主线、四级递进（响应老师"聚焦"意见，主动讲）**：上次开题会老师指出软测大类太宽，本课题据此做了两层收敛——**方法维度**收敛到黑盒、白盒两族：黑盒管"测什么"（等价类/边界值/判定表等依据需求设计），白盒管"测够没有"（覆盖分析/调用链/变异测试依据代码度量），两族组合成闭环；**层级维度**按测试四级递进分配自动化深度：单元与集成两级深度自动化（研究主体），系统与验收两级半自动辅助（业务流场景自动生成执行、验收场景清单辅助人工确认）。类型维度排除压测/安全/界面（需要另一套测试预言，与功能正确性目标不符）。

（如被问研究问题，给 RQ 口径：①容器沙箱有没有性能惩罚 ②生成失败后哪种修复策略更优 ③补测闭环是"学习环"还是"重试环" ④失败归因准确率多少 ⑤报告审查能否拦住数字失真。）

## 2. 怎么做（4.5 分钟）——本次汇报的重点

### 2.1 总体框架（1.5 分钟）

**五层架构，一张图讲完**：

| 层 | 内容 | 对应测试理论 |
|---|---|---|
| L1 界面层 | Web 界面：任务管理、报告展示、人工确认门 | 人机协作 |
| L2 编排层 | LangGraph 固定图：单元级 9 节点主图（克隆→分析→计划→备环境→生成→执行→评估→报告→审查）+ 集成级子图 + 级间串行接力 | ISTQB 四阶段（分析/设计/执行/评估） |
| L3 技能层 | 工具注册表：执行类 + 评估类，每次调用自动留审计台账 | 工具调用可追溯 |
| L4 沙箱层 | Docker 常驻容器 + 预构建镜像，LLM 生成的测试在隔离环境里跑 | 环境即镜像、可复现 |
| L5 数据层 | SQLite 数据库：任务、用例、测试条件、RTM 矩阵、审计台账全落库（进度表口径 18 张表起步） | 过程可追溯 |

**一个关键设计决策**（主动讲，这是答辩加分点）：编排骨架是固定图，LLM 的"规划"是节点的产物，不是让 LLM 自由控制流程——保证系统可复现、可画图、可讲解。

### 2.2 五个关键机制（2 分钟，每个一句话+一个关键词）

1. **测试条件层（plan/RTM）**：LLM 把自然语言需求拆成结构化测试条件，建需求追踪矩阵，用例六要素结构化（编号/标题/级别/输入/步骤/预期）——对应测试设计阶段的正统方法论。
2. **带护栏的补测闭环（R-Loop）**：失败先归因三分类——环境失败修环境、用例缺陷重写用例、**产品缺陷冻结为"证人"如实上报，绝不为它改断言**；同指纹熔断防原地打转，轮次预算防无限重试。核心纪律：**不承诺"直到成功"，达标或预算耗尽时如实上报**。
3. **多道审查闸**：生成的用例过静态闸+可收集闸（+LLM 交叉语义审），报告数字全部由确定性代码从数据库算出，LLM 只负责叙述，报告再做二次审查（规则闸先行+LLM 闸）——针对的就是 2412.14137 指出的"生成器为通过而设计断言"问题。
4. **防造假证据链**：每条断言标注预期值来源（需求明示/文档/源码推导），需求明示的失败用例永不删除、永不为它改断言——宁可误报，不可造假。
5. **四级双轨应用策略**：单元级=黑盒方法骨架（等价类/边界值/判定表/状态迁移/蜕变等槽位模板）+白盒覆盖反馈与缺口回灌；集成级=契约断言+调用链分析定位集成路径；系统级=业务流场景自动生成执行；验收级=场景清单辅助人工确认并可转化为可执行回归资产；配跨级需求追踪，高层失败可定位到单元用例与代码位置。

### 2.3 实验设计（1 分钟）

- **E1 容器 vs 宿主性能对比**（支撑沙箱选型）；
- **E2 三种修复链路受控对比**（剪除/重写/混合，同一被测对象同一初始条件）；
- **E3 补测闭环轮次轨迹**（每轮有没有信息增量）；
- **E4 变异标定**：用 mutmut 注入已知缺陷，测归因器的混淆矩阵——归因准确率从"口头承诺"变成可量化指标；
- **E5/X 格**：自建"出题—答题—阅卷"三方盲测语料（植入已知缺陷附答案键），控制变量逐个开关测各组件对检出率的贡献；
- **E6-E8（计划）**：集成层黑盒白盒双轨消融、跨级需求追踪与缺陷溯源有效性验证、四级评价矩阵。

一句话：**所有结论都有可控真值，不自说自话。**

## 4. 预期成果（1.5 分钟）——开题按"预期"口径讲

3. **五项预期结果**（与 docx 一致）：
   - 验证容器化执行不引入显著性能损失：同机对比实验测量容器与宿主直跑耗时，如实报告单机、微型被测项目等实验边界；

   - 验证跨级缺陷溯源链能将高层测试失败定位到具体单元用例与代码位置。

## 5. 可能被问的问题（一句话回答口径）

| 问题 | 回答口径 |
|---|---|
| 创新点在哪？是把现有工具拼起来吗？ | 单点技术都有出处（TestGen-LLM/CoverUp/YATE），创新在三点：全流程四阶段闭环的系统化整合；防造假机制（证人冻结/预期来源标注/审查双闸）；用控制变量实验量化每个组件的贡献——国内外都缺第三点。 |
| LLM 幻觉、生成不可靠怎么办？ | 多道闸（AST 静态检查/容器内可收集检查/LLM 交叉语义审/报告数字比对）+ 评估数字全由确定性代码计算 + 归因保守默认"宁可误报不可造假"。这正是 2412.14137 实证的问题，本课题的设计就是针对它。 |

| 容器会不会很慢？ | 预研初步显示容器执行性能与宿主直跑相当（常驻容器+exec 模式、镜像预构建），正式结论以对比实验为准。【中期/答辩用】实测：热运行 0.8 秒 vs 宿主 3.1 秒（约 3.8 倍），冷启动一次性 1.3 秒。 |
| 怎么证明系统有效，而不是自己说好？ | 可控真值：盲测语料（植入已知缺陷+答案键，出题人/答题人/阅卷人隔离）+ mutmut 变异标定混淆矩阵 + 每格 n≥3 的控制变量矩阵。 |
| 中途发现需求理解错了/需求变更怎么办？ | RTM 的反向追溯：条件→用例→结果可反查受影响范围；v1 范围是单轮生成，需求变更影响分析列未来工作（诚实边界）。 |

| 上次老师说范围太大，现在收敛成什么了？ | 两层收敛：方法维度收敛到黑盒、白盒两族（黑盒管"测什么"、白盒管"测够没有"，两族组合成闭环）；层级维度按四级递进——单元/集成深度自动化（研究主体），系统/验收半自动辅助。面向 Python、功能正确性；压测/安全/UI 排除，系统级仅做业务流冒烟。收敛是研究范围的校准，系统架构按此设计。 |
| 为什么只做黑盒和白盒，其它测试不做？ | 两个维度回答：①方法维度——用例设计方法按"是否依据程序内部结构"分为黑盒族（依据需求规格设计）与白盒族（依据代码结构度量），这两族穷尽了可系统化设计方法的主体；灰盒只是两族的混合策略不是第三族（本课题的黑盒设计+白盒覆盖反馈本身就是受控的黑白组合）；经验型方法依赖人工直觉、不可预注册复现，其中可自动化的错误推测法已做成缺陷模式知识库吸收进黑盒族。②类型维度——性能/压测、安全、UI 等要么作用于系统层级、要么需要另一套测试预言（性能阈值、漏洞模式），与"功能正确性"的聚焦口径不符，全部列为未来工作。一句话：黑盒管"测什么"、白盒管"测够没有"，两族组合成闭环，这就是本课题的方法主线。 |
| 黑盒白盒测试自动化前人做过很多，你的空间在哪？ | 前人（TestGen-LLM/CoverUp/YATE）只做单点环节；本课题的空间在①全流程四阶段闭环+四级递进的系统化整合 ②防造假机制（证人冻结/预期来源标注/审查双闸）③用控制变量实验量化各组件贡献——这三点是文献里缺的。 |

## 5.5 名词对照页（老师听不懂时翻这里）

> 讲稿里我们自己的叫法，第一次出现时用一句话解释；这页是备查。

| 我们的叫法 | 一句话解释 | 对应的通行术语 |
|---|---|---|
| 五层架构 | 界面层/编排层/技能层/沙箱层/数据层 | 系统分层设计 |
| 四级双轨 | 单元/集成/系统/验收四个测试级别递进应用，黑盒+白盒两族方法贯穿 | 测试级别 × 用例设计方法族 |
| 固定图编排 | 主流程画成固定有向图，每步一个节点；LLM 只在节点内产出内容，不决定走向 | 工作流编排（LangGraph） |
| plan 节点 | 把自然语言需求拆成结构化"测试条件"的那一步 | 测试分析（ISTQB）+ 验收标准 |
| RTM | 需求→条件→用例→结果 的对应矩阵，证明覆盖、支持反查 | 需求追踪矩阵（Gotel 1994） |
| R-Loop | 失败后"归因→修复→重测"的闭环，有轮次上限 | 回归测试闭环 / 反馈驱动生成 |
| 指纹熔断 | 两轮失败报错指纹相同即判"原地打转"，停止重试 | 对应 ISTQB"测试会磨损"原则 |
| 缺陷证人冻结 | 判定为产品真缺陷的失败用例保留为证据，禁止改断言让它变绿 | oracle 独立性 / 防过拟合 |
| expected_basis | 每条断言标注预期值来源（需求原文/文档/源码推导） | 测试预言（oracle）来源标注 |
| 准出标准冻结 | 开局就定死覆盖率阈值+轮次预算，过程不可改 | exit criteria（ISTQB） |
| 静态闸 / 可收集闸 | 生成用例先做语法引用检查，再容器内试收集，两道都过才执行 | 静态分析 + collect-only 校验 |
| 契约测试（集成级） | 按 OpenAPI 契约断言接口行为（状态码/字段/模式），不猜实现 | 契约测试 / schema 断言 |
| 调用链分析（集成级） | 从代码调用图定位集成层应覆盖的路径与入口 | 调用图分析（白盒） |
| 跨级溯源 | 高层测试失败沿"验收←系统←集成←单元"链定位到单元用例与代码位置 | 需求追踪的反向应用 |
| 变异标定 | 注入已知小错误，看系统能否判为产品缺陷，用混淆矩阵算准确率 | 变异测试（mutation testing） |
| 三方盲测 | 出题人（造语料+答案键）/答题人（被测系统）/阅卷人（评分）隔离 | 盲测协议 / 基准评测 |
| X 格 | 每次只关一个机制、其余不变地跑，比较检出率贡献 | 消融实验（ablation study） |
| E1-E8 | 实验编号：E1 性能 / E2 三链路 / E3 轨迹 / E4 变异标定 / E5 审查 / E6-E8 集成双轨消融与跨级溯源（计划） | 实验编号（论文内部） |
| static_only | 该语言不做动态执行、只做静态扫描的分级策略 | 缺陷降级 / 范围界定 |

> 内部文件名（如 `skills/evaluate.py`、`data/corpus/corpus-001`、`grade_task45.json`）只出现在代码文档里，开题报告正文不出现；答辩被问到再解释"这是实验数据落盘位置"即可。
