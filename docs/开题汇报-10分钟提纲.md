## 0. 开场（30 秒，可直接念）

> 老师好，我的题目是《基于大模型 Agent 与容器技术的自动化单元测试方法研究》。
> 一句话概括：让大模型 Agent 按照测试的四个阶段——分析、设计、执行、评估——自动完成**单元测试**的全流程闭环，用容器技术保证执行环境隔离、可复现、可审计，最后用控制变量实验量化"哪种方法组合最有效"。
> **范围一句话**（响应上次开题会意见）：按老师建议，课题已收敛到单元测试这一个层级（Python、功能正确性）；黑盒方法（等价类/边界值/判定表）和白盒覆盖分析是用例设计阶段内部使用的两类技术，压力/安全/界面测试不在范围内。

## 1. 选题（2 分钟）

**背景三句话**：
1. 软件测试是质量保障的核心环节，但用例设计和执行高度依赖人力，覆盖不足、回归成本高。
2. 大模型已经能从自然语言需求直接生成测试用例，但现有方法有三个已知问题——
   - 断言"跟着实现走"：实证研究（arXiv:2412.14137）表明这类生成器测不出缺陷，反而会把缺陷行为验证成"预期"；
   - 生成物缺乏可信执行环境，过程不可复现、不可审计；
   - 缺乏"哪种 Agent 测试方法更有效"的可量化对比。
3. 国内研究多集中在提示词工程和单点生成，缺一套覆盖"分析—设计—执行—评估"全流程的系统化方案。

**研究目标一句话**：构建一个可控、可审计、可复现的测试 Agent 系统，并通过控制变量实验找出最适合 Agent 测试的方法组合。

**为什么聚焦单元测试（响应老师意见，主动讲）**：软件测试是个大类，本课题收敛在**单元测试层级**——它是测试金字塔的基座、人力投入最密集的一层（ISTQB §5.1.6）；课题限定 Python 语言、功能正确性目标，性能/安全/界面测试明确排除。老师提到的黑盒/白盒不是被排除而是被内化：等价类/边界值/判定表（黑盒）是用例设计的方法骨架，覆盖分析（白盒）是查漏反馈——两者都在单元测试设计阶段内部。

（如被问研究问题，给 RQ 口径：①容器沙箱有没有性能惩罚 ②生成失败后哪种修复策略更优 ③补测闭环是"学习环"还是"重试环" ④失败归因准确率多少 ⑤报告审查能否拦住数字失真。）

## 2. 怎么做（4.5 分钟）——本次汇报的重点

### 2.1 总体框架（1.5 分钟）

**五层架构，一张图讲完**：

| 层 | 内容 | 对应测试理论 |
|---|---|---|
| L1 界面层 | Web 界面：任务管理、报告展示、人工确认门 | 人机协作 |
| L2 编排层 | LangGraph 固定图 9 节点：克隆→分析→计划→备环境→生成→执行→评估→报告→审查 | ISTQB 四阶段（分析/设计/执行/评估） |
| L3 技能层 | 工具注册表：执行类 3 个 + 评估类 5 个，每次调用自动留审计台账 | 工具调用可追溯 |
| L4 沙箱层 | Docker 常驻容器 + 预构建镜像，LLM 生成的测试在隔离环境里跑 | 环境即镜像、可复现 |
| L5 数据层 | SQLite 16 张表：任务、用例、条件、RTM 矩阵、审计台账全落库 | 过程可追溯 |

**一个关键设计决策**（主动讲，这是答辩加分点）：编排骨架是固定图，LLM 的"规划"是节点的产物，不是让 LLM 自由控制流程——保证系统可复现、可画图、可讲解。

### 2.2 四个关键机制（2 分钟，每个一句话+一个关键词）

1. **测试条件层（plan/RTM）**：LLM 把自然语言需求拆成结构化测试条件，建需求追踪矩阵，用例六要素结构化（编号/标题/级别/输入/步骤/预期）——对应测试设计阶段的正统方法论。
2. **带护栏的补测闭环（R-Loop）**：失败先归因三分类——环境失败修环境、用例缺陷重写用例、**产品缺陷冻结为"证人"如实上报，绝不为它改断言**；同指纹熔断防原地打转，轮次预算防无限重试。核心纪律：**不承诺"直到成功"，达标或预算耗尽时如实上报**。
3. **多道审查闸**：生成的用例过静态闸+可收集闸，报告数字全部由确定性代码从数据库算出，LLM 只负责叙述，报告再做二次审查（规则闸先行+LLM 闸）——针对的就是 2412.14137 指出的"生成器为通过而设计断言"问题。
4. **防造假证据链**：每条断言标注预期值来源（需求明示/文档/源码推导），需求明示的失败用例永不删除、永不为它改断言——宁可误报，不可造假。

### 2.3 实验设计（1 分钟）

- **E1 容器 vs 宿主性能对比**（支撑沙箱选型）；
- **E2 三种修复链路受控对比**（剪除/重写/混合，同一被测对象同一初始条件）；
- **E3 补测闭环轮次轨迹**（每轮有没有信息增量）；
- **E4 变异标定**：用 mutmut 注入已知缺陷，测归因器的混淆矩阵——归因准确率从"口头承诺"变成可量化指标；
- **E5/X 格**：自建"出题—答题—阅卷"三方盲测语料（植入已知缺陷附答案键），控制变量逐个开关测各组件对检出率的贡献。

一句话：**所有结论都有可控真值，不自说自话。**

## 4. 预期成果（1.5 分钟）——开题按"预期"口径讲

   - 同机对比实验验证容器化执行不引入显著性能损失（如实报告单机/微型项目等实验边界）；

## 5. 可能被问的问题（一句话回答口径）

| 问题 | 回答口径 |
|---|---|
| 创新点在哪？是把现有工具拼起来吗？ | 单点技术都有出处（TestGen-LLM/CoverUp/YATE），创新在三点：全流程四阶段闭环的系统化整合；防造假机制（证人冻结/预期来源标注/审查双闸）；用控制变量实验量化每个组件的贡献——国内外都缺第三点。 |
| LLM 幻觉、生成不可靠怎么办？ | 三道闸（AST 静态检查/容器内可收集检查/报告数字比对）+ 评估数字全由确定性代码计算 + 归因保守默认"宁可误报不可造假"。这正是 2412.14137 实证的问题，本课题的设计就是针对它。 |
| 和直接用 ChatGPT/Copilot 生成测试的区别？ | 单点生成 vs 全流程：有条件拆解、有隔离执行、有回归补测、有准出核对与如实上报；且过程全部落库可审计。 |
| 容器会不会很慢？ | 实测相反：常驻容器+exec 模式热运行 0.8 秒，比 Windows 宿主直跑 3.1 秒快约 3.8 倍；镜像预构建，冷启动一次性 1.3 秒。 |
| 怎么证明系统有效，而不是自己说好？ | 可控真值：盲测语料（植入已知缺陷+答案键，出题人/答题人/阅卷人隔离）+ mutmut 变异标定混淆矩阵 + 每格 n≥3 的控制变量矩阵。 |
| 中途发现需求理解错了/需求变更怎么办？ | RTM 的反向追溯：条件→用例→结果可反查受影响范围；v1 范围是单轮生成，需求变更影响分析列未来工作（诚实边界）。 |
| 【中期/答辩用】关掉方法骨架反而 0.78 最高，是不是说明五方法没用？ | 不能这么推。0.78 那一格同时保留 plan/RTM，只是方法骨架关掉——说明"检出主要靠需求被拆成显式条件"，方法骨架的作用要在"条件已固定"的前提下单独测，这正是后续实验要拆开验证的；n=3、标准差 0.19，现在只能作为待解释的观察。 |
| 【中期/答辩用】0.33 和 0.56 的差距，能说明问题吗？ | 不能单独说明，所以只写"方向性证据"：关闭组三次完全一致（0.33 标准差为 0）是唯一稳的点；数字已按"占位项剔除分母"的重算口径统计，论文里会继续扩大语料（增加真实缺陷数）并复跑后才下结论。 |
| 中期检查在第 1 周就要论文初稿，来得及吗？ | 按学院时间表倒排：第 1 周（约 2027-02-25）前要交"可运行系统+论文初稿"，所以进度表把实验与初稿都压在 2027.02 中下旬；关键技术已完成预研验证，系统实现按进度表推进，主要工作量在系统完善、实验与写作，风险可控。 |

| 我们的叫法 | 一句话解释 | 对应的通行术语 |
|---|---|---|
| 五层架构 | 界面层/编排层/技能层/沙箱层/数据层 | 系统分层设计 |

| R-Loop | 失败后"归因→修复→重测"的闭环，有轮次上限 | 回归测试闭环 / 反馈驱动生成 |

| 变异标定 | 注入已知小错误，看系统能否判为产品缺陷，用混淆矩阵算准确率 | 变异测试（mutation testing） |
| 三方盲测 | 出题人（造语料+答案键）/答题人（被测系统）/阅卷人（评分）隔离 | 盲测协议 / 基准评测 |
