# 两阶段人机协作流程设计（2026-10-31，用户提出+AI 补充，待实施）

## 用户原始诉求（原话要点）
1. 人工确认完 → 先做 clone/摸底/出考纲/出题（这些是主要的），做好后**停下来**等人审查；
2. 人审查时：插入/取消用例 + **对话框**把自己的想法告诉 AI 让它再生成需求的用例；
3. 审批完 → 下发执行 → 才做布考场/开考/判卷/写报告/复审；
4. 两个流程各做单独界面，显示做到哪里（进度条），期间输出全显示；
5. 任务列表的操作按钮保留。

## AI 补充的 6 条设计决策
1. **确认语义升级**：确认=授权+自动启动阶段一，跑完停在"待审查"（新任务状态，schema CHECK 需迁移）；下发=启动阶段二。任务列表新增"待审查"状态胶囊。
2. **对话增补三纪律**：①反馈只增补不动已批准用例——每轮独立 test_gen_fbN.py 走同样三道闸，可整轮禁用；②反馈历史+生成结果全留档（llm_calls phase=gen_feedback）；③预算封顶：增补≤5 轮、每轮条数上限（防无限对话）。
3. **R-Loop 归属阶段二**：执行中用例挂了自动修复重跑（无人值守能力保住）；阶段一人工审查只管初始用例集。两线不混。
4. **四级接力点不变**：阶段二 L1 报告+复审过 → 自动接 L2→L3→L4。
5. **资产平移**：wb-plan 方案链面板、用例勾选启停、插入用例表单全搬进阶段一评审页；"输出全显示"用现成 agent_messages 日志流加实时区。
6. **进度条零新发明**：节点本就写任务状态，两段式 stepper（阶段一 4 格：克隆/摸底/考纲/出题；阶段二 5 格：布考场/开考/判卷/报告/复审）。

## 风险与注意
- schema CHECK 迁移：老库 ALTER 不改 CHECK——SQLite 改 CHECK 需重建表或放宽新库 CHECK+代码层校验（选后者省事：status TEXT 保留 CHECK 但加新值需重建，评估工作量时注意）
- 修复循环的 generate 在阶段二上下文里跑：generate 节点不依赖 provision 重跑（容器活着，写盘+回灌即可）——拆图时保持该性质
- 3s 轮询重渲染：阶段一页面的展开/收起状态用粘性 Set（同 PG_COLLAPSED 先例）
- 对话增补的用例 expected_basis 纪律照旧（用户口头反馈≠需求明示，标注"用户反馈"新枚举或复用"需求明示+备注"——实施时定）
