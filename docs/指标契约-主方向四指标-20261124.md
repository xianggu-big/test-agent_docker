**outcome 判定规则（按顺序，先中先得）**——v1 正式版（对草案 §5.1 有一处修订，见 §3 修订记录）：

1. `not_completed_user`：任务被用户/管理员取消（`test_tasks.status='cancelled'`，stop API 路径）。
2. `not_completed_env`：`failure_kind='env'` 的 stop。**修订**：不再要求"零有效执行"——S1-S4（零执行）与 S7/S9 落 env（有执行但环境致未达标）都归此，`有效完成率(排环境)` 分母因此同口径排除。env 类失败率=此计数/D。
3. `not_completed_agent`：`failure_kind ∈ {'case_defect','none'}` 且 verdict=stop 且非诚实出口（S5/S14，及 S7/S9 落这两类）；含出题 0 条、不可解析、脚手架坏、预算耗尽未获结论、图异常。
4. `completed`：有有效执行 + 报告落库 + verdict=pass（`repair.py:206-207`）；或 failure_kind=product_defect（S6/S12 有失败变体——检出缺陷即目标达成）。
5. `completed_with_limitation`：有报告落库的诚实出口（S8/S10/S11/S12 无失败变体/S13）。

**"有效执行"定义**：本 attempt 终态快照中 ≥1 条 `test_case_results` 行 status ∈ {passed, failed}（防假绿铁律：用例数>0 且断言真执行）。v1 无 run_id，用终态快照（`agent_runs.summary_json`）判定；历史任务用最新轮 `evaluation_rounds` 的 passed+failed>0 近似（标 approx）。

**手算示例**：任务 #2601 stop_reason="管理员停止" → status=cancelled → not_completed_user（只报计数不进分母）。任务 #X：3 passed / 2 failed，failure_kind=product_defect，stop_reason="疑似产品缺陷…" → completed。任务 #Y：0 passed / 0 failed，failure_kind=env（Go 工具链闸）→ not_completed_env。

**异常边界**：零样本（D=0）→ 四个率全部 `null` 不报 0；`not_completed_user` 不进 D 也不进分子；缺失字段（无报告行）→ not_completed_agent 并计"报告缺失数"。

### 1.2 工具调用结局分类表（对码项 2）

**代码事实**：`skill_invocations.status` 取值域 = `ok / failed / timeout / denied`（`registry.py:32` SkillResult 注释；写入点 `registry.py:220-239`）。策略闸 `Decision` 字段 = `allowed / reason / risk / stop / stop_reason`（`tool_policy.py:27-33`）。Agent 决策循环内每步的证据行 status（`tool_loop.py:199,214,229,253,260`）：`unparseable / denied / <registry status>`。

| 结局 | 判定 | 锚点 |
|---|---|---|
| `ok` | 能力执行成功返回 | `registry.py:239` |
| `failed` | handler 异常/执行失败（tool_loop 兜底也归此） | `tool_loop.py:244-246` |
| `timeout` | 注册表超时闸（future.result 超时 → status="timeout"） | `registry.py:194-200` |
| `denied_registry` | 注册表闸拒：停用/确认门/schema/任务不存在 → status="denied" | `registry.py:157,162,172,174` |
| `denied_policy` | 策略闸拒（Decision.allowed=False）→ evidence status="denied"，deny_reason=reason | `tool_loop.py:213-215` |
| `parse_error` | 模型输出不可解析 → evidence status="unparseable" | `tool_loop.py:194-201` |
| `not_executed` | 策略闸 stop=True（预算/重复）——该步已发起但未执行 | `tool_loop.py:211-212`；`tool_policy.py:89-101` |
| （finish） | goal_met，不是调用，**不计入分母**，单独计数 | `tool_loop.py:203-204` |

**denied_policy 的拒绝原因前缀 → 子类**（`tool_policy.py:47-101` 七闸顺序=优先级）：

| reason 前缀 | 子类 | 闸 |
|---|---|---|
| `协议违规` / `call 缺 capability` | protocol | 闸 1 |
| `能力不在菜单` | existence（**编造能力幻觉的机器证据**，进 C2） | 闸 2 |
| `参数校验拒绝` | schema | 闸 3 |
| `密钥键名越界` / `能力声明了 secrets` | secret | 闸 4 |
| `验证冻结任务仅允许 R0` / `静态模式仅允许 R0` | mode | 闸 5 |
| `R3 需人工批准` / `R4…` / `R2 目录插件仅 normal` | governance | 闸 5 |
| （预算/重复走 stop=True 不产生 denied） | — | 闸 6/7 |

**循环级 stop 原因取值域**（`tool_loop.py:158-264`）：`goal_met / budget / repeated_action / policy_deadlock / no_new_evidence / hard_error`（hard_error 含菜单空 `:166`、LLM 构造失败 `:171`、LLM 调用异常 `:188`、两次不可解析 `:198`）。

**手算示例**：某 run 循环摘要 `{loops:[{mode:strategy, stop:goal_met, steps:3, used:{...}}]}`，步骤结局=[ok, denied_policy(能力不在菜单), finish] → 发起分母=2（denied 计入），执行分母=1，调用成功率=1/2=50%，执行成功率=1/1=100%，拒绝率=1/2=50%；denied 中因编造（existence）比例=1/1=100%。

**异常边界**：零调用 run 不进分母但报"零调用 run 数"；`denied_registry` 与 `denied_policy` 分开计——混算会掩盖"模型编造"与"平台治理"两类不同性质的拒绝。

### 1.3 finish 产物键 → claim 类型（对码项 3）

**代码事实**：strategy finish 形态键 = `summary` + `strategy.priorities[].{order, capability_id, why, args_hint}` + `evidence_plan` + `fallback`（`prompt_library.py:555-569`）；diagnose finish 形态键 = `diagnosis.{kind, confidence, evidence_refs, reason, suggested_action}`（`prompt_library.py:571-575`）；diagnose 四分类 = scaffold_error / env_error / product_defect / expectation_dispute（`prompt_library.py:578-589`）。

| claim 类型 | 来源键 | 核对方法 | 幻觉类别 |
|---|---|---|---|
| C1 引用断言 | `diagnosis.evidence_refs`（step 序号）、`strategy.priorities[].args_hint` 引用的文件/符号 | 序号 ∈ 本次循环 evidence 列表；路径 ∈ 工作区；符号 ∈ 索引 | 机器可核对 |
| C2 工具断言 | 发起调用的 `capability` + `args` | ∈ 菜单（策略闸 2）；符合 schema（闸 3）——**即 denied_policy 子类 existence/schema 的机器计数** | 机器可核对 |
| C3 事实断言 | finish 的 `summary`；`strategy.priorities[].why`；`diagnosis.reason` | 人工复核三值：supported / contradicted / unverifiable | 机器不可核对 |
| 不计 | `evidence_plan`、`fallback`、`suggested_action` | 计划与降级路线，非断言 | — |

**公式**：可核对幻觉率 = (C1 无效引用 + C2 无效调用) / (C1 引用总数 + C2 调用总数)；事实断言幻觉率 = contradicted / 已标注 C3（unverifiable 单列不进分子）。
**流程**：执行者预标（每条带证据指针）→ 用户抽检 ≥20%（Q3 未勾 → 只叫"预标值"）→ 分歧仲裁 → 定稿。
**与 5.2 的关系**：同一次编造能力既是 denied_policy(existence)（5.2）又是 C2 幻觉——报告须给"denied 中因编造所致比例"，两数同源不同名。
**已知边界**（对码结论）：`AGENT_STRATEGY_FINISH_EXAMPLE` 示例里 `capability_id: "gen_cases"` 非真实菜单 id（真实 `test.gen.cases`，`capabilities.py:449`）——Q4 未拍板不改提示词，C2 对示例本身不计（示例是提示词不是模型产出）。
