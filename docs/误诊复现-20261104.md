# task_366 误诊 A/B 复现记录（2026-11-04，论文 6.9 讨论素材）

> 论据口径：12 条「疑似并发缺陷」的失败根源不在被测项目 questionforge，
> 而在平台生成用例的路径脚手架。本文记录本地一次性复现的 A/B 对照实验——
> 同一容器、同一 MySQL 隔离库，唯一变量是用例文件中 1 行 ROOT 定义。

## 0. 环境架构（MySQL 在哪、怎么连）

| 角色 | 位置 | 说明 |
|---|---|---|
| MySQL 服务 | **宿主机 Windows 服务**（127.0.0.1:3306，8.0.32） | Docker 里**没有** MySQL 镜像/容器 |
| 生产库 | 宿主 MySQL `questionforge`（20 表，23 任务） | 全程未被触碰 |
| 隔离测试库 | 宿主 MySQL `questionforge_test`（20 表，迁移标记至 013） | 与仓库 ci.yml 的测试库同名同口径 |
| 执行容器 | Docker `mta-test:node20-jest`（node20+jest） | 平台 run 节点同款镜像 |
| 容器→宿主 MySQL | `--add-host=host.docker.internal:host-gateway` + `QF_DB_HOST=host.docker.internal` | 被测项目 `lib/db.js:16-20` 以 `QF_DB_*` 环境变量取连接参数，`QF_DB_NAME` 默认生产库名，必须显式指到 `_test` |

注意：容器内 127.0.0.1 是容器自己，不是宿主机——凡在容器里跑的 DB 依赖用例，
必须走 host-gateway 映射，这正是「环境依赖缺失」类归因（ECONNREFUSED）的成因之一。

## 4. 结论与论文引用口径

1. **A/B 对照唯一变量 = 1 行路径脚手架** → 12 条失败的平台侧成因实锤；
   A 组在 MySQL 就位时仍全灭，排除「数据库环境缺失」作为主因（环境缺失只解释
   无 DB 容器里 cleandata 4 条的 ECONNREFUSED 形态，见修复会话 8/12 实验）。
2. 被测项目 questionforge 全程只有 1 条真缺陷（多进程并发初始化的迁移竞争，
   修复会话在老 schema 库上 8 进程并发实测 21/24 败，修复后 0/40 败，GET_LOCK 串行化）。
3. 误诊链（6.9 讨论「AI 归因的虚高」叙事）：脚手架路径错 → 子进程报错只进
   jest stderr 且被适配器丢弃 → 归因器无 stderr 证据，从源码猜 exit 分支 →
   12 条全部误诊「并发产品缺陷」。修复 = 确定性脚手架修正（gen_tests）+ stderr
   诊断段（js_adapter）+ 归因判别纪律（defect_analysis），commit 7321cca。
4. 可复用教训：**「形态相似 ≠ 根因同一」**——外部 AI 报告的 env 假说（spawn
   ENOENT）能自洽解释失败形态（exit 1 + stdout 空），但与落库原始文件矛盾；
   引用任何失败解释前先核对原始证据。
