## 0. 一页结论

1. **方法组合**：黑盒 9 法 + 白盒 8 法（本文 §2/§3），每条带已核验出处、怎么做、系统落点、语言场景适配、模板化可行性。
2. **沙箱不需要"万能"**：需求规格说明与源码是**测试设计**的输入（已有：requirement_text + clone 工作区）；沙箱只由**执行语言+工具链**决定。所以"随机应变"的正确形态 = 语言检测 → 镜像注册表 → 按需自动补齐（§6），不是为每种可能造环境。
3. **用户三模式**（用户点名的需求）：①手动感知型——下发被守卫拦下，顶栏红条提示，去界面点单镜像下载按钮（已实现）②一键准备——点一下全补齐（已实现）③傻瓜式一条龙——开局自动拉取镜像，用户不怕等（新增一个开关）。
4. **预置模板库**：6 种方法可"槽位填充式"生成（LLM 只填 JSON 参数，代码骨架预置）——降 token、提过闸率、缩运行时间（§5）。
5. **大厂七维度**：检出力/成本/稳定性/可追溯/风险分级/防造假/规模治理（§7）——论文"讨论"节与答辩框架。

## 1. 目的 · 价值 · 边界（论文绪论与"范围界定"节素材）

### 1.1 测试的目的是什么（为什么做单元测试）

- 单元测试是测试金字塔的基座、人力投入最密集的一层（Fowler 2012 ✅官方、ISTQB CTFL v4 §5.1.6 ✅官方）——自动化收益最明确。
- 单元级缺陷暴露成本最低、定位最准：函数级输入输出契约清晰，oracle 问题在单元层最可控（Barr TSE 2015 综述 ✅Crossref）。
- LLM 时代的新动机：LLM 大量生成代码 → "AI 写码"需要对称的"AI 测码"守门（TestGen-LLM ✅arXiv 2402.09171 证明了工业可行性：73% 推荐接受率）。

### 1.2 帮助人类解决什么问题（论文"意义"节）

1. **把重复劳动闭环化**：分析→设计→执行→评估四阶段全自动，人类只做确认门与终态判读。
2. **把"老师傅经验"显式化**：错误推测法从"个人直觉"变成可复用的缺陷模式知识库（§2-B5），新工程师生效。
3. **把测试有效性从"感觉"变成"数字"**：覆盖率（测了什么）× 变异杀死率（测出了什么）双尺子，归因混淆矩阵给准确率置信区间（E4）。
4. **把"不可信"关进容器**：LLM 生成物在隔离沙箱执行、全程审计台账，可复现可追责。
5. **把"造假"堵住**：断言先于执行、预期来源标注、证人冻结、报告双闸——针对 2412.14137 ✅arXiv 实证的"生成器验证 bug"问题，这是本课题对现有工具链的差异化贡献。

### 1.3 作用在哪些方面

开源中小型 Python 项目的单元回归测试；LLM 辅助编程的生成物质量守门；测试课程教学演示；未来接入 CI 作为提交门禁（DORA 口径度量收益，✅官方 dora.dev）。

### 1.4 边界（诚实范围，答辩防线）

| 维度 | 边界 | 依据/现状 |
|---|---|---|
| 测试级别 | 只做单元测试（+轻量集成）；集成/系统/验收不做 | 收敛口径 |
| 测试类型 | 功能正确性；性能/压测/安全/UI/E2E 明确排除 | 开题会意见 |
| 语言 | Python 全链路；Java 镜像就绪、执行链路 v1 占位（nodes.py 诚实终止）；其他语言 static_only（不进沙箱） | analyze 分级（口径 b） |
| 白盒深度 | 语句/分支覆盖（coverage.py 能力圈）；路径覆盖/数据流列为未来工作 | §3-W4 |
| oracle | 自动归因不可能 100% 准——"宁可误报不可造假"，混淆矩阵给准确率 | vision §7 |
| flaky | v1 不治理（指纹熔断≠flaky），数据层留人工标注通道 | industry 报告 §7 |
| 实验环境 | 单机/Windows 宿主/微型项目/n≥3 复跑 | experiment-design §7 |

## 2. 黑盒方法族（需求规格说明驱动，9 法）

> 共同输入：requirement_text（自然语言需求）+ 函数签名/docstring。共同纪律：断言先于执行、expected_basis 标注预期来源。共同产出：pytest 用例（六要素落库）。

### B1 等价类划分（Equivalence Partitioning）——已实现

- **出处**：ISTQB v4 §4.2.1 ✅官方；学术形式化 = Ostrand & Balcer 类别划分法，CACM 1988，DOI 10.1145/62959.62964 ✅Crossref（本轮核验）。
- **怎么做**：需求→输入域分有效/无效等价类→每类取一个代表值→一类一条用例。
- **落点**：五法骨架第一法（prompt_library）；槽位模板 T1（§5）。
- **场景**：输入校验类函数（长度/范围/格式）；语言无关。

### B2 边界值分析（Boundary Value Analysis）——已实现

- **出处**：ISTQB v4 §4.2.2 ✅官方；Myers《The Art of Software Testing》1979（书，无需 DOI）。
- **怎么做**：min-1/min/min+1/max-1/max/max+1 六点 + 空/None/极端值；本项目"六点模板"直接参数化。
- **落点**：五法第二法；V6 边界攻击开关已实测——LLM 不主动边界攻击（corpus-002 0 证人；Tanaka 2510.25297 ✅arXiv 同结论），**模板化正好补这个短板**（模板强制注入六点，不靠 LLM 自觉）。
- **场景**：数值区间/长度限制/金额/年龄/分页。

### B3 判定表测试（Decision Table Testing）——已实现

- **出处**：ISTQB v4 §4.2.3 ✅官方。
- **怎么做**：LLM 从需求抽条件桩+动作桩→列判定表→合并无关列→每列一条用例；组合爆炸时 LLM 负责化简（这是 LLM 擅长的语义活）。
- **落点**：五法第三法；槽位模板 T2（条件×动作 JSON → 参数化）。
- **场景**：多条件组合业务规则（折扣/权限/费率）。

### B4 状态迁移测试（State Transition Testing）——新增 P1

- **出处**：ISTQB v4 §4.2.4 ✅官方；Chow《Testing Software Design Modeled by Finite-State Machines》IEEE TSE 1978，DOI 10.1109/TSE.1978.231496 ✅Crossref（本轮核验，0-switch/N-switch 覆盖思想）。
- **怎么做**：LLM 从需求/接口抽（状态集, 事件集, 迁移表）→生成 ①合法迁移全覆盖用例 ②非法迁移抽样用例（必须被拒绝）→落成 JSON 交模板渲染。
- **落点**：新增 gen_tests 第七、八法之一；状态机 JSON schema + 通用遍历模板 T3（状态机代码骨架不变，LLM 只填状态/事件/预期）。
- **场景**：订单/购物车/会话/连接生命周期；**诚实边界**：需求里状态语义不显式时 LLM 会瞎猜——先检测需求关键词（状态/订单/登录…）再启用。
- **语言**：语言无关（纯设计层）；Python 先行。

### B5 错误推测法（Error Guessing）→ 缺陷模式知识库——已实现，知识库升级 P1

- **出处**：ISTQB v4 §4.4.1 ✅官方；理论支撑 = 缺陷模式/失效分类学（testing-theory §1.4 已定稿）。
- **怎么做**：把"老师傅经验"显式化为**通用缺陷假设清单**（与具体项目无关、只需改函数名）：None/空串/空列表、0/负数/浮点精度、重复提交、编码/时区、超长输入、并发重入（单元层退化为顺序模拟）。每条假设=一个预置模板用例，LLM 只填"该函数签名下这个假设的输入怎么构造+预期是什么"。
- **落点**：五法第五法已有；**知识库+模板 T4 是 P1 升级**——这是用户"基础方法提前准备、随项目改几个地方就能用"的直接落点，运行时几乎零 LLM 成本（只填槽位）。
- **场景**：所有函数通用；尤其需求写得含糊时（黑盒里最不依赖需求质量的一法）。

### B6 随机测试（Random Testing，DART 谱系）——新增 P2

- **出处**：Godefroid/Klarlund/Sen《DART: Directed Automated Random Testing》PLDI 2005，DOI 10.1145/1065010.1065036 ✅Crossref（本轮核验原始版）。
- **怎么做**：inspect 签名→类型驱动随机值→crash oracle（不崩=过）+可选断言。定位为**冒烟层**（弱 oracle，量大便宜）。
- **落点**：Hypothesis st.data/随机策略即可实现（Python）；登记进五法+PBT 之后作为第九法。
- **场景**：解析器/健壮性冒烟；与 B7 的区别：不写属性、只打不崩。

### B7 属性测试（Property-Based Testing）——已实现（方案 B）

- **出处**：Claessen & Hughes《QuickCheck》ICFP 2000，DOI 10.1145/351240.351266 ✅Crossref（本轮核验原始版）；工具 Hypothesis ✅官方；LLM+PBT 三篇 ✅arXiv（2505.23549/2510.25297/Etna 2603.27002）。
- **怎么做**：LLM 提炼性质（守恒律/对合/往返 encode∘decode=id/幂等/单调）→生成 @given 策略函数→Hypothesis 执行。
- **落点**：已实现（PBT_ENABLED，方案 B 实验）；V7 断言独立性列语料 v2。
- **场景**：纯函数/可逆变换/集合操作；oracle 弱的需求的强替代。

### B8 蜕变测试（Metamorphic Testing）——新增 P1

- **出处**：Chen 等《Metamorphic Testing: A Review of Challenges and Opportunities》ACM CSUR 2018，DOI 10.1145/3143561 ✅Crossref（旧核验；注意不是 LLMORPH，方向相反，见 literature-map §5）。
- **怎么做**：LLM 提炼蜕变关系 MR（输入变换→输出关系：幂等/对称/单调/平移不变）→每条 MR 生成"源输入+跟随输入+关系断言"用例；**归因联动：MR 违反=强 product_defect 信号**（进 repair 三分类，新增强信号源）。
- **落点**：gen_tests 新法；MR 模式库 T5（常见五类 MR 的参数化骨架）。
- **场景**：**oracle 不明确的函数**（答辩"没有规格怎么办"的标准答案）。

### B9 组合测试（Pairwise / Combinatorial）——新增 P2（加分项）

- **出处**：Kuhn 等《Software fault interactions and implications for software testing》IEEE TSE 2004，DOI 10.1109/TSE.2004.24 ✅Crossref（本轮核验；实证大部分缺陷由 ≤2 因素交互触发）；工具 Microsoft PICT（GitHub 开源 ✅官方仓库存在性）。
- **怎么做**：LLM 抽因子+取值集→pairwise 贪心组合→parametrize 批量用例。
- **落点**：P2；Python 可自写 30 行贪心或调 PICT。
- **场景**：多参数配置函数；把大厂"配置矩阵"思想下放到单元层。

## 3. 白盒方法族（源码结构驱动，8 法）

> 共同输入：clone 下来的源码 + coverage.py/radon 等确定性分析结果。共同纪律：白盒分析结果是**确定性代码**算的，LLM 只消费结果。

### W1 语句覆盖（Statement Coverage）——已实现

- **出处**：ISTQB v4 §4.3.1 ✅官方；工具 coverage.py ✅官方。
- **落点**：pytest --cov=term-missing；test_reports.coverage_line。

### W2 分支/判定覆盖（Branch/Decision Coverage）——已实现

- **出处**：ISTQB v4 §4.3.2 ✅官方。
- **落点**：coverage.py branch 模式；per_file 缺口行→缺口回灌（V4）的数据源。

### W3 覆盖缺口反馈生成（Coverage-Guided Generation）——已实现

- **出处**：CoverUp ✅arXiv 2403.16218；CodaMosa ICSE 2023 ✅Crossref。
- **怎么做**：term-missing 缺口行→注入 generate 提示词→补测（预算内）。
- **落点**：已实现（V4 开关，X4 对照格）；与 CoverUp 的差异=预算内补测+准出冻结（论文已写）。

### W4 圈复杂度 + 基路径分析（Cyclomatic Complexity / Basis Path）——新增 P1

- **出处**：McCabe《A Complexity Measure》IEEE TSE 1976，DOI 10.1109/TSE.1976.233837 ✅Crossref（本轮核验）；工具 radon（PyPI Python 圈复杂度标准工具，实现时核验版本）。
- **怎么做**：analyze/plan 阶段对目标模块跑 radon→V(G) 报告→①复杂度热点优先提示生成（"该函数 5 条独立路径，至少覆盖全部 if/else/for 分支方向"）②报告新增指标"复杂度热点未覆盖"③V(G) 作为风险分级依据（§7 维度五）。
- **场景**：控制流密集函数（解析/规则引擎/校验器）。
- **成本**：低（radon pip 即装，纯确定性）。

### W5 变异测试（Mutation Testing）——已实现（标定仪器定位）

- **出处**：Jia & Harman IEEE TSE 2011 ✅Crossref（旧核验）；工具 mutmut ✅官方；生产级对位 MutGen ✅arXiv 2501.12862。
- **定位**：**不是用例设计方法，是用例有效性的白盒度量仪器**——"覆盖率度量测了什么，变异分数度量测出了什么"（ISTQB 大纲 mutation 0 处，官方依据已核，理论章五法表不收它）。
- **落点**：已实现（E4 混淆矩阵 14/14；mutation_kill.py）；未来升级=条件级杀死率进 collect_metrics（P2）。

### W6 静态分析（Static Analysis）——已实现（闸），分级执行 P2

- **出处**：静态测试理论（testing-theory §1.1）；工具 ruff/bandit/semgrep ✅官方（旧核验）。
- **落点**：已实现=AST 静态闸（生成物 import/符号校验）+collect-only 闸；P2=static_only 分级真正执行（低占比语言整仓 ruff/bandit，不进沙箱——正好与 §6 三态衔接）。

### W7 数据流测试（Data-Flow Testing）——未来工作 P2（诚实边界）

- **出处**：Rapps & Weyuker《Selecting Software Test Data Using Data Flow Information》IEEE TSE 1985，DOI 10.1109/TSE.1985.232226 ✅Crossref（本轮核验；def-use 对覆盖 c-use/d-use 谱系）。
- **定位**：论文相关工作中**必须提**（白盒谱系完整性），实现列未来工作——Python 无成熟 def-use 工具链，自研成本高。这是"白盒深度边界"的出处挂靠。

### W8 覆盖引导模糊测试（Coverage-Guided Fuzzing）——边界条目 P2

- **出处**：Manès 等《The Art, Science, and Engineering of Fuzzing: A Survey》IEEE TSE，DOI 10.1109/TSE.2019.2946563 ✅Crossref（本轮核验）；工程标杆 OSS-Fuzz/libFuzzer（Google ✅官方）。
- **定位**：单元层级内的正确形态 = **Hypothesis target() 面向度量的引导**（targeted PBT，工具文档核验存在）；完整 fuzzing 引擎（Atheris for Python）列 P2——写清"单元层 fuzzing 的降维形态"防答辩被问越级。

## 5. 预置模板库设计（"基础方法提前备好，随项目改几个地方"）

### 5.1 原理

把"与具体项目无关的方法骨架"提前写死成 pytest 代码模板，LLM 只生成**槽位 JSON**（函数名/等价类代表值/边界点/条件表/状态机/MR 对），确定性代码渲染成用例。学术挂靠：IEEE 829 用例规格传统（结构化）✅旧核验 + TestGen-LLM 准入过滤思想（结构先验提高通过率）✅arXiv 2402.09171。

### 5.2 模板清单（P1 落地 5 个）

| 模板 | 方法 | LLM 填的槽位 | 收益 |
|---|---|---|---|
| T1 等价类参数化 | B1 | 函数名、类清单（类名/代表值/预期/是否无效） | 6 类代表值≈1 次小调用 |
| T2 边界六点 | B2 | 函数名、参数上下界、区间语义 | 强制六点，治"不主动边界攻击"实证短板 |
| T3 判定表 | B3 | 条件桩、动作桩、规则表 | 化简由 LLM、渲染零成本 |
| T4 状态机遍历 | B4 | 状态集、事件集、迁移表、非法迁移预期 | 遍历骨架不变 |
| T5 缺陷模式包 | B5 | 函数签名 + 每条假设的构造参数 | **几乎零生成成本**（知识库预置） |

### 5.3 生成协议

gen_tests 提示词改为双通道：方法∈{B1,B2,B3,B4,B5} 且签名可解析 → 走槽位通道（输出 JSON → 校验 → 渲染 → 进静态闸）；否则回退自由生成通道（现状）。渲染产物与自由生成走**同一套闸与落库**，实验可比。

### 5.4 学术注意（防效度事故）

模板=结构先验。做"模板 vs 自由生成"消融时，对照组提示词**不得含模板示例**（writing-for-agents 已抓过 V2 被 schema 示例污染的前科）；两通道的 token/时长/过闸率/recall 全落库，正好是论文"方法组合消融"实验（§8）。

## 6. 沙箱自适应设计（回答"沙箱要随机应变吗"）

### 6.1 概念澄清（先纠正一个隐含误解）

需求规格说明和源码是**测试设计的输入**（系统已有：requirement_text + clone 工作区），与沙箱无关；**沙箱只由"用什么语言执行测试"决定**。所以不需要"万能沙箱"，需要的是：**语言检测（已有 analyze）→ 镜像注册表（已有 IMAGE_BUILD_CTX）→ 按需自动补齐（已有 preflight，需任务级化）**。三者都在，缺的只是"开局自动串起来 + 用户可选模式"。

### 6.2 三态分级（沿用口径 b，沙箱策略各不同）

| 主语言 | 分级 | 沙箱策略 |
|---|---|---|
| python | full | 常驻容器 mta-test:py312，全方法链路 |
| java | full* | mta-test:jdk17-maven 就绪；执行链路 v1 诚实占位（nodes.py 终止），设计层模板可先行 |
| 其他 | static_only | **不进沙箱不拉镜像**（省时间）；P2 落 ruff/bandit 静态报告 |

### 6.3 开局自动补齐流程 + 用户三模式（用户点名的需求）

```
任务确认下发
   │
   ├─ analyze 已测语言占比 → 主语言/分级 → 该任务需要的镜像（0 或 1 个）
   │
   ├─ 模式③ 一条龙（config.AUTO_PREPARE_ENV=1 或任务表单勾选，默认关）：
   │     缺镜像 → 自动构建/拉取 → 状态条显示"准备镜像中"→ 完成后自动继续下发（用户不怕等）
   │
   ├─ 模式① 手动感知（现状默认）：下发被 env_gate 拦下（409+中文提示）
   │     → 顶栏红条+悬停明细 → 设置页单镜像按钮（已有）/ 一键准备（已有）
   │
   └─ 模式② 一键准备：任意时刻点顶栏按钮异步补齐（已实现）
```

- **镜像缺失时的获取顺序**：本地有→用；本地无→`docker build`（注册表构建上下文，工具链版本锁死=可复现账，vision §6）；未来可加 registry pull 兜底（P2）。
- **任务级化（修正现有浪费）**：现在 env_gate 的 ensure 会把注册表里**所有**镜像都构建（包括用不上的 java）。改为**只补该任务所需镜像**（preflight.ensure 加 images 参数）。
- **兜底**：provision 前置 ensure_image(task.image)——镜像在"准备完成→下发"间隙被清掉也能自愈（正好补上此前发现的"ensure_image 没接主链路"缺口）。

### 6.4 代码改动清单（都很小，P0）

1. `preflight.ensure(auto_repair, images=None)`：images=None=全部（现状），否则只补指定镜像。约 5 行。
2. `server.env_gate(task)`：查任务主语言→只需 python 镜像（java 镜像标"链路待接入"不自动构建）。约 10 行。
3. `nodes.provision`：ensure_container 前调 `runner.ensure_image(state["image"])`。2 行 + 1 单测。
4. L1 新建任务表单加"自动准备环境（开局拉镜像，需等待）"勾选 → POST /api/tasks 带 auto_prepare 字段。约 20 行前端。
5. config 加 `AUTO_PREPARE_ENV = False`（默认手动模式，实验预注册纪律：默认值冻结）。

### 6.5 论文口径

"**按需供给的预构建镜像注册表**"：语言检测决定镜像选择，注册表保证工具链版本锁死（可复现），缺失自动补齐（自愈），三档用户模式（可控性）。与 Testcontainers 差异表述不变（行业解决被测代码的依赖，本系统解决生成物的隔离与审计）。E1 的预构建 vs 现场 build 数据直接支撑该设计（benchmarks/results）。

## 7. 大厂软测视角：七个维度（论文"讨论"节框架）

| 维度 | 大厂怎么想 | 本系统落点 | 出处 |
|---|---|---|---|
| 1 检出力 | 覆盖率会说谎，变异分数才是金标准（TestGen-LLM/MutGen 都按"可度量改进"设计） | E4 变异标定、E5 审查、recall 盲测 | 2412.14137 ✅、Jia&Harman ✅ |
| 2 成本 | 每个用例都有 token/时长/维护价——测试是投资不是开销 | E1 耗时基准；P1-E token 台账计划 | DORA ✅ |
| 3 稳定性 | flaky 是头号治理对象（Google/Meta 专题工程） | 指纹熔断≠flaky 的诚实边界；重跑检测列未来工作 | FlakyGuard ✅arXiv 2511.14002 |
| 4 可追溯 | 每条缺陷要能回答"哪条需求、谁批的、什么证据" | RTM+六要素+审计台账+expected_basis | Gotel 1994 ✅ |
| 5 风险分级 | 不是所有模块平等——复杂度/变更频率驱动优先级 | W4 radon 复杂度→plan 优先级（P1 新增） | McCabe ✅ |
| 6 防造假 | AI 生成时代的新维度：测试会"迁就"实现（overfitting） | 证人冻结/预期来源/双闸——本课题差异化卖点 | 2511.16858 ✅、2412.14137 ✅ |
| 7 规模治理 | 选择性回归/隔离/去抖是工程化后半场 | 每轮全量重跑的诚实边界；testmon/TIA 列未来工作 | Yoo&Harman ✅、pytest-testmon ✅工具 |

方法论整体参照《Software Engineering at Google》（Winters 等，O'Reilly 2020，书）：测试尺寸分级、flaky 治理、"测试是代码"的维护哲学——大厂维度的一句话出处。

## 8. 与实验设计的衔接（RQ 与消融开关）

- 现有 V 开关矩阵（V1-V6）天然承接方法组合消融：每个新方法一个开关（B4/B6/B8/B9 各一），指标沿用 recall/extra_suspect/token/时长——**"哪种方法组合在每 token 成本下检出率最高"就是方法组合实验的研究问题**，与 experiment-design.md 的 RQ 框架同构。
- 模板通道 vs 自由生成通道 = 新对照格（防示例污染见 §5.4）。
- 优先级：论文主线实验仍以已完成的 E1-E5+X 格为准；方法组合消融列为**扩展实验**（有余力做 B4 状态迁移与 B8 蜕变两个 P1 新法的开关对照即可，B6/B9 只写设计不实现）。
