# 任务卡-C：并发容量实验（决择单 #2，2026-11-09）

> 用户问题原话："一次性大概进行三个大型项目的运行"。本卡把"能扛几路并发"从推测变成实测数据，供论文"容量边界/局限"节使用。
> 成本控制：**主跑用本地模型（qwen3-4b-inst-test，零成本）**，DeepSeek 档仅作可选对照（余额允许时一格即可）。
> 纪律：不碰生产库（tmp 库或独立端口）；每格结果 JSON 留档 data/reports/concurrency/；完成打勾回写。

## 0. 前置（已核实）

- 系统天然一任务一容器（mta-run-{tid}，1 核 1GB 限额）；容器热运行 0.8s；
- LLM 侧本地模型 ~16 tok/s、无并发限制；DeepSeek 档有 API 限流；
- exec_queue 为单 worker 串行——**本实验不改它**，直接并发下发多任务（各任务独立线程），观察的是"系统现状下的并发行为"，这正是论文要的"当前架构容量边界"。

## 1. 实验设计

1. **被测对象**：3 个真实 demo 项目（data/demo/ 下选：场景A python / js-calc / go-ver-gate——覆盖三种工具链；"大型项目"用 questionforge 本地路径可作一格，标注其体量）；
2. **并发梯度**：N ∈ {1, 3, 5}（本地模型档）；N=3 时三个项目同时下发；
3. **因变量**（每任务）：端到端耗时、各阶段耗时（skill 台账 duration_ms 已有）、LLM 调用次数与 token、终态 verdict、失败归因分布；
4. **系统级**：宿主 CPU/内存采样（psutil 或 docker stats 轮询 5s）、容器峰值并发数、SQLite 写锁等待（busy_timeout 触发日志）；
5. **对照变量**：本地模型 vs DeepSeek（可选一格 N=3）。

## 2. 诚实边界（预注册，写进论文）

- 单机 Windows 宿主；项目为中小型 demo（<3k 行）；n=1~3 每格（耗时类指标报均值±离散度，检出类不下结论）；
- 本地模型速度（~16 tok/s）会拉长端到端耗时——并发容量结论**分容器层与 LLM 层两条线陈述**，不合并成一个数字。

## 3. 实现要点

- `scripts/run_concurrency_probe.py`：按梯度建任务→确认→并发下发（threading）→轮询至终态→采样宿主资源→输出 JSON+md 摘要表；
- 资源采样：5s 间隔记录 docker stats 快照与宿主内存，跑完画折线（matplotlib 已有）；
- 不改任何生产代码；LLM 档切换走既有 profile 机制（local 档直接用现 profile，deepseek 档临时切回再还原——或双 Ollama 起第二模型，取简）。

## 5. 边界（不做）

不改 exec_queue 为多 worker（那是第一段演进，见 docs/高并发演进路线设计）；不做压力压测；不引入 psutil 新依赖时可用 docker stats + wmic 替代（实现时取简）。
