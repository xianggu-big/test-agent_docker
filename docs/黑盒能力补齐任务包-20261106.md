# 黑盒能力补齐任务包（2026-11-06，白盒/黑盒规划讨论落地的正式任务队列）

> 定位：**黑盒能力层建设**。与 E10 实验并行，不占用 E10 波次窗口（本包为确定性工程开发，无 LLM 跑数压力）。
> 背景讨论结论（2026-11-06 会话）：白盒侧语言/工具链/A-B-C 分档已定稿（见《多语言测试工具链与LLM替代分档-20261106.docx》）；黑盒侧盘点出五个缺口：日志（部分）、DB 验证（半个）、UI（无）、gRPC（无）、抓包（无）。
> 执行顺序：**阶段 1（日志）→ 阶段 2（DB）→ 阶段 3（UI）→ 阶段 4（gRPC）→ 阶段 5（抓包，可降级为边界声明）**。

## 0. 设计纪律：语言差异如何规范化（先于一切开发拍板）

**结论：黑盒测试的核心逻辑与被测语言无关，禁止按语言写差异化 prompt。**

- 黑盒只看输入/输出（HTTP、DB、UI、日志），不看源码——`POST /api/order` 打到 Java 服务还是 Go 服务，黑盒层面完全一样。用例设计、请求构造、断言验证、场景编排四层全部语言无关、prompt 复用。
- 语言真实差异只存在于两层，且**都被确定性代码吸收，不进 prompt 经验**：
  1. **服务启动层（recipe）**：`uvicorn` / `java -jar` / `go run` / `npm start` 各不同——由 stack_detect 探测 + recipe 白名单配置解决（已有机制，按语言补 recipe 模板即可）；
  2. **可观测性解析层**：Python Traceback / Go panic / Java 堆栈 / Node unhandled rejection 格式各异——由确定性解析正则按语言分支吸收，LLM 只消费解析后的结构化证据（错误类/行号/消息）。
- prompt 里唯一允许出现语言信息的形式 = **事实注入**：把探测到的确定事实（如"该服务为 Spring Boot，错误响应遵循 RFC 7807 JSON 格式"）作为只读上下文注入。**禁止**写"Java 容易出 X 类问题、Go 容易出 Y 类问题"这类经验性 prompt——那是 vibes，违反"证据必须确定性"红线。
- 唯一例外：UI 场景注入的是 DOM 快照事实、gRPC 注入的是 proto 定义事实——同属事实注入，不属经验规则。

## 统一五步模子（五个缺口共用，新能力一律照此接入）

```
① 采集层（确定性）    真实执行工具：sidecar 容器 / 日志分流 / grpcurl / Playwright / mitmproxy
② 提取层（确定性）    从被测项目提取"真值清单"：schema / proto 定义 / DOM 快照 / 日志文件 / 迁移 SQL
③ 生成层（LLM 受闸）  LLM 只能引用真值清单构造方案，虚构条目整案剔除并留痕
④ 执行层（确定性）    原工具执行，结果结构化落表（绝不让 LLM 直接判定）
⑤ 落库层             证据原文可追溯（日志行号/HAR 条目/截图/trace），LLM 叙述必须引用
```

## 阶段 1 · 运行时日志分流与 log_analyze（P1，约 2 天）

- **现状**：case_results 只解析 pytest/jest 测试报告输出；被测应用运行时 stdout/stderr 无独立采集，归因三闸（环境闸/flaky 判定）缺日志地基。
- **方案**：
  1. runner.py 执行时分流被测服务进程与测试进程输出：容器内重定向 `> /workspace/logs/app_r<N>.log` + `docker logs` 兜底，按任务/轮次落 `data/workspaces/<tid>/logs/`；
  2. 确定性先行：错误行正则统计（Traceback/ERROR/WARN 计数、首次出现行号），按语言分支解析（Python Traceback / Java 堆栈 / Go panic / Node rejection），落新表 `app_logs`；
  3. 新 skill `log_analyze`：LLM 只做摘要与异常解释，必须引用行号，日志原文落库可追溯（与 defect_analysis 同纪律）；
  4. API 加 `GET /api/tasks/{tid}/logs?round=N`。
- **前置调研**：无重型开源依赖（纯工程活）；参考 pytest caplog 机制思路。
- **验收**：真机跑一个 L2 冒烟任务 → app_logs 有按轮次分档的应用日志行 → 故意埋的环境错误（如端口占用）能被正则命中且 log_analyze 叙述引用了真实行号。
- **验收记录 ✅（2026-11-06，zcode 闲时开发）**：`python scripts/smoke_applogs.py` 真机两臂全 PASS（真 Docker L2 leg + 真 LLM）——A 埋错臂（data/demo/L2场景-applogs，/boom 抛 RuntimeError）：完整 L2 leg 判「契约违背 1 处」证人语义正确，app_logs 3 行入库（error_log/python_traceback/python_exception 三 kind），宿主快照 65 行，log_analyze 摘要引用真实行号 7/8/64（citations_ok=True，证据不足处如实标注）；B 端口占用臂（data/demo/L2场景-applogs-portbind）：provision fail-fast 路径日志分流落库，`ERROR: [Errno 98] bind` 被正则命中。证据=data/reports/applogs_accept/accept_20261106-193425.json；测试矩阵 24 条单测全绿（tests/test_app_logs.py 四语言正负例+引用闸负例+路径拼接+幂等 / tests/test_app_logs_api.py 鉴权过滤 404）；表数契约 27→28 同步（schema/test_db/module_check/README）；回归 630 过 1 跳 / 守卫 138 OK。实现偏差两处已记录：容器路径用 /work/logs/app.log（仓库 /work 约定，任务卡写作 /workspace）；服务启动失败也分流落库（任务卡只写执行轮，环境证据价值更高）。

## 阶段 2 · DB 验证补齐：sidecar 建库 + db_assert（P1，约 3 天）

- **现状**：db_probe 仅 sqlite 家族真实建库+灌种子；MySQL/Postgres 只做驱动识别，不建库不验证（"半个"）。
- **方案**：
  1. sandbox runner 增加 sidecar 容器编排：起官方 `mariadb`/`postgres` 精简镜像 → 等端口就绪 → 执行被测项目迁移/种子 SQL → 被测容器经 docker network 连接；recipe 增加 `db_services` 声明段；
  2. 新 skill `db_assert`：LLM 生成验证 SQL（"下单后 orders 表应新增一行…"）→ **只读闸**（sqlglot 解析 AST，白名单仅 SELECT/SHOW；出现 UPDATE/DELETE/DROP 整案剔除留痕）→ 容器内执行 → 结构化结果落库。
- **前置调研**：**Testcontainers**（testcontainers-python）——决定引入其容器编排模式还是抄模式自实现（按项目纪律先调研后动手，结论写回本卡）。
- **验收**：真机跑一个含 MySQL 的 demo 项目 → sidecar 建库成功 → db_assert 的只读 SQL 验证通过/失败各一例，越权写 SQL 被闸门剔除留痕。

## 阶段 3 · UI 黑盒：Playwright 接入（P2，约 3.5 天）

- **现状**：无任何 UI 测试能力（未接 Playwright/Selenium）。
- **方案**：
  1. 镜像：`mcr.microsoft.com/playwright/python` 官方镜像（含 headless chromium），注册进 IMAGE_BUILD_CTX；
  2. 真值清单：执行前采集页面可达性树/DOM 快照落盘——UI 版"端点清单"；
  3. LLM 生成操作序列（goto/click/fill/expect），**铁律：每步 selector 必须引用快照中真实存在的元素**，虚构元素整案剔除（同 scenario_gen 端点铁律）；
  4. 确定性执行 pytest+playwright，每步截图 + trace.zip 落库；失败证据进 defect_handoff 缺陷报告单。
- **前置调研**：Playwright 官方 trace viewer 机制；DOM 快照用 accessibility tree（稳定优于裸 selector）。
- **验收**：对内置 demo 前端页面生成 3 条场景 → 全部真实执行 → 截图/trace 落库 → 埋一个按钮失效缺陷能被场景命中并出缺陷报告单。

## 阶段 4 · gRPC 接口测试（P2，约 2 天）

- **现状**：黑盒仅覆盖 HTTP REST，无 gRPC。
- **方案**：完全复用 HTTP 模式，只换真值清单来源——
  1. 端点提取 D4 降级链加一级：解析 .proto 文件（service/rpc/message 定义）；
  2. LLM 按 proto message 构造请求 JSON，**闸门：service+method 必须命中 proto 清单**；
  3. 执行：容器预装 grpcurl（fullstorydev/grpcurl，业界标准），或生成 grpcio client 代码；被测服务开 reflection 时可免 proto。
- **前置调研**：grpcurl 的 `-import-path`/`-proto`/reflection 三种调用模式实测。
- **验收**：含 .proto 的 demo 服务 → proto 清单提取正确 → 合法 RPC 调用通过 + 虚构 method 被闸门剔除留痕。

## 阶段 5 · 抓包（P3，约 2.5 天，可降级为边界声明）

- **现状**：无。
- **方案**：不上 tcpdump/pcap（要 root、LLM 读 pcap 不友好）。mitmproxy sidecar 作被测容器 egress 代理 → 流量落 HAR（标准结构化 JSON）→ 确定性解析入库 → LLM 分析引用具体条目。mitmproxy 原生支持 HTTP/HTTPS/HTTP2。
- **诚实边界**：对被测项目外部第三方依赖的流量观测不承诺——若投入产出比不足，本阶段降级为文档边界声明，不视为缺口。
- **验收（若实施）**：被测服务调用外部 HTTP API 的流量被 HAR 完整记录且条目可被报告引用。

## 护栏（全程有效）

- 不动实验数字/论文结论/已有测试断言；不跑真实任务链；不写 data/test_agent.db 真实库（开发期用临时库）。
- 每阶段独立分支开发，先立失败测试/确定性脚本再实现，保留"修复前失败、修复后通过"证据。
- 新增 skill 一律经 SkillRegistry 注册（schema/风险分级/超时/审计台账），新表进 layer5-data-schema.sql 单一真源。
- 阶段 2/3/5 涉及新镜像，构建后跑 `python scripts/build_images.py --only <tag>` 自检。

## 测试矩阵（每阶段的自动化测试清单，与【验收】真机条目并行生效）

> 分层原则（项目既有纪律）：单测锁闸门与解析器（改坏实现必须变红）、集成测 skill 注册与落库
> 幂等、【验收】条目管真机端到端。三者缺一不可；所有新测试进 pytest 全量，module_check 守卫
> 契约同步更新。

| 阶段 | 必备单测（正例+负例） | fixture/集成 |
|---|---|---|
| 1 日志 | 四语言错误行正则各≥1正1负（Python Traceback / Java 堆栈 / Go panic / Node rejection）；log_analyze 引用不存在行号 → 必须失败（防 vibes 叙述） | 日志分流路径拼接；app_logs 落库幂等（重跑不重复计行） |
| 2 DB | sqlglot 只读闸正负例矩阵（SELECT/SHOW 过；UPDATE/DELETE/DROP/`;` 注入剔除并留痕）；sidecar 配置解析（db_services 段缺字段必报错） | db_assert 结果落库幂等；sidecar 端口就绪等待的超时分支 |
| 3 UI | selector 真值闸负例（虚构元素整案剔除并留痕）；操作序列 schema 校验（未知动作类型拒绝） | 内置最小静态 HTML 快照 fixture（不依赖网络）；截图/trace 落盘路径校验 |
| 4 gRPC | proto 解析正负例（service/rpc/message 清单提取）；闸门负例（虚构 method 剔除留痕；合法 method 放行） | 内置最小 .proto fixture；grpcurl 调用参数拼装单测（不起真服务） |
| 5 抓包 | HAR 解析（标准 HAR fixture → 结构化条目） | mitmproxy 配置生成单测（不起真代理） |

- **实现顺序纪律**：负例测试先于实现写（失败测试先行，护栏明文要求）；闸门类功能的负例
  （注入/越权/虚构）优先级最高——它们是"防造假"卖点的直接证据。
- **验收关系**：单测不替代【验收】真机条目；真机验收通过后，对应单测必须留在测试套件里
  永久锁机制。
