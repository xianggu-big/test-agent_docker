## 任务 14｜数据库选型（报告）
现状：**SQLite（WAL 模式）单文件 27 表**，标准库驱动零依赖。
- **本地运行：SQLite 是正确选择**——单机、单写者、零运维；WAL 下读写并发足够本项目（实测多任务并发无锁死，busy_timeout 5s 兜底）。不适合的是多进程写-intensive 场景（我们用后台线程单进程写，规避了）。
- **云端部署：PostgreSQL**——行级锁/并发写、JSONB（defects/summary/gwt 等 JSON 列直接受益）、物化视图（聚合报表）、生态成熟（RDS/Cloud SQL 托管）。迁移成本：SQL 方言差异点=datetime('now')→now()、json_extract→JSON 操作符、executescript 建库→迁移工具（Alembic）。**不建议 MySQL**（JSON 函数弱于 PG）；更不建议 MongoDB（关系/事务/RTM 外键语义不匹配）。
- 论文可写：数据层抽象在 `store/db.py` 单点（get_conn），换 PG 只动这一层。

## 任务 15｜黑盒白盒固有方法还缺什么（调研）
已实现：等价类/边界值/判定表/语句分支覆盖/错误推测（五法骨架）+状态迁移/蜕变/PBT/条件缺口回灌/变异标定/复杂度热点/覆盖回灌。**缺的、有新意的方向**（按性价比排序）：
1. **组合测试（ pairwise / CIT ）**——完全缺席；n 参数组合爆炸的确定性降噪，工具成熟（PICOSAT/ACTS），实现约 1 天，消融格好做。
2. **基于历史缺陷的突变算子加权**（mutation slope）——现有变异标定是均匀算子；按 radon 热点/缺陷密度加权算子是空白点。
3. **断言自动强化**（assertion amplification，EvoSuite 思路）——对"通过但断言弱"的用例做回归断言捕获，区别于现有"静态弱断言剔除"。
4. **输入依赖链分析**（数据流覆盖 def-use）——设计文档里列了边界条目，白盒轨唯一没落的标准覆盖族。
5. **LLM 不确定性感知生成**（self-consistency：同 prompt n 次采样取交集用例）——与现有单次生成互补，直接可做消融。
论文角度：1/2 是"组合创新"最稳（空白点+工具成熟），5 最贴 LLM 主题。

## 任务 16｜开源对比与避免造轮子（调研）
权威底稿：`docs/oss-testing-pipeline-comparison.md`（8 项目×8 维度）。本轮 GitHub 复核要点：
- **TestGen-LLM/Meta**（单测修复思路）→ 我们已有 prune/rewrite/证人生成物修复，无重复轮子。
- **CoverUp**（覆盖回灌 pytest）→ 已实现同思想（V4 缺口回灌）。
- **Pynguin**（随机+搜索生成）→ 与 LLM 生成正交；可作未来"混合基线"对比项，不建议引入（重依赖）。
- **EvoSuite**（Java 全自动）→ Java 链路未接，Tier3 兜底已覆盖演示面；引 EvoSuite 是"接 Java"的最省路径（容器里跑 jar 而非自己写 JUnit 生成器）——**建议列为 Java Tier2 的实现捷径**。
- **Schemathesis/Keploy**（API 层）→ L2 集成轨已有自研契约生成；Keploy 流量录制思想已在 A 源借鉴。
- **真空缺**：多语言编排层（语言→镜像→生成器→解析器的注册表化）。当前 hardcode 在 analyze/gen_tests 的分支里；若加第 3 门执行语言（Java）建议先做"语言适配器注册表"再写生成器，避免第三份 if-else。
结论：**没有需要重造的轮子；最值得借的是 EvoSuite 路径与适配器注册表架构**。

## 任务 17｜Redis 对本项目的设想（报告）
四个可落地点（按价值排序）：
1. **执行队列**（已落库 exec_queue 表，SQLite 轮询实现）→ Redis List/BullMQ 可换成真发布订阅，worker 多进程横向扩。当前单机单 worker 够用，**上云多实例时才有必要**。
2. **实时日志流**：agent_messages 现在靠 2-3s 轮询；Redis Pub/Sub + SSE 可推实时（>5 任务并发时轮询压力可见下降）。
3. **token/预算停车线计数器**：llm_calls 现查库；Redis INCR 原子计数+TTL 天然适合"每任务/每天预算"。
4. **注册表级缓存**：镜像存在性/环境自检结果（preflight）缓存 60s，减少 Docker API 探测。
结论：**本地单机不需要 Redis**（SQLite+线程已覆盖，引入=多一个运维组件）；**云端部署时 1/2 两点是真实收益**。不建议为"看起来分布式"而引入。

## 任务 18｜OCR/LLM 视觉"截图指哪测哪"（评估）
**值得做，且成本比想象低**：用户在需求卡旁贴截图 → 多模态 LLM（GLM-4V/Qwen-VL 免费额度大）直接输出"截图中的表单/按钮/流程"结构化描述 → 并入需求文本走现有 plan 管线。**不需要自建 OCR**（现代 VLM 的 OCR 能力已够）。工程落点：前端需求卡加图片上传 → 新表 task_attachments → 需求组装时拼"用户标注区域描述"。风险：截图≠可测行为规格，需在提示词里强制"从截图提取行为线索，不臆造功能"；预计 1-1.5 天。建议列为 v2 演示亮点（答辩现场截图指测，观感极强）。
