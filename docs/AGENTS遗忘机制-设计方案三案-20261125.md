# AGENTS.md 遗忘机制·设计方案三案（2026-11-25）

> **状态**：待用户选案，未实施。本文只做设计。
> **需求原话**：超过 N 天的条目自动压缩整理成显而易见的标题（带索引位置）；建一个遗忘池存放被压缩的原句；某天突然用到时原文仍可取回。
> **关联**：全局 `~/.zcode/AGENTS.md` 的「抗压缩失忆协议」；现有钩子脚本 `~/.zcode/cli/hooks/progress.py`。

## 0. 一屏结论

1. **遗忘已经在发生，只是不受控。** 项目 `AGENTS.md` 现在 86,045 字符，加载器只装得下约 57,700 字符——最老的三分之一每次会话都被直接丢掉，没有索引，也没有池。
2. **天数要拆成两个数，15 天不能直接当"全文保留期"。** 按现在的写法，15 天的全文就是 4.5 万字符。建议：**全文 7 天（另加体积闸 25,000 字符）、标题索引 30 天、遗忘池永久**。数据上 15 天覆盖 97% 的回看，所以 15 天适合做标题层的下限。
3. **三个方案**：A 机械轮转（脚本切标题，零 token，一小时做完）；B 睡眠整理（AI 按主题合并，索引最好读）；C 分层热度（A + 自动召回 + 再加热，"突然用到"全自动）。
4. **推荐**：先上 A 止血并建好池和索引，运行两周后按需要加 C 的自动召回；B 留给大阶段收尾时手动触发。三案共用同一个池格式，可以叠加。

## 3. 天数怎么定

天数不是一个拍脑袋的常量，由两个约束夹出来：

**约束一：回看距离决定"至少留多久"。** 工作话题几乎都在最近一次记录的 10 天内被再次提起，15 天覆盖 97%，最大 21 天。

**约束二：体积预算决定"最多留多久"。** 全文层每轮请求都要重读，设预算 25,000 字符。保留天数 = 预算 ÷ 日均增量，而日均增量取决于每条写多长：

| 每条平均长度 | 日均新增 | 7 天 | 15 天 | 30 天 |
|---|---|---|---|---|
| 现状（约 790 字符） | 约 3,300 | 23k | 50k | 99k |
| 400 字符 | 约 1,700 | 12k | 25k | 50k |
| 200 字符（你的现行规定） | 约 840 | 6k | 13k | 25k |

所以结论分两种情况：

- **维持现在的写法**：全文保留期只能是 7 天左右，而且重活周（像 11-20 到 11-23）还得靠体积闸提前下沉。
- **执行"每条 ≤ 200 字符"的写入口径**：15 天全文只要 1.3 万字符，完全放得下，30 天也刚够预算。

**建议的三层数字**

| 层 | 放在哪 | 保留多久 | 理由 |
|---|---|---|---|
| 全文 | `AGENTS.md` 顶部 | ≤ 7 天，且总量 ≤ 25,000 字符 | 覆盖 80% 的回看；体积闸兜住高峰周 |
| 标题索引 | `AGENTS.md` 底部「遗忘索引」 | 30 天 | 覆盖观测到的全部回看；每条约 40 字符，30 天约 5,000 字符 |
| 遗忘池 | `docs/遗忘池/` | 永久 | 你的要求：原文可取回 |

**自适应**：脚本每月重算一次"全文天数 = 25,000 ÷ 近 14 天日均字符"，夹在 3 到 15 之间，并打印出来。写法变短，保留期自动变长。

**体积闸的规则**：全文超过 25,000 字符时，从最旧的未钉住条目开始继续下沉，直到达标；2 天内的新条目不动，实在降不下来就报警而不是硬删。

## 4. 三案共用的底座

无论选哪个方案，下面这些是一样的。

**条目识别**。状态行的现成格式是 `- **<emoji> <标题>（<日期…>）**：<正文>`。脚本取行内第一个 `20\d\d-\d\d-\d\d` 当日期，取第一个 `（20` 之前的部分当标题。解析不出日期的行永不自动归档，只报出来。

**钉住，永不自动遗忘**：`🔴` 开头的硬规则；标题里带 `[钉]` 的条目。`▶️` 不自动钉（多数是过期的"进行中"标记）——现有的两条长期指令（"会话执行指令"等）在首次迁移时手工加 `[钉]`。

**遗忘池**（每个项目一份，进 git，误操作可回滚）：

```
docs/遗忘池/
  pool-2026-11.md      # 按月一个文件，只追加
  INDEX.md             # 总索引：ID · 日期 · 标题 · 所在文件
  archive.log          # 每次归档的记录
```

池里的每一条：

```
<a id="F-1120-07"></a>
## F-1120-07 · 2026-11-20 · ✅ G7-G10 真机格补跑收官
<!-- archived=2026-11-28 from=AGENTS.md chars=1204 sha256=… -->
- **✅ G7-G10 真机格补跑收官（2026-11-20 晚，……）**：……（原句整行，逐字节）……
```

- **ID** 是 `F-月日-序号`，按原条目的日期编号，短、可排序、可 grep。`forget.py --recall F-1120-07` 直接打印原句。
- **`--verify`** 逐条重算 sha256，确认原文没被改动。
- 池文件按月约 100–150 KB，**永远不要整文件读进上下文**，只按 ID 取。

**留在 `AGENTS.md` 里的索引行**：`- F-1120-07 G7-G10 真机格补跑收官`。索引区顶部写一句怎么取回。

**复活**：某条被用到、需要常驻时，把原句**复制**回顶部作为新条目并注明"（复活自 F-1120-07）"；池里那份不动。

**不进池的东西**：全局 `~/.zcode/AGENTS.md`（规则本身）；记忆目录（`MEMORY.md` 及其主题文件）。池管事件流水，记忆管提炼后的事实，两边互不自动写入。

**配套的写入口径**：标题要当成"将来的索引"来写——含对象和结果，日期和 commit 号放正文。好标题的例子：`✅ G8 竞态格 v3 PASS——总编排收官（2026-11-24……）`；差的例子：`▶️ 2026-11-04 02:00 压缩防线`。

**首次迁移**：第一次运行会一次性归档几十条，文件从 86,000 字符降到 2 万多。那些现在就在截断线以下、本来已经看不见的条目，由此重新获得一个索引。

**接法**：和 `progress.py` 一样，一个脚本挂多个事件，stdin 读事件 JSON，`ZCODE_PROJECT_DIR` 定位项目，`additionalContext` 注入提示。ZCode 一共七个钩子事件，没有压缩前事件；`SessionStart` 只在启动和恢复时触发。所以"自动"的含义是**每次开新会话时整理**，不是"压缩时整理"。

**安全**：临时文件写完再替换；检测到合并冲突标记就跳过；改写前留最近 3 份备份；提供 dry-run。

## 5. 方案 A：机械轮转

**一句话**：一条原文对应一个标题，脚本到点就搬，不靠 AI。

- **触发**：`SessionStart` 钩子（启动、恢复时各一次）+ 手动命令。
- **动作**：时间闸（超过 7 天且未钉）→ 入池 → 标题进「遗忘索引」。索引行超过 30 天的，移到 `INDEX.md`，`AGENTS.md` 里留一行指针。
- **标题来源**：现有的加粗标题去掉日期括号，超过 60 字符截断。这个项目里每条本来就有加粗标题，所以不需要 AI 来"总结"。
- **注入**：有动作时注入一行 `[遗忘] 归档 5 条（F-1105-01…05）；AGENTS.md 现 23,400 字符 / 42 条`。
- **召回**：手动。`--recall`，或让 AI 在池里 grep `F-`。

| | |
|---|---|
| 优点 | 确定性；零 token；原文逐字节；大约一小时能做完；立刻解决截断 |
| 代价 | 相关条目不合并（G8 一件事会留 6 条标题）；不识别"已被取代"，旧的 FAIL 标题仍留在索引里，只能靠图标和日期区分；召回靠人 |
| 文件缩到 | 约 2 万–2.5 万字符 |

## 6. 方案 B：睡眠整理

**一句话**：AI 按主题把多条原文合成一条能直接读懂的记忆行。

- **触发**：①你说"收尾 / 总结 / 先停一下"时，如果超期条目 ≥ 8 条或文件超 25,000 字符，就顺手整理一轮；②兜底：每周一次闲时任务当"记忆整理员"。
- **流程**：
  1. 先跑方案 A 的机械下沉；
  2. AI 读本轮入池的原句和现有索引，按主题聚簇；
  3. 每簇写一条 ≤ 200 字符的记忆行：现状 + 原因 + 池 ID；
  4. 标出"已被取代"的链条，索引里只留终态；
  5. 条目里的"坑 / 约束"提议进记忆目录或 `项目经验.md`——只提议，不自动写；
  6. 产出整理记录，单独一个 commit。
- **索引变成主题索引**，例如：`- G8 竞态格：终态 PASS（11-24 v3），窗口在 0.5–1.0 秒；v1/v2 两败是占位格不健康 → F-1121-02, F-1123-04, F-1124-01`。
- **防错**：AI 只能写"引用池 ID 的索引行"，不许改池；前两轮先出 dry-run 差异给你看；行数不降反升就回滚。

| | |
|---|---|
| 优点 | 索引质量最高；文件最小（能真正做到 ≤ 30 行）；消除互相矛盾的历史；能顺手提炼坑 |
| 代价 | 花 token 和时间（闲时免费档可用）；非确定性；摘要可能失真（有 dry-run 和回滚兜底）；依赖触发纪律 |
| 文件缩到 | 1 万字符以内 |

## 7. 方案 C：分层热度 + 自动召回

**一句话**：方案 A 的全部，再加"你一开口，相关的旧原文自动送回来"和"被用过的条目不容易被忘掉"。

1. **自动召回**（`UserPromptSubmit` 钩子）。把你的提问分词（英文词 ≥ 3 字符、`F-xxxx-xx`、任务号、中文词组），去匹配索引标题和总索引。命中前 3 条，就把原句通过 `additionalContext` 注入，封顶 2,500 字符，格式是 `[自动召回] F-1120-07 G7-G10 真机格补跑收官：<原句>`。你不用开口让它去翻池。
2. **热度记录**。命中、注入、AI 主动 `--touch`，都往 `heat.jsonl` 追加一行（ID、时间、来源）。
3. **再加热**。近 3 天被用过的条目，索引行重新计龄，标注"最近用到 11-25"，不会被时间闸冲走；被用超过 2 个不同日子的，以"复活行"（标题 + 一句话 + ID）升回全文层。全文不回全文层，保护体积。
4. **自适应天数**：每月按"预算 ÷ 近 14 天日均"重算。

| | |
|---|---|
| 优点 | 最接近人脑记忆；"突然用到"全自动；能撑到明年 2 月中期检查乃至答辩；老化和召回本身零 token |
| 代价 | 工程量最大（多两个钩子、匹配器、热度日志）；误命中会注入无关内容（靠阈值、封顶、开关压）；多两个参数 |
| 文件缩到 | 约 2 万–2.5 万字符 |

## 8. 对比与推荐

| | A 机械轮转 | B 睡眠整理 | C 分层热度 |
|---|---|---|---|
| 谁来压缩 | 脚本，切标题 | AI，按主题合并 | 脚本切标题（可叠加 B） |
| 一条标题对应 | 一条原文 | 一个主题的多条原文 | 一条原文 |
| 触发 | 会话启动 / 恢复 | 收尾口令 / 每周闲时 | 启动钩子 + 每次提问钩子 |
| 召回 | 手动 | 手动 | 自动注入 + 手动 |
| 一次性投入 | 约 1–2 小时，零 token | 协议 2–3 小时，每轮 10–30 分钟 | 约半天 |
| 误伤风险 | 极低（只搬不改） | 中（有 dry-run 和回滚） | 低到中（误命中） |
| 适合 | 想马上止血 | 想让索引一眼读懂 | 想让"突然用到"自动发生 |

**推荐路线**：A → C → B。

1. 先上 A。它满足你的全部四条要求（自动压缩、标题带索引、池存原句、随时取回），而且是另外两案的地基。
2. 跑两周。A 顺手记录每次手动召回，你就能看到"到底多常翻旧账"。
3. 翻得勤就加 C 的自动召回；想在一次大阶段收尾时把历史读薄，就用 B 跑一轮。

如果只想选一个一步到位，选 C。

## 10. 未核实与风险
