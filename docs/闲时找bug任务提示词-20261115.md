# 闲时任务提示词：全仓找 Bug → 修复 → 回归 循环（2026-11-15）

> 用法：把下方分隔线内全文复制进 ZCode 闲时任务的初始输入框。
> 设计原则：自足（不依赖本会话上下文）、每轮结束都是可停状态、零 API 成本、不碰真实库。

## 任务：对 test_agent 全仓做"找 Bug → 修复 → 回归测试"循环，直到收敛

你是本仓库的无人值守质量会话。任务 = 按测试流程对全部代码做静态扫描 + 动态测试 + 逻辑审查，
找出 bug/逻辑漏洞/边界缺陷，逐个修复并配回归测试，然后进入下一轮，直到收敛。
开工前先读项目根 `AGENTS.md`（很长，重点读顶部 10 条与「当前状态」节）——它是唯一权威状态源。

### 红线（违反任何一条=任务失败）

1. **零 API 成本**：禁止调用 DeepSeek/任何付费 API（`DEEPSEEK_API_KEY` 存在也不许用）。所有验证走
   fake-LLM（tests/ 有大量先例）或无 Key 诚实降级路径。不要跑 E9/E10/G 等实验驱动器。
2. **真实库只读**：`data/test_agent.db` 一行都不许写。所有新测试一律 tmp 库
   （monkeypatch `config.DB_PATH`；fixture seed 后必须 `conn.commit()`——否则撞 database is locked）。
3. **禁止起服务跑冒烟**：不要对 8000/8010 端口起 uvicorn 跑 api_smoke/api_adversarial
   （会写生产库+可能与并行会话的常驻服务冲突）。接口层验证用 `fastapi.testclient.TestClient` +
   tmp 库模式（tests/test_charts_api.py 等是范本）。`MTA_E2E=1` 不要开（保持 e2e_slow skip）。
4. **git 纪律**：每修复一个 bug 即 commit（路径范围化 `git add <具体文件>`，**禁止 `add -A`**；
   可能有并行会话同仓工作，不碰它未提交的文件）；提交信息中文说明修了什么+怎么验证；**不 push**。
5. **写代码一律用 Write/Edit 工具**，禁止 bash heredoc 内嵌 Python（本项目转义坑累计 10+ 次）。
6. **只修不造**：禁止重构、禁止加新功能、禁止改架构、禁止"顺手优化"。发现可疑但无法证实的，
   记入报告"存疑清单"，不许动代码。
7. **实验口径冻结区不动**：config.py 的实验开关与预算参数、已定稿记账口径
   （如 `log_llm_call` 的 phase 字面量）、docs/ 论文草稿、data/ 下实验驱动器与语料。
8. 开工先 `git status`：若工作树脏（有未提交改动），列出脏文件、跳过涉及这些文件的区域，在报告里说明。

### 开工检查（第一件事）

1. 读 `AGENTS.md` 顶部；2. `git status` + `git log --oneline -3`；3. **实测基线**（不信文档数字，自己跑）：
   `python -m pytest -q`（预期 1042 passed 1 skipped 量级）与 `python scripts/module_check.py`（预期 138 OK）。
   基线若不是绿的：停下来，把失败原样写进报告，只允许修"让基线变绿"这一件事。

### 循环流程（无轮次上限，循环直到收敛；每轮结束必须回到"全绿+已提交+进度已固化"的可停状态）

每轮 = 【发现】→【分诊证实】→【TDD 修复】→【全量回归】→【commit + 固化】：

1. **发现——多维度发散，宁多勿漏**（此阶段只广撒网不设准入门槛，可疑就记下来；收紧发生在下一环节）。
   第一循环把下列维度各扫一遍，之后每轮至少带 1 个上轮没用过的新视角；同一维度两轮之间必须有增量
   （新探针、新模块面、或前轮修复引入的改动面）。鼓励自创维度：
   - R1 结构探针：扩展 `data/reports/static_scan_20261115/scan.py` 的六类模式
     （State 字段未声明/条件边 mapping/skill 注册键/闭包捕获 conn/make_chat phase/幂等表裸 INSERT）+ 新探针；
   - R2 异常路径与边界：except 分支降级语义、None/空集合传播、除零/下标越界/编码、
     f-string 与 JSON 解析容错、极端输入（超长/空串/非法 UTF/巨型数字）；
   - R3 并发与资源：线程池（SkillRegistry._pool）下连接生命周期、delete-first 幂等、
     文件句柄/容器清理路径、超时与取消语义（future 超时后任务仍在跑=已知语义，勿当新 bug）；
   - R4 口径一致性：图节点 return vs State 声明、记账 phase vs 路由 phase、
     状态机枚举 vs set_status 调用点、API 返回字段 vs 前端消费字段、文档承诺 vs 实现；
   - R5 数据正确性：SQL 聚合口径（分母/分子漏项）、JSON 落库→读回往返、排序稳定性、
     浮点比较、时间戳/时区/格式；
   - R6 安全面：SQL 拼接注入点、路径穿越（用户输入拼文件路径）、未转义输出、
     角色守卫漏挂的端点、提示词注入面；
   - R7 失败可恢复性：中途崩溃后的残留状态（半写库/孤儿容器/悬挂队列行）、重跑语义、
     补偿路径缺失、finally 缺失；
   - R8 评测器自省：测试与脚本自身的缺陷（假绿/恒真断言/漏报分母/阅卷器口径）——
     本项目历史实锤过"阅卷器虚高 0.8 作废"，评测器也是被测对象；
   - R9 语义正确性：对照需求与设计文档读代码——实现了但**实现错**的逻辑（不是没实现，是做错）、
     隐含假设失效（参照 docs/LLM隐含假设失败模式清单-20261105.md 的 18+10 类）；
   - R10 自创维度：任何值得扫的角度，报告里注明维度名与发现数。
2. **分诊证实——修复准入门（在这里收紧，发现再多也只修真 bug）**。每个候选过三问，全过才准修：
   - **①是设计偏差吗？** 对照设计真源（见下节优先级链）确认"实现违背了设计意图"，
     而不是"我觉得可以更好"。设计如此=不是 bug（哪怕看起来丑）；无设计依据的改进=存疑清单。
   - **②测试可证实吗？** 必须能写出最小复现（tmp 库/纯函数断言，参照
     `data/reports/static_scan_20261115/verify_phase_bug.py` 的实证风格）并跑出**红**。
     说不出复现路径、或红只在"我假设的调用方式"下出现=不修，记存疑。
   - **③修复会碰冻结区吗？** 改动若触碰实验口径/记账字面量/已发布行为契约/前端依赖字段 →
     移交"未修清单"交用户拍板，不许动手。
   证实不了的写"存疑清单"。已知非 bug 勿报：34 处 except-pass 多为双保险降级设计（2026-11-15 抽验过）；
   裸 INSERT 若同函数有 ON CONFLICT upsert 或属追加台账=合法。
3. **TDD 修复——方向锚定设计，不要改偏**。修复是把实现**拉回设计意图**，不是发明新行为：
   - 设计真源优先级链（冲突时以上位为准）：`AGENTS.md` 已定口径 → docs/ 设计文档
     （vision-and-gaps / experiment-design / 任务卡）→ 既有单测锁定的行为契约 → 代码现状；
   - 修法优先取**同仓既有模式**（如幂等用 ON CONFLICT upsert、降级用诚实留痕），
     禁止为修一个 bug 引入新机制/新依赖/新抽象；
   - 修复若需要"设计上根本没有的行为"才能成立 → 说明你诊断错了，回发现阶段重新定性；
   - 先写回归测试跑**红**（断言失败信息=bug 本体），再修代码跑**绿**；
     一个 bug 一个测试一个 commit。修完立即全量 `python -m pytest -q` 确认无副作用。
   参照范例：evaluate.py 路由 phase 修复（commit 2c0e16a）——发现=静态扫描，证实=tmp 库动态实证，
   修法=对齐 PHASE_GROUPS 设计真源而非发明新路由，红→绿+全量回归。
4. **固化**：每轮结束把「本轮发现 N 条/修复 M 条/存疑 K 条/回归数字/commit 列表」追加写进
   `docs/闲时找bug报告-20261115.md`（开工即建），并同步在 `AGENTS.md` 顶部追加一行状态
   （一行以内、200 字内，格式仿现有条目）——这是唯一能扛上下文压缩的通道，每轮必写。

### 什么算 bug（发现从宽，准入从严）

**发现阶段**（第 1 步）什么都可以报——发散不设限。**修复准入**（第 2 步三问）才是收窄器：
必须同时满足"实现违背设计真源 + 测试可证实红 + 不碰冻结区"才动手。
典型真 bug：会炸任务链的异常、数据错误（记错账/翻倍/丢字段）、幂等破坏、逻辑颠倒、竞态、
资源泄漏、边界崩溃、跨模块口径不一致、评测器自身假绿、测试能证实的错误行为。
**不算**（发现可记但修复准入会拦下）：风格问题、性能微优化、未来工作（AGENTS.md 已列）、
需要真网络/真 LLM 才能验证的假设、文档措辞、无设计依据的"改进机会"。
修不了的（需产品决策/需额度/影响实验口径）如实列"未修清单+原因"交用户拍板。

### 收敛与收尾

- **收敛判据（唯一）**：连续两轮【发现】阶段均零"可证实 bug"，且两轮使用了不同探针/视角
  （防假收敛：上轮没找到≠没有）。除此之外不设轮次上限——一直循环找修直到达标。
- 每轮若发现非零，修完回归提交后直接进入下一轮，不停不等。
- 收尾交付：①报告终稿（每轮发现/修复/证据/未修清单/最终回归数字/收敛判定依据）②AGENTS.md
  顶部一行终态 ③最终 `git log --oneline` 列表。最后再跑一次 `python -m pytest -q` +
  `module_check`，把两个数字原样写进报告——没有新鲜证据不得声称"全部修复"。
- DeepSeek API 防浪费永久有效：无论循环多少轮，验证一律 fake-LLM/tmp 库，一次真实 API 调用都不许发生。
