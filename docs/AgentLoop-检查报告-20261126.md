# AgentLoop 检查报告（2026-11-26）

> **目的**：在把 Agent Loop 长期打开之前，查清 strategy 和 diagnose 两个节点现在到底能不能干好各自的活。
> **方法**：对码当前代码（`文件:行号`）+ 只读查询生产库运行账本（测量批 30 次运行，#2604–2633，提示词 v1）。
> **位置**：检查 → 设计 → 测试 三步的第一步。设计见 `docs/AgentLoop-设计报告-20261126.md`，测试见 `docs/AgentLoop-测试任务报告-20261126.md`。

## 0. 结论先行

1. **两个节点从建立起就在"盲跑"。** 能力把取证的文字写进磁盘文件，只把一行摘要回给决策模型。模型自己写在结论里的话是："证据列表未展示函数体细节，无法据此判定"。这是根因。
2. **所以历次的 PASS 只证明了流程和格式，没证明任务完成的质量。** 循环能跑、闸能拦、产物键齐全、会收尾——这些是真的。但它读到了什么、诊断得对不对，从来没被验证过。
3. **strategy 的现状**：30 次运行 30 次正常收尾，平均 2.3 步，每次都产出了带优先项的策略。但优先项是模板化的：30 次全部把"跑一遍单元测试"列为第一优先，而规划阶段根本没有容器，跑不了；点名的目标 74 个里 53 个是 `.`、`./...`、`tests` 这类泛指。
4. **diagnose 的现状**：只触发过 3 次运行、共 4 轮循环。4 轮全部 `置信度=low`，全部建议"交人工"；同一种失败情形给出了 3 种不同的类别；2 次取证调用被参数闸拒掉（模型要 `tail_n=200`，上限 50）；其中 1 轮一次取证都没做就下了结论。
5. **现在"一直开着"不划算**：每个任务多花 2–3 次模型调用，换回来的是一份泛泛的策略。先把"看不见"修掉，再大规模测，测过了再默认开。

## 2. 两个节点现在是什么样

| | strategy（策略） | diagnose（诊断） |
|---|---|---|
| 该干的活 | 规划前先读代码，指出具体风险点，产出优先项供规划参考 | 补测之前判定上一轮失败属于哪一类，给出建议 |
| 在图里的位置 | `analyze → strategy → plan`，只在单阶段主图里 | `evaluate → diagnose → generate`，仅当判定是补测且轮次 ≤ 2 |
| 输入 | 需求原文 + 任务上下文 + 能力菜单 | 一句固定目标"诊断上一轮失败……"+ 任务上下文 + 菜单（只留只读能力） |
| 步数预算 | 8 步，其中观察能力最多 3 步 | 3 步 |
| 产物 | `agent_strategy`：优先项（能力、理由、参数提示）、取证计划、降级路线 | `agent_diagnosis`：类别、置信度、证据引用、理由、建议动作 |
| 产物去哪 | 只有每项的"能力 + 理由"进规划提示词；参数提示里的目标被丢掉；生成提示词看不到它 | 类别、置信度、理由（截 200 字）、建议动作进生成提示词；永不写判定 |

## 3. 逐项检查结果

### C1（根因）模型看不到能力取回的内容

- 能力返回结构里，`summary` 的注释就写着"≤200 字摘要（进观察空间）"，`evidence` 只有三键 `kind / path / sha256`（`capabilities.py:54-62`）。
- 取证的正文写进 `data/artifacts/task-*/agent-loop/` 下的文件（`capabilities.py:81-88`），不回传。
- 观察包里每条证据只渲染一行：`step{N} {能力}={状态}: {摘要前 120 字}`（`tool_loop.py:117-119`）。
- 结果：读一个文件，模型只看到"`src/calc.js: 行 1-16（共 16 行）`"，看不到那 16 行是什么；取日志，只看到"`日志尾部已取证`"，看不到日志。

模型自己的原话（账本 `decision_json` 里的 finish 摘要）：

> "已读 src/calc.js 全部 16 行源码，但证据列表未展示函数体细节，无法据此判定 add/div/clamp 的实现是否符合规格"
>
> "近期证据仅显示读取成功，未包含函数体细节，无法据实判断……"
>
> "本轮无任何证据：近期证据列表为空……"

### C2 诊断拿不到上一轮的失败信息

- 诊断的目标是一句固定的话，观察包里没有"哪些用例失败了、报了什么错"（`agent_nodes.py:84`、`tool_loop.py:112-125`）。
- 这些信息平台其实都有：上一轮的输出、错误输出、判定和归因都在状态里。但没有放进诊断的观察包，诊断得自己花步数去取。
- 诊断一共 3 步。账本里 4 轮诊断的调用情况：

| 运行 | 第 1 次调用 | 结果 | 最终结论 |
|---|---|---|---|
| #2618 | 没有调用，直接收尾 | 零取证 | `env_error`，low，交人工 |
| #2620（第 1 轮） | 取日志，`tail_n=200` | 被参数闸拒 | `env_error`，low，交人工 |
| #2620（第 2 轮） | 取日志，`tail_n=50` | 成功，但只看到"日志尾部已取证" | `scaffold_error`，low，交人工 |
| #2621 | 取日志被拒，改 50 后成功 | 同上 | `expectation_dispute`，low，交人工 |

- 同一种情形（见 C5），三种类别，理由都写着"无任何观察证据"或"未见具体失败信息"。

### C3 能力菜单和阶段不匹配

- strategy 在 `analyze` 之后、`provision` 之前运行，这时容器还没创建。但菜单里有 5 项依赖容器或依赖上一轮运行：`test.run.unit`、环境金丝雀、`test.observe.logs`、`test.observe.coverage`、`test.diff.replay`。菜单只按语言过滤（`capabilities.py:484-504`）。
- 2×2 时代的留档里，`test.run.unit` 被调用 11 次，11 次全部失败，原因是 `404 No such container`。
- 本批 30 次运行里模型没有去调用它，但 30 次的策略都把"`test.run.unit`"写成第一优先项——它想做而做不到。

### C4 参数提示不带取值范围

- 菜单的参数提示只给类型和是否必填，比如 `tail_n*:integer`，没有上限（`capabilities.py:468` 起）。模型写了 200，校验器上限是 50，一步就浪费掉了。

### C5 诊断的真实触发场景，是"零执行"被读成了"覆盖不足"

- 3 次诊断运行的第一轮都是：通过 0、失败 0，判定补测，归因 `none`，文案是"通过但覆盖率 0% 低于目标 70%，补测"。
- 实际含义是没有任何用例被执行，更像收集或脚手架问题。评估节点的判定文案把诊断带偏了。

### C6 策略的产物是模板化的

- 84 条优先项（每次 2–5 条，平均 2.8 条），点名的能力分布：`test.run.unit` 30、`test.gen.cases` 23、`test.observe.read` 21、`test.observe.coverage` 10。
- 能力 id 全部写的是真实菜单 id，没有照抄示例里的简写（与 Q4 设计方案 §2.1 的"84/84"一致）。
- 点名的目标 74 个：`src/calc.js` 这类真实路径 21 个；泛指 53 个（`.` 21、`./...` 14、`tests` 11、`coupon` 8）。
- 有的运行把同一个调用原样重复了两次（#2618 两次 `path=. mode=list`），因为每次只拿回"`.: 5 项`"，学不到东西。

### C7 产物往下游传的时候丢了细节

- 进规划提示词的只有"序号. 能力：理由"和降级路线（`prompt_library.py:605-616`）。参数提示里点名的目标没有传过去。
- 生成用例的提示词完全看不到策略，只看得到诊断。

### C8 提示词的示例描述了模型做不到的事

- strategy 的收尾示例写的是"已读 calc 模块源码与首轮用例执行结果……"（`prompt_library.py:555-564`）。可在规划阶段，模型既看不到源码内容（C1），也没有任何执行结果（C3）。
- 示例里的能力 id 简写和参数键写错，Q4 设计方案已经处理，会升到 v2。

### C9 历史数据只能当"盲跑基线"

- 2×2 的 24 格、v1 重测的 24 格、测量批的 30 格，全部是盲跑条件下产生的。
- 这些数据可以回答"流程通不通"，回答不了"节点有没有用"。修复后的批次要单独成表，不和它们合并。

### C10 默认打开的影响面

- 现在默认关，关态下图形态、提示词、库行为逐字节不变，有编译期的节点集合断言锁。
- 默认开后要动的面：`config.py:236` 的默认值；所有默认关态的测试；黄金演示脚本里显式的旗标（留着无害）；成本上每个任务多 2–3 次模型调用（账本实测每次决策平均 1.4 秒）。

## 5. 从来没验证过的

1. 模型读到证据内容后，策略能不能落到具体的函数和边界上。
2. 诊断在脚手架错、预期存疑、零执行这三种已知情形下，类别判得对不对。
3. 策略对生成用例的实际影响：点名的目标有没有变成用例。
4. 打开后在不同语言、不同项目上的稳定性，以及对检出率、成本、耗时的影响。
5. 归因三闸（环境闸、差分闸、连跑闸）开着跑的真实触发情况。
