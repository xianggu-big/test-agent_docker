# zcode 闲时任务：项目全身体检提示词与使用策略（2026-10-31）

> 目的：用免费 token + GLM-5.3 做一次独立、证据化、只读优先的"全身检查"，
> 最大化模型推理价值，避免把额度耗在重复跑测试、贴大文件、改代码上。

## 一、最大化这次机会的 6 条策略

1. **只读审计优先**：默认不改产品代码、不写真实库、不跑真实任务链；先出体检报告，
   修复另开一轮。否则模型会把额度花在改代码和回归上，检查面反而变窄。
2. **给它"地图 + 已知状态"，但不让它信**：把 HEAD、基线数字、外部阻塞（DeepSeek 402）
   写进提示词，要求它独立复验；禁止把文档声称当事实。
3. **按"面 → 线 → 点"三段推进**：先全仓地图与自动化基线，再逐模块深挖，最后红队对抗；
   每段有明确产出，避免一上来钻牛角尖。
4. **要求证据而不是形容词**：每条发现必须带 `文件:行号`、复现命令/输出、期望 vs 实际、
   影响、置信度、建议修法、复验命令；没有证据的写"未验证"。
5. **让它做"声称-实现"对照表**：这个项目最大风险是文档/论文声称与实现漂移（历史上多次发生）。
   让模型逐条核对 README/AGENTS/规划/论文草稿中的关键断言，比泛泛读代码更有价值。
6. **第二轮再修**：体检报告出来后，挑 P0/P1 让另一个闲时任务按"一次一个修复 + 单测 + 回归"
   执行；不要让同一轮既审计又大改，容易把证据链弄丢。

## 二、可直接粘贴的主提示词（推荐）

> 使用方式：zcode 闲时任务里选项目目录 `D:\test agent_docker`，模型 GLM-5.3，
> 把下面整段粘贴进去。若界面有"只读/允许修改"选项，选只读或"仅报告"。

```text
你是独立第三方软件质量审计员，对仓库 D:\test agent_docker 做一次"全身休检"。
目标是找出会影响论文答辩、实验可信度、系统正确性与安全性的真实问题，而不是复述文档。

【硬约束（必须遵守）】
1. 默认只读审计：不修改产品代码、不改文档结论、不提交、不 push、不安装新依赖。
2. 不写真实数据库 data/test_agent.db；不清理 data/workspaces；不杀正在运行的服务进程。
   需要查库时用 sqlite3 只读打开，或复制到临时目录再查。
3. 不跑真实任务链：不运行 run_task / run_task_levels / scripts/run_e7_corpus003.py /
   scripts/run_grid.py / scripts/grade_corpus.py / scripts/mutation_kill.py。
   原因：项目 LLM 走 DeepSeek，当前余额 402；跑真实任务既会失败又会污染实验数据。
4. 不做需要外网的检查（pip install / git clone / LLM 调用）。允许本地命令、pytest、sqlite 只读、
   node --check、docker ps 之类的只读探测。
5. 任何会写文件的命令必须先说明写到哪个临时路径；体检报告除外（见产出）。
6. 只报告有证据的问题；推测必须标"未验证/低置信度"，不得把猜测写成结论。

【已知状态（用于校准，不可当事实，必须独立复验）】
- 当前分支 main，HEAD 7397e0b，工作树应干净。
- 最近一次全量回归：pytest 299 passed, 1 skipped（e2e 慢测默认跳过）。
- 最近一次守卫：python scripts/module_check.py = 105 OK / 0 MISS / 25 PASS / 0 FINDING。
- corpus-003：build_corpus validate OK；calibrate_corpus 5 真缺陷可暴露 + 2 decoy 不暴露。
- 四级链路：L1/L2/L3/L4 + 跨级 RTM 溯源链；D10 报告页有四级卡/溯源链。
- 外部阻塞：E7 真机 n≥3 因 DeepSeek 402 未跑；task155 结果标 status=blocked。
- 历史文档（如 docs/L2验证测试报告.md）允许保留旧数字，不算漂移；当前口径以 README/AGENTS 为准。

【执行流程（按阶段输出，不要跳步）】
阶段 0（地图，约 10 分钟）：读 AGENTS.md、README.md、docs/项目进度时间表.md、
docs/四级双轨测试框架研究规划.md §11、docs/layer5-data-schema.sql、test_agent/ 目录树。
产出一页"系统地图 + 关键断言清单"（声称 → 代码/表/入口 → 待验证项）。

阶段 1（自动化基线，约 15 分钟）：实际运行并记录原始输出：
- python -m pytest -q
- python scripts/module_check.py
- python scripts/build_corpus.py validate data/corpus/corpus-003
- python scripts/calibrate_corpus.py corpus-003
- node --check test_agent/api/static/app.js
- 只读抽查：sqlite3 只读查询 22 张表是否存在、关键表行数、llm_calls 是否有异常累积
任何失败/跳过都要解释原因，不得用"应该通过"代替。

阶段 2（逐面深挖，约 40 分钟）：至少覆盖以下 10 个面，每面给出"通过/有问题/无法验证"：
A. 数据层：22 表 DDL 与 db.py 迁移一致性、外键/索引、重跑幂等（delete-first/upsert）、
   真实库被测试误写的风险、WAL/并发。
B. 核心语义：归因三分类、R-Loop 三停、证人冻结、指纹熔断、报告双闸、单快照一致性；
   找"能造假/能被绕过"的路径（这是论文的防造假卖点，必须红队）。
C. 四级链路：LEVELS_* 默认关、trace_from 链、L2 handler 根/调用图、L3 引用链、L4 转化器；
   检查跨级溯源链是否有"广撒网候选"冒充"精确定位"的表述风险。
D. 评测协议：corpus-003 真值/decoy、阅卷分母、E7 blocked 处理、数字是否只有一个来源；
   检查 recall/命中率等指标能否被测试套件全过或空集刷高。
E. 安全：登录/token、角色守卫、路径穿越（repo_url/workspace）、命令注入（docker exec/
   pip/uvicorn）、XSS（前端 esc）、密钥落库/日志、CORS/CSRF、拒绝服务（超时/资源限额）。
F. 前端/API 契约：前端调用的端点是否都存在、错误分支是否展示、四级卡在无数据时是否退化、
   JS 语法、XSS、长文本截断。
G. 测试质量：测试是否真锁机制（反向验证：改掉实现是否变红）、是否有测试写真实库/依赖顺序/
   共享状态、断言是否过弱、e2e 跳过的风险。
H. 文档/论文一致性：README/AGENTS/规划/论文草稿中的数字、表数、节点数、调用点数、默认开关、
   实验状态是否与代码一致；区分"历史文档"与"当前声称"。
I. 可运维性：容器回收、孤儿容器、超时、日志、数据库备份、失败恢复、启动顺序。
J. 依赖与可复现：requirements 固定版本、Python 版本假设、离线可跑性、脚本入口是否真实存在。

阶段 3（红队对抗，约 20 分钟）：选 3 个最危险假设主动攻击，例如：
- 能否让报告在失败时写出"全部通过/已解决"而通过审查？
- 能否让 L2/L3 在服务未就绪/端点为空时被记为 pass？
- 能否通过构造场景/语料让 recall 或溯源命中率虚高？
- 能否通过 repo_url/文件名/LLM 输出注入执行任意命令或读到宿主文件？
每条给出攻击步骤与结果；不能实际执行的标"设计推演"。

阶段 4（产出，约 15 分钟）：写一份报告到 docs/体检报告-20261031.md（只写这一个文件），结构：
1. 一句话结论 + 体检总分（按 10 个面给 通过/黄/红）
2. 基线复验结果（命令 + 原始关键输出）
3. 发现清单（按 P0/P1/P2 排序，最多 20 条；每条含：标题、证据 file:line、复现命令、
   期望 vs 实际、影响、置信度、建议修法、复验命令）
4. "声称-实现"对照表（至少 15 条关键断言：文档说 X → 代码实际 Y → 结论）
5. 测试缺口矩阵（机制 → 现有测试 → 缺正例/负例/边界 → 建议补的测试）
6. 建议的下一轮 10 个动作（按投入产出排序，标注"只改文档/加测试/改代码"）
7. 未验证/无法验证清单（诚实边界）
最后在对话里只回：P0/P1 摘要 + 报告路径。

【输出纪律】
- 不要贴大段源码；引用 file:line 和 5-15 行关键片段即可。
- 不要重复跑同一个测试；一次结果记下来复用。
- 不要把"文档写了"当证据；以代码、DDL、实际命令输出为准。
- 发现历史遗留问题先判断是否已被后续提交修复；不要重复报已知已修项。
- 如果时间/额度不够，优先完成阶段 1+2 的 A/B/C/D/H，再补 E/F/G/I/J。

现在开始：先输出阶段 0 的地图与断言清单，然后按阶段执行。
```

## 四、第二轮修复提示词（另开闲时任务）

```text
你是修复工程师。上一轮体检报告在 docs/体检报告-20261031.md。
本轮只处理报告中的 P0 项，一次一个：
1. 先复现问题并记录失败证据；
2. 写最小修复 + 至少一个能"改坏就变红"的单测；
3. 跑相关测试 + 全量 pytest + module_check；
4. 更新受影响的文档/守卫契约；
5. 每项独立 commit（路径范围化），不 push。

每完成一项在对话里报告：问题 → 修法 → 证据 → 回归结果 → commit。
```

## 五、体检后你怎么验收

- 报告是否给出**可复现命令与原始输出**（不是"检查通过"四个字）。
- 是否至少找出 1 个**文档声称与实现不符**或**测试锁不住机制**的问题（这个项目历史上每轮都有）。
- 是否区分了"历史文档旧数字"与"当前声称漂移"，没有把历史文档当 bug 刷数量。
- 是否守住了只读边界：真实库/工作区/服务进程没有被审计任务破坏。
- P0 清单是否不超过 5 条、每条都能在 10 分钟内复现。
