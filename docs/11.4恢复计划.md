## 2. 现成方法调研（研究先行，均已联网核验，2026-11-04）

| 方法/项目 | 来源 | 解决什么 | 用到本项目哪里 |
|---|---|---|---|

| **BugsInPy** | [arXiv:2401.15481](https://arxiv.org/pdf/2401.15481v1)，493 个真实 bug，17 个 Python 项目（pandas/keras/matplotlib/scrapy/ansible 等） | Python 真值基准 | Python 真值来源 |

| **TestGen-LLM 验收过滤器** | Meta，FSE 2024，[arXiv:2402.09171](https://arxiv.org/pdf/2402.09171)：候选用例必须"能构建 → 连续多次跑可靠通过（跑 5 次丢弃任一失败）→ 新增覆盖"三级过滤 | 生成用例的质量闸 | 闸 2 的"连跑 k 次"策略与验收顺序直接沿用（其衍生实践默认 k=3） |

| **变异测试**：mutmut（Python）/ PIT pitest（Java）/ Stryker（JS/TS） | [对比指南](https://www.pistack.xyz/posts/stryker-vs-pitest-vs-mutmut-self-hosted-mutation-testing-guide-2026/)、[pitest 官方](https://pitest.org/quickstart/maven/) | "测试的测试"：注入已知 bug 验证用例集能否杀死 | G5 用例质量度量；自制语料的用例强度抽检 |

结论：**"被测项目缺陷 vs 用例错误 vs 环境错误"的判别不需要发明新方法**——业界标准做法是"差分执行 + 可靠性连跑 + 基准真值 + 变异抽检"四件套，全部有论文/工程背书。我们做工程化整合，创新点落在"把它嵌进四级双轨与防造假闸门体系"。

## 3. 核心方案：失败归因三闸（Env-Gate / Diff-Gate / Label-Gate）

> 命名说明：与现有"防造假三道闸"（语义闸/证人闸/报告闸，管造假）不同，本三闸管**失败归因**，防的是"把用例/环境错误记成产品缺陷"。

### 闸 1 环境闸（Env-Gate，跑真用例之前）
- 每个任务容器启动后、跑生成用例前，先跑 **金丝雀套件**（2-4 条已知正确的极简测试）：
  1. 框架自检：`assert 1+1==2` 级（验证测试框架可运行）；
  2. 依赖自检：`import` 被测项目主依赖（验证依赖装全）；
  3. IO/网络自检：tmp 文件读写（+ 可选 localhost 端口探测，按项目类型）。
- 任何金丝雀失败 → 任务判 `env_invalid`，**不得产出任何产品缺陷结论**，报告标注环境错误清单。fail-fast，不等 12 条全错再事后分析。
- 记录**环境指纹**（镜像、语言版本、依赖清单、金丝雀结果）进台账，供事后审计。

### 闸 2 差分闸（Diff-Gate，对失败用例）
沿用 LIBRO/TestGen-LLM/SWT-Bench 的标准做法：
- 每条生成用例在两个版本上执行：**V_bug**（被测版本）与 **V_ref**（对照版本）。
- V_ref 来源优先级：基准自带 fix 提交（Defects4J/BugsInPy）→ git 上一稳定 tag/commit → 用户指定"已知好版本"。无任何对照来源（如无 git 的本地目录）→ 降级为"闸 1 + 连跑 + LLM 评审"并标低置信。
- 2×2 判定矩阵：

| V_bug | V_ref | 判定 | 置信 |
|---|---|---|---|
| fail | pass | **product_defect**（缺陷暴露） | 高 |
| fail | fail | **test_defect 或 env_error**（用例/环境错，不许记产品缺陷） | 高 |
| pass | pass | 正常（记录覆盖贡献） | — |
| pass | fail | **用例把 bug 行为写成断言**（overfit/断言反演，要求重写） | 高 |

- 可靠性连跑（TestGen-LLM 口径）：判定用例**连跑 k 次**（默认 k=3，可配），结果不一致 → 标 `flaky`，不入归因分母。
- 成本控制：只对 V_bug 上失败的用例做 V_ref 复跑（fail-to-pass 子集），不双跑全量。

### 闸 3 归因闸（Label-Gate，输出侧）
- 每条失败用例落库必须带 `label ∈ {product_defect, test_defect, env_error, flaky, uncertain}` + 证据（差分结果、日志摘要、最小复现）+ 置信度。
- `uncertain` 与 `flaky` **不计入任何统计分母**（与现有防造假口径一致，不拿脏数充数）。
- 报告页新增归因分布：本轮 12 条失败 → 1 product_defect / 8 test_defect / 2 env_error / 1 flaky（示意），一眼看穿"全错是谁的锅"。

### 配套：变异抽检（离线，可选）
对自制语料：用 mutmut/PIT/Stryker 注入已知变异，验证用例集能杀死（mutation score）——回答"测试用例本身行不行"（G5）。对第三方真值基准则不需要（真值现成）。

## 6. 执行流程与成功标准

流程（每个语言/项目）：
```
环境体检卡 → Env-Gate 金丝雀 → agent 四级链路跑 → 失败用例进 Diff-Gate（V_ref 复跑 + 连跑 k 次）
→ Label-Gate 归因落库 → 归因分布报告 → 人工抽检 ≥20 条验证归因正确性
```

成功标准（衡量"测试 agent"本身，不是衡量被测项目）：
1. **归因精确率**：product_defect 标签人工抽检正确率 ≥80%；
2. **用例有效率**：test_defect + env_error 占全部失败 ≤30%（task_366 事故基线 12/12=100% test_defect，必须数量级下降）；
3. **已知缺陷命中率**：A 轨基准子集上 fail-to-pass 命中（SWT-Bench 口径）按成本设定目标，起步 ≥30%；
4. **外部效度**：B 轨至少 2 个真实项目上产出"可复现、跨级溯源到 file:line"的缺陷报告各 1 份；
5. 全程成本台账（llm_calls/时长/归因分布）齐全，可进论文第 6 章。
