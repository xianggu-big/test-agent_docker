# 软件测试理论基础（开题草案 · 理论章素材）

> 用途：开题报告"相关理论/研究内容"章节的修正版理论底稿。
> 口径说明：每节末尾的「系统落点」把传统理论映射到本课题的 Test Agent / Docker 实现，理论章与设计章由此咬合。

## 1. 测试分类体系

### 1.1 按是否运行程序：静态测试 / 动态测试
- **静态测试**：不运行程序的测试，包括代码评审、静态分析、规范检查。
- **动态测试**：运行程序、给定输入、比对预期输出的测试。

**系统落点**：低占比语言「仅静态扫描、不拉执行镜像」的分级策略，理论依据即静态测试；静态扫描（ruff / bandit / semgrep 等）属于静态测试的自动化形态。

### 1.2 按对内部的可见性：黑盒 / 白盒 / 灰盒
- **黑盒测试**：不关心内部结构，**依据是需求规格说明（功能要求与性能指标）**。
- **白盒测试**：针对程序内部结构、逻辑与循环，基于控制流设计用例（如语句/分支/路径覆盖）。
- **灰盒测试**：黑盒方法为主、辅以对内部的有限了解。**接口测试的现代主流实践是灰盒**：外部行为用黑盒设计，同时需要校验数据库状态变化、替身（mock/stub）外部依赖、分析失败日志。

### 1.3 按质量属性：功能测试 / 非功能测试
- 非功能测试含性能（负载/压力/稳定性）、安全等，自成体系。
- **本课题范围界定**：以功能正确性为主；性能仅**采集**耗时与资源占用作为输出指标，不承诺负载/压力/稳定性测试能力。

### 1.4 经验驱动的测试
- 术语：**错误推测法**（error guessing）与**探索式测试**（exploratory testing），理论支撑为缺陷模式 / 失效模式分类学——测试人员依据已有经验与软件失效常识，针对薄弱点设计攻击性用例。
- 本课题做法：将"老师傅经验"**显式化**为缺陷模式知识库，注入用例生成的提示词骨架，使经验驱动方法可被 Agent 复用。

## 2. 测试级别

经典分层：**单元测试 → 集成测试 → 系统测试 → 验收测试**，逐级扩大范围、逐级靠近用户视角。

**系统落点**：本课题聚焦**单元测试为主 + 轻量集成**，对象为可自动构建的开源中小型项目；需要复杂外部服务或硬件的项目明确标注为不支持，诚实降级。

## 3. 测试流程（四阶段）

### 3.1 测试分析阶段
- 基于需求与性能要求制定**测试条件**，建立**需求追踪矩阵（RTM）**。
- RTM 的作用（正名）：①正向保证每条需求都有用例覆盖；②反向在需求变更时快速定位受影响用例（变更影响分析）。**RTM 防不住需求变更，它保证的是覆盖与可追溯。**
- 合理选择测试内容、人员、资源与时间。

**系统落点**：对应 `analyzing` 状态——克隆仓库、语言占比探测、模块拆分、分级策略（full / static_only / skip）。被测对象 = 不同规模程序；执行者 = Test Agent；环境 = Docker 镜像；组织方式 = 持续测试队列。**准出标准在分析阶段定死**（覆盖率阈值 + 预算上限），后续闭环据此判定。

### 3.2 测试设计阶段
用例规格包含六要素（源自 IEEE 829 传统）：

| 要素 | 说明 | 本课题用例即代码的对应 |
|---|---|---|
| 编号 | 便于查询与追溯 | `test_cases.id` |
| 测试标题 | 表明测试目的 | `name` |
| 重要级别 | 对应用户需求优先级 | `priority`（驱动执行队列） |
| 测试输入 | 需求中的输入条件 | 参数化用例的 `content` 数据段 |
| 操作步骤 | 尽量完善 | 可执行脚本本体 |
| 预期结果 | 需求的预期输出、状态变化 | **断言（assertions）** |

**两条纪律**：
1. **预期结果必须在执行前定义**——防止"先看结果再定预期"的事后合理化；自动化中对应**断言先于执行生成**（先生成断言，再运行代码验证），这是 LLM 生成用例可信的前提。
2. 用例设计方法必须是**显式的方法论**而非自由发挥。本课题采用五种方法作为生成提示词骨架：

| 方法 | 黑盒/白盒 | 原理 | 示例 |
|---|---|---|---|
| 等价类划分 | 黑盒 | 输入域分等价类，每类取代表 | 密码 6~20 位 → 有效取 10 位；无效取 5 / 21 / 空串 |
| 边界值分析 | 黑盒 | bug 集中于边界：min-1、min、min+1、max-1、max、max+1 | 上例取 5、6、7、19、20、21 |
| 判定表 | 黑盒 | 多条件组合全列出，每列一条用例 | 「VIP 且满 99」折扣逻辑 → 4 组合 |
| 语句/分支覆盖 | 白盒 | 基于控制流图，每条分支至少执行一次 | if-else 两方向均有用例 |
| 变异测试 | 质量度量 | 注入人工缺陷验证用例能否捕获 | 捕获=有效；漏捕=用例无效 |

**时代演进**（论文可写成从传统到本课题的演进）：IEEE 829 重量级文档 → 敏捷轻量格式（Given-When-Then）→ **用例即代码**。上表右列即六要素在本系统中的代码化形态，一个不缺。

### 3.3 测试执行阶段
- 传统要求：测试执行进度计划（规程、自动化脚本、执行时间与执行者）、回归测试、优先级与技术/逻辑依赖。
- **系统落点**：执行进度计划自动化为**优先级任务队列**（`container_jobs`：优先级、并发上限、资源限额、超时回收）；执行全部发生在容器内，宿主机只收结果（执行与判定分离）；**环境即镜像**——工具链版本锁死，实验可复现。
- 回归测试：修复后重测以防回归，是自动化价值最大的场景。本课题的**补测闭环（R-Loop）**即"失败 → 修复/重生成 → 回归重跑"的自动化。

### 3.4 测试评估阶段
基本要求：量化覆盖（行/分支覆盖率）与缺陷跟踪报告。本课题补充三件闭环要件：
1. **准出标准核对**：回到分析阶段定死的标准（覆盖率阈值、预算），达标才收敛，未达标如实上报——评估与计划首尾闭合。
2. **缺陷分析指标**：缺陷密度、分布、逃逸率。
3. **测试有效性自评估（漏测分析）**：线上/标注集问题回溯未覆盖原因，反哺用例生成。

**指标与数据表落点**：

| 指标 | 口径 | 数据表 |
|---|---|---|
| 用例通过率 | passed / (passed+failed+skipped) | `test_reports` |
| 行/分支覆盖率 | coverage.py / JaCoCo | `test_reports.coverage_*` |
| 有效用例率 | 触发断言差异或捕获变异的用例占比 | `test_cases` + 变异实验 |
| 缺陷检出率 / 误报率 | 相对人工标注集 | `feedback_annotations` |
| 工具调用成功率 | Skill 调用 ok / 总调用 | `skill_invocations` |
| 耗时与资源 | 阶段墙钟 + 容器 CPU/内存 | `container_jobs`、`test_reports.duration_ms` |

## 4. 缺陷分类与生命周期

**失败三分类**（判读正确率的前提，分错类则指标全错）：
1. **环境失败**：依赖装不上、端口占用等 → 非 bug，修环境重跑；
2. **用例缺陷**：断言写错、用例自相矛盾 → 误报，重写用例；
3. **产品缺陷**：断言合理而代码行为不符 → 真实发现，记入报告。

**缺陷生命周期**：新建 → 确认 → 修复 → 回归 → 关闭。本课题的 R-Loop 自动化了「回归」环节，并带两条护栏：
- **同指纹熔断**：失败指纹（报错关键栈+位置哈希）与上轮一致即判定原地打转，终止重试；
- **如实上报**：轮次上限或预算耗尽时输出真实报告（如"覆盖率停在 58%，未达标"），禁止伪装成功。

## 5. 传统流程 → 本课题系统组件映射总表

| 传统测试理论 | 本课题实现 | 层次 |
|---|---|---|
| 测试分析（范围、RTM、资源计划） | analyzing：语言探测、模块拆分、分级策略 | L2 Agent + L3 Skill |
| 测试设计（六要素、五方法） | gen_tests：方法驱动提示词 + 用例即代码 | L3 Skill + 用例库 |
| 环境搭建 | 环境即镜像（py312 / jdk17-maven），依赖容器内安装 | L4 Docker |
| 执行进度计划 | container_jobs 优先级队列 + 资源限额 + 超时回收 | L4 调度 |
| 回归测试 | R-Loop 补测闭环（同指纹熔断、预算停止） | L2 Agent |
| 静态测试 | 低占比语言 static_only（ruff/bandit/semgrep） | L4 Docker |
| 测试评估（覆盖+缺陷+准出核对） | collect_report + 指标表 + 误报标注闭环 | L3 Skill + L5 数据 |
| 缺陷跟踪单 | test_reports.defects（结构化）+ feedback_annotations | L5 数据 |
