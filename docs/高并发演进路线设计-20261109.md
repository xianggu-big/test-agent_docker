# 高并发演进路线设计（2026-11-09，决择单第 3 项）

> 定位：本文回答"如果高并发多项目是真实需求，系统如何长大"——产出为①演进路线设计（三段式）②论文展望章可用段落。**本轮不实现任何并发设施**（决择单：只做方案）。

## 1. 容量实测锚点（已有数据，演进叙事的起点）

- 单机 3~10 路并发容器无压力（每任务一容器、1 核 1GB 限额；三项目并发实测可行性已评估）；
- 真实瓶颈 = LLM 侧：单任务 ~40k~140k token（实测 max prompt 40,634），并发 N 路 = N 倍烧钱速率 + API 限流是队头；
- 现有机制与分布式组件的单机简化对照：exec_queue 队列↔Job 调度、资源限额↔ResourceQuota、超时重建↔activeDeadlineSeconds、token 停车线↔分布式原子计数器。

## 2. 三段式演进路线（每段独立可验收）

### 第一段：单机真队列（5~20 并发）
- exec_queue 从"单 worker 串行"升级为"N worker 信号量池"（N 可配）；
- SQLite → PostgreSQL（多写并发正解；29 表 schema 迁移一次性工程）;
- 全局 token 预算池（跨任务原子计数）——没有它，并发就是烧钱失控；
- 验收：N=10 并发跑真实项目，p95 队列等待、LLM 限流触发率、预算池不超支。

### 第二段：多机工人（20~50 并发）
- 共享队列（Redis Stream）+ 多台工人机器各自拉任务跑本地 Docker；
- 工人无状态化：工作区/镜像就绪自检（preflight 已有）搬到工人侧；
- 验收：2 台机器 × 20 并发，任务分配均匀、无重复消费（Stream ACK 语义）。

### 第三段：集群编排（百级）
- 执行层迁 Kubernetes Job（对照表已备：PriorityClass/ResourceQuota/TTL 清理）；
- 数据层云 PG + 对象存储（工作区快照）；
- LLM 网关统一限流/记账/多供应商路由（与每节点路由任务卡-B 衔接）。

## 3. 论文展望章可用段落（可直接收编）

> 本系统当前为单机架构，实测可承载约 10 路以内的容器并发（每任务独立容器、1 核 1GB 限额），瓶颈位于大模型 API 的吞吐与成本而非容器层。向高并发演进的路径已识别为三段：其一，任务队列真队列化（信号量池+全局 token 预算池）与数据层迁移 PostgreSQL，支撑单机 20 路以内并发；其二，引入共享队列（如 Redis Stream）实现多机工人拉取式执行；其三，执行层迁移 Kubernetes Job 并配套统一 LLM 网关。本系统已实现的任务队列、资源限额、超时回收与预算停车线，分别是上述分布式组件（Job 调度、ResourceQuota、activeDeadlineSeconds、原子计数器）的单机简化形态，演进是配置与部署层的扩展，不要求方法层重构。
