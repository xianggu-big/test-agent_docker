## 1. 为什么没拉开差距

六个原因，都有实测依据：

1. **任务在天花板上。** 关臂（不开循环）的覆盖率已经到顶：corpus-003 均值 0.945，演示项目 js 1.00、go 0.79、coupon 0.99。需求本身给了缺陷线索：js-calc 的需求直说"clamp 上边界可疑"，corpus-003 的 REQUIREMENT.md 写明"1~4 小时闭区间""重叠返回 409"。bench3 的需求显式化梯度（94.4% → 86.7% → 0%）说明检出主要由"需求给不给线索"决定。
2. **尺度太粗。** 行覆盖只量"执行过"，不量"测得对不对"；小项目十几条用例就打满，没有区分度。
3. **循环实际很窄。** 策略平均 2.6 步收尾（预算 8 步），调用 100% 是读文件；诊断 13 次全部 1 步收尾，而且 45 格检出任务里 44 格首轮就停，诊断几乎不触发。
4. **产物只是提示词里的一段话。** 主链路本来就带需求、源码、五方法知识库、陷阱库前 4 条、热点、覆盖率回灌；策略多加的那段对简单项目是重复信息。
5. **不沉淀。** 每个任务从零开始，上次学到的东西下次用不上。
6. **读得少而且截得机械。** 源码预算固定 24000 字符，按文件顺序截断；tornado 那格被截掉 460 段，截掉的可能正是要测的。

"多思考几轮"单独不管用的原因：模型能做的只有读文件，小项目读完一个文件就没事可做，所以 2.6 步就自己收尾了。多出来的轮次要有价值，必须有事给它做：一张必须逐条交代的清单（广度），和逐点下钻的义务（深度）。

**唯一可见的正信号在"需求含糊"处**：Wave2 的知识库臂对默认臂检出 0.80 对 0.60（方向性读数）；本次对照臂 G2 检出开臂 1.00 对关臂 0.75，方向一致但样本不足。差距会出现在基线"无知"的地方：需求含糊、项目类型陌生、项目大、工具不匹配。现有实验项目恰恰都是基线不无知的小项目。

## 2. 根因一句话

不是思考轮数不够，而是**没东西可想、想了不沉淀、沉淀了不约束**。重设计对应三件事：给它一张可积累的清单去想（大纲库）；把它的产物从"提示"变成"必须交代的账目"（账目化）；让它把验证过的东西写回来（写回进化）。

## 3. 专家模型：两个 agent 重新定位

### 3.1 策略 agent：从"读文件出优先项"到"出一份测试计划"

| 步 | 做什么 | 对应专家行为 | 产物 |
|---|---|---|---|
| ① 认类型、调经验 | 判定语言、项目类型、技术栈、体量；调出对应的大纲 | "这是个 Go 写的 REST 服务，这类东西我见过" | 原型键、大纲条目集 |
| ② 勘察 | 按大纲逐项核对项目，把条目映射到具体函数、端点、文件；标适用/不适用及理由 | 翻代码，心里对着检查单 | 大纲账目表 |
| ③ 猜想 | 在大纲之外提出若干"这里可能出错"的假设 | 经验带来的直觉、错误推测法 | 猜想清单 |
| ④ 选型 | 按项目特征与条目的工具需求，从工具目录选工具并验证 | "这个项目该用竞态检测和契约测试" | 工具清单（带理由） |
| ⑤ 交计划 | 广度账目 + 按风险分配深浅 + 猜想 + 工具，交给生成器与规划节点 | 写测试计划 | 测试计划 |

**广度** = 大纲账目：每个适用条目必须落到"已规划（带目标符号和预期依据）""不适用（带理由）""本轮不覆盖（带原因）"三者之一。没交代完不允许收尾（机器闸，同现有泛指闸的做法）。

**深度** = 每个已规划条目按风险分分配深浅。风险分由需求强调程度、热点复杂度、扇入、该类项目的历史缺陷密度相乘得出（复杂度与扇入模块画像里已有）。
- 浅：一条正常 + 一条异常。
- 中：等价类 + 边界值 + 错误路径。
- 深：组合（判定表、状态转换、性质、变形关系）+ 模糊或属性抽样；跑完后对着存活的变异子补测。

**新的广度指标——大纲覆盖率** = 已规划 ÷（适用 − 有理由豁免）。它和行覆盖是两把尺子：行覆盖量"执行过"，大纲覆盖量"该想的想到了没有"，不受小项目天花板影响。这给了对照实验一个能拉开差距的读数。

**位置调整（可选）**：现在是"案头勘察"（规划前）。L2 起可以加一次"现场勘察"（环境准备好之后）：跑一遍仓库自带测试、拿基线覆盖、做静态分析，用来修订计划。设计报告里把"挪动节点位置"列为备选，这里给出分两次做的折中。

### 3.2 诊断 agent：从"一步分类"到"分诊 + 模式库 + 假设驱动"

| 步 | 做什么 | 产物 |
|---|---|---|
| ① 认失败形态 | 失败签名聚类，查模式库（见过的签名 + 上次有效的修法） | 已知 / 未知 |
| ② 取证 | 已知则一步出结论；未知则假设驱动：每多一步写明"要区分哪两个假设" | 证据链 |
| ③ 结论 | 类别、置信、证据引用、建议；脚手架与环境类可在闸内直接修 | 诊断 |
| ④ 写回 | 新签名入库为候选；修法有效性随运行积累 | 模式库增量 |

详见 §7。

## 4. 测试大纲库（可复用资产）

### 4.1 结构

- **原型键**：(语言, 项目类型)。项目类型由确定性信号判定：REST/API 服务、库或 SDK、命令行工具、数据管道、Web 前端、gRPC 服务、monorepo 应用等。判定复用现有的环境探测（每个字段带推断依据）、端点提取、入口形态；歧义才让模型判一次。
- **维度层（广度）**：跨领域通用 + 语言特有 + 类型特有。示例：
  - 黑盒通用：等价类与边界（数值、字符串长度、集合大小）、判定表与组合、状态转换与非法状态、幂等与重复提交、并发与竞态、时间与时区、排序与分页、错误输入与错误码契约、持久化与重启恢复、编码与国际化、数值精度与溢出、大输入。
  - 白盒：语句/分支/条件覆盖、循环边界、变异分析（等价变异、边界变异、返回值变异、语句删除）、数据流（未初始化、未使用）、异常处理分支。
  - 语言特有举例：Python 的可变默认参数与 None 传播；Go 的 nil map 写入、error 被覆盖、goroutine 泄漏、整数溢出；JS/TS 的类型强制转换与异步时序；Java 的空指针与异常层级；PHP 的松散比较与数组键转换。
- **条目层**：检查点 + 触发条件（什么项目特征下适用）+ 典型缺陷模式 + 建议方法（黑盒/白盒）+ 预期依据来源（需求、文档、惯例）+ 建议工具 + 历史命中统计。
- **状态**：候选、已验证、淘汰。

### 4.2 账目化：让大纲成为约束而不是提示词里的佐料

策略 agent 收尾时提交的是账目表而非优先项清单。机器闸检查：适用条目是否都有归宿、不适用是否带理由、已规划是否带目标符号。生成器按账目表生成，报告页展示"大纲覆盖矩阵"（哪些条目测了、哪些豁免、为什么）。

### 4.3 想象槽：防止被清单框住

每次策略必须提出若干条大纲之外的风险假设。执行后回填：证实、证伪、未验证。证实的成为候选条目。"大纲外命中数"单独统计，作为创新能力指标。一句话：**大纲是凝固的经验，猜想是经验的候选**。

### 4.4 写回进化

- **升级**：某条目在一个原型下连续命中若干次，从候选升为已验证（人工确认）。
- **漏检回灌**：跑完后被人工、变异、差分发现的缺陷，若没有任何已规划条目覆盖，自动生成"缺条目"提案。
- **降权**：长期零命中且高成本的条目降权，不删除，留痕。
- **版本化**：大纲库带版本号，run 行记录用的是哪个版本，跨版本不混算（沿用项目既有的版本可比纪律）。

### 4.5 冷启动

从已有资产导入：五方法知识库、陷阱库、模块画像里的"模块特征 → 测试路线"规则表、各语言陷阱条目。再从两千多个历史任务里挖"哪类用例真抓到过缺陷"。最后由模型按原型起草，人工审定。

**Wave2 的教训**：知识库只加厚会进平台期（0.92 / 0.92 / 0.90）。价值在"选得准、约束得住"，不在文本量。所以大纲库的第一性指标是条目命中率，不是条目数。

## 5. 工具自适应（选型与插件）

### 5.1 现状

插件管理器已建好安全的一半：七步生命周期（模型只申请、目录解析、沙箱安装、契约验证、任务启用、推广回滚），只接受目录编号加版本、摘要固定防偷换、任务容器无外网、平台侧预拉取后离线装、模型永远不能批准自己。**但工具目录里是 0 条目**，"发现缺口"只是模型随手申请，没有系统的选型。调研报告的结论：测试 agent 自主接入工具没有完整开源先例，是创新点也是风险。

### 5.2 四步

1. **工具需求识别**（确定性为主）：项目画像信号（语言、版本、框架、构建系统；是否有 HTTP 端点、数据库、消息队列、文件 IO、并发、时间依赖、浮点、外部服务）× 大纲条目的"建议工具"字段，产出工具需求清单，每项写明服务哪个条目、期望得到什么证据。
2. **目录选型**：目录条目含编号、固定版本、适用语言与原型、用途、离线安装方式、能力封装（参数 schema、风险级、是否需要容器）、许可证、体积、已知坑、验证过的镜像、状态、摘要、使用账本。策略 agent 从目录里选，每选一个写理由。闸：语言与镜像兼容、许可证白名单、单任务额外工具数上限。
3. **金丝雀验证**：装好先跑最小自检（工具能起、能对空项目产出结果），失败即卸载回退并记账。没自检过的工具不进正式测试轮（同现有环境闸的思路）。
4. **使用账本**：（工具, 原型）→ 是否产出证据、是否检出、耗时、失败率。选型时把统计带给模型；长期不产出的工具降权。这是工具层面的自进化。

### 5.3 新工具准入三档（需要拍板，涉及"网络隔离"硬边界）

| 档 | 做法 | agent 的权力 | 安全承诺 |
|---|---|---|---|
| 甲 人工准入（现状） | agent 提工具申请卡，人批准后平台拉取、验证、入目录 | 只能申请 | 容器零外发 |
| **乙 隔离检疫准入（推荐）** | agent 可触发取回；取回由平台侧独立进程执行，只允许访问包源镜像白名单；取回后固定摘要，在一次性镜像里自检与查许可证，通过才入目录为"候选"；人只审"候选转正" | 能自己把需要的工具弄进来用 | 测试容器仍然零外发、无密钥；取回走单一白名单通道加检疫 |
| 丙 完全自主 | agent 在任务容器内联网下载执行 | 完全 | 推翻网络隔离与供应链防线，不建议 |

推荐乙：agent 拿到了"发现缺工具就自己弄进来用"的权力，安全边界讲得清。

### 5.4 工具范围（限黑盒、白盒）

覆盖率插桩、变异分析、模糊测试与属性测试生成、契约与快照 oracle、测试替身与隔离（时间、网络、数据库、文件系统）、失败子集重跑与乱序执行、调用图与影响面分析、运行期检查器（竞态、内存、未初始化读）、依赖环境探测。**不含**性能压测、安全扫描、部署运维类。

## 6. 体量自适应预算

### 6.1 体量画像（零 LLM，进策略前算）

范围内代码行数、文件数、模块数、导出符号数（函数、类、端点）、依赖数、最大文件行数、热点复杂度、已有测试数、需求指向范围（需求点名的模块与端点）。据此分四档。

### 6.2 策略预算表（起始值，待标定）

| 档 | 范围内代码 | 步数 | token | 观察步 | 阅读方式 |
|---|---|---|---|---|---|
| S | ≤ 2 千行 | 8 | 3 万 | 3 | 直接读 |
| M | 2 千 – 2 万行 | 16 | 8 万 | 8 | 先地图再选区 |
| L | 2 万 – 10 万行 | 32 | 20 万 | 16 | 分层阅读 + 勘察笔记 |
| XL | > 10 万行 | 48 | 30 万 | 24 | 只读需求相关子图，其余声明未覆盖 |

现状是固定 8 步 / 3 万 token / 观察 3 步。**关键不是"给更多"，是"按范围给"**：预算按"路由后的范围内代码量"定，而不是按仓库总量；大仓库先把钱花在地图和选区上。喂给生成器的源码预算（现固定 24000 字符）同样按档伸缩，并且改成按"账目表对应的目标符号"喂，不再按文件顺序截断。L 档单格成本约为现在的八倍，需要单独的停车线。

### 6.3 分层阅读

- 第 0 层 地图（零 LLM）：文件树、清单文件、入口、端点表、公开符号、依赖图、热点、已有测试清单。复用项目知识索引、调用图、仓库原生测试结构卡、盲意图骨架。
- 第 1 层 选区：按需求与大纲把条目映射到模块，每条写目标符号；映射不上的标"未定位"。
- 第 2 层 下钻：对选中的目标读函数体窗口，单模块预算上限，防止一头扎进一个文件。

### 6.4 勘察笔记（让长循环不迷失）

现在每一步只带最近 3 条证据，读多了就忘。改成 agent 每步维护一份有界的结构化笔记：已确认事实、目标清单、开放问题、大纲账目状态。下一步只看笔记加新证据，原始证据留在账本里供人查。这份笔记同时是人可读的勘察记录。

### 6.5 诊断预算（按失败复杂度）

| 失败形态 | 判据 | 步数 | 允许的证据动作 |
|---|---|---|---|
| 已知签名 | 模式库命中 | 1 – 2 | 失败摘要即可 |
| 单簇新签名 | 多条失败同一指纹，库中无 | 4 – 6 | 重跑失败子集；读用例与栈帧附近源码 |
| 多簇 | 两个以上不同指纹 | 每簇 4 步，总上限 10 | 逐簇 |
| 零执行或环境 | 没有任何用例被执行 | 4 – 6 | 环境探测、依赖树、金丝雀 |

现状是固定 3 步 / 1 万 token / 只读。改后 token 随步数给，上限 6 万。每多一步必须写明要区分哪两个假设。

## 7. 诊断 agent 重设计

- **位置前移：停判前分诊。** 现在断言失败首轮就按"疑似产品缺陷"停，诊断根本进不去（昨夜实锤：预期争议类不可达）。改为：断言失败准备停判时先跑一次最短路径的只读诊断，产出"预期依据核查"——每条保留失败的预期来自需求、文档还是惯例。全部无依据时，判决由规则引擎降为"预期存疑待裁决"（C7 旗标已做雏形）。铁律不变：诊断只提议，判决由规则依据可核对的证据落，人工终裁。
- **模式库**：失败签名（语言 × 错误类 × 消息指纹）→ 已知类别、上次有效修法、出现次数。签名由确定性聚类产出（缺陷聚类旗标已有）。
- **可执行的动作（闸内）**：脚手架修复（现有 AST 差异闸：改断言、删用例一律拒）、环境修复（重装依赖）。产品缺陷与预期争议永不自动处理。
- **写回**：新签名入库为候选，修法有效性随运行积累。

## 8. 自由度分级

原则：**自由在节点内，边界在闸上。**

| 级 | 策略 agent | 诊断 agent | 新增的闸 |
|---|---|---|---|
| L0 现状 | 读文件，出优先项提示 | 只读，3 步，只建议 | 已有 |
| L1 | 大纲账目 + 体量预算 + 勘察笔记 + 猜想槽 | 停判前分诊 + 模式库 + 自适应步数 | 未交代不许收尾；假设驱动 |
| L2 | 加：从目录选工具 + 金丝雀 | 加：脚手架与环境修复（AST 闸内） | 工具数上限、自检、AST 闸 |
| L3 | 加：经验写回（条目提案、工具账本） | 加：模式写回 | 人工审"候选转正"；版本化 |

每级一个旗标、默认关，逐级做对照，就是论文的消融梯子。

**永远不放开**：改判决真值、改节点流转、超硬预算上限（钱）、测试容器联网、静默改基线或 oracle、自己批准新工具转正。

## 10. 前提检验与风险

动手之前先逐条挑战假设，每条给出最便宜的证伪方法：

| 假设 | 最便宜的证伪 |

|---|---|
| 基线"无知"的项目上，大纲能提高检出 | 零代码：手写两份大纲，直接拼进需求文本，在需求含糊的格上对照 10 对 10 |
| 大纲条目能可靠映射到目标符号 | 在三个不同体量的项目上看映射命中率 |
| 大项目上体量预算能提高落地率而不爆成本 | 一个 L 档项目，L0 对 L1 |
| 工具选型带来新增证据 | 挑一个明确需要专门工具的项目（如需要竞态检测的 Go） |
| 写回不会把库带偏 | 条目命中率监控加人工审转正 |

风险与对策：
- **清单化测试框住思维**：猜想槽强制大纲外假设；单独统计大纲外命中。
- **工具膨胀**：数量上限、金丝雀、账本降权。
- **自进化漂移**：版本化、人工审转正、可回滚。
- **自由度提高带来方差**：每臂样本要够（30 以上）才能不说"方向性"；钱与低价窗是硬约束。
- **模型能力**：现在全部用 flash；L1 以上的多步勘察可能需要给策略相位单独路由更强的模型，这是成本决策。
- **"为消融造基建"的老问题**：每阶段先证伪再建，能手工就不写代码。

### 13.1 数据逼出的四条设计原则

| # | 数据事实 | 设计原则 |
|---|---|---|
| P1 | 留出项目 B 臂 152 条用例（4 倍量）只 1/5 格踩中根因；三个有缺陷项目全天花板 | **广度不是瓶颈，靶点是**。大纲条目必须落成 (靶点符号, 输入构造, 预期, 依据) 四元组，纯文本清单出局 |

### 13.2 设计 v2：用"假设单"取代"大纲清单"

- **确定性边界器**（新组件，零 LLM）：从需求文本（正则抽数值区间/长度限制）与函数签名（默认值、类型）解析约束 → 确定性生成端点、越界、类型错误用例文件。这是"命中可靠性"的机制保证——corpus-001 根因这类区间缺陷从"1/5 碰巧"变成"每格必踩"。
- **假设单**（策略 agent 新产物）：每条 = {id, 靶点符号, 输入构造（可引用边界器产物）, 预期, 依据∈{需求,文档,惯例}}。生成器按假设单定向生成；惯例依据的失败由规则路由进争议区。
- **oracle 三层**：需求文本→可判缺陷；文档/注释→弱缺陷（标注）；惯例/推断→只进争议区。C7 预期依据审计复用，校准从 4-gram 收紧到"期望子句对齐"。
- **广度清单降级**为假设的话题库（维度提示），不再进需求文本。
- V8 通道（诊断可达）已验证，是争议区路由的实现前提。
