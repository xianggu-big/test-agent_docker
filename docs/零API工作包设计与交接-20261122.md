## 任务 1：BugsInPy 扩量准备层（~1 天，性价比最高）

### 目标
真仓库梯度从 n=1（tqdm bug9）扩到 10-15 bug——**全部准备层零 LLM**，充值后一键点火 ≈¥1-2。

### 对码现状

### 设计方案
1. **选 bug**：从 BugsInPy 官方 493 bug 清单选 10-15 个，筛选标准：①纯 Python 依赖（无 C 扩展编译——容器装不了）②pytest 测试（非 unittest 特殊 runner）③官方失败用例存在且在 fixed 版 ④项目体积 <50MB。已知好例：tqdm bug9。候选优先看：pandas-too-many/numpy 系（大，慎选）、requests、matplotlib（C 扩展排除）、keras（排除）——**建议选中小型纯 Python 项目**（如 tqdm 系列、black、flake8、protobuf 纯 py 部分、youtube-dl、thefuck）。
2. **manifest 批量落盘**：`data/benchmarks/manifests/bugsinpy-{repo}-bug{N}.json`，字段对齐 benchmarks.py REQUIRED_BASE + buggy_ref/fixed_ref（codeload 的 commit/tag）。
3. **staging 脚本**：`scripts/stage_bugsinpy_batch.py`——codeload 双 ref 拉取（buggy/fixed 两份）+ 官方失败用例从 fixed 版提取 + digest 封存（tarball sha256 入 manifest，防 rug pull）。
4. **P0 预检脚本**：零 LLM 跑通"buggy 必败+fixed 必过"（容器内 `mta-test:py312`，同 bench3 复演形态）。
5. **格定义**：扩 `run_bench3.py` `stage_all()` ①段为读 manifests 目录批量注册（幂等守卫已有先例：`if not (d / "buggy" / ...).exists()`）。

### 验收标准
- 10-15 个 manifest 全过 `validate_manifest`；staging 幂等（跑两次零 diff）；P0 预检全 PASS（buggy 败 fixed 过）；`run_bench3.py --precheck` 报出全部新格。

### 坑
- codeload URL 形态：`https://codeload.github.com/{owner}/{repo}/tar.gz/refs/tags/{ref}`（或 `/commit_sha`）；**BugsInPy 官方仓库的 buggy/fixed 标签在 `BugsInPy/{repo}` 镜像组织下**——先拉一个验证 tag 存在再批量。

## 任务 2：伪造网络环境（~2 天，最大工作量块，用户点名感兴趣）

### 目标
容器"有网的感觉、零真实外发"：`--internal` Docker 网络 + 桩服务器，点亮 SUT 的网络代码路径（连接/重试/超时/错误分支），测"只有有网才能测出的 bug"（重试风暴、熔断不触发、部分失败处理缺失）。

### 对码现状
- **`ensure_container`/`_run_sandbox` 无 network 参数**（`test_agent/sandbox/runner.py:163-208`）——`containers.run(...)` 未传 network，默认 bridge（外网可达）。这是本任务唯一的平台侵入点。
- 网络隔离现状（TODO-06 已验证）：默认 bridge=全通无隔离；`--network none`=全断（与 host.docker.internal DB 依赖互斥）。分级白名单是当时结论，本任务=第三档"假网"。
- 白名单闸先例：`test_connection` 的 `known_base_urls` + `follow_redirects=False`（commit d1c8c51，D 包安全边界）——桩端点注册表可挂同款治理。

### 设计方案
1. **runner 扩展**（最小侵入）：
   - `ensure_container(..., network: str | None = None)` 透传 `_run_sandbox` → `containers.run(network=network)`；docker-py 支持多网络需用 `networking_config`（单网络直接 `network=` 即可；双网络：先 `network=` 主网络创建，再 `client.networks.get(...).connect(container)`——**先建后连**两步）。
   - 旗标 `config.FAKE_NET_ENABLED`（默认 False=零变化）。
2. **网络生命周期**：`scripts/ensure_fake_net.py`——`docker network create --internal mta-fakenet`（幂等：存在即复用）；任务结束不删网络（共享资源），容器随任务清理。
3. **桩服务器**：
   - 镜像：`wiremock/wiremock:3x`（或 `wiremock` 2.x alpine）预拉取（平台侧容器可联网拉，任务容器不能——先例：D2 插件预拉取）。
   - 桩定义：JSON mapping 文件（端点→响应/延迟/故障），放 `data/fakenet/{task_type}/mappings/`，bind mount 进桩容器。
   - 启动：任务 provision 阶段（旗标开时）起桩容器 `mta-stub-{task_id}`（唯一名纪律）挂 internal 网，SUT 容器双网络：eth0=bridge（保 host.docker.internal MySQL）、eth1=mta-fakenet。
   - SUT 指向：环境变量 `API_BASE_URL=http://mta-stub-{task_id}:8080`（internal 网内 DNS 按容器名解析——这是"有网的感觉"的机制）。
4. **契约生成 mock（可选加分）**：OpenAPI spec 喂 WireMock（或 Prism）自动生成 mapping——平台黑盒契约轨的 spec 提取链路现成（`_walk_spec_files` OpenAPI 分支），提取物直接变桩定义。
5. **故障注入**：WireMock 原生支持延迟/固定延迟/故障响应（mapping 里 `fixedDelayMilliseconds`/`fault: CONNECTION_RESET_BY_PEER`）——不用额外引入 toxiproxy，第一版不做。
6. **端点注册表**：桩端点进治理——`test_connection` 白名单扩"stub:" 前缀端点（known_base_urls 加桩注册，留痕可审计）。

### 执行步骤
1. runner network 参数+单测（fake client 断言 network 透传）→ 2. ensure_fake_net.py+真机 network create 幂等 → 3. 桩容器手动起一个+curl 验证 internal 网内可达、**宿主外发验证不可达**（`docker run --network mta-fakenet curl 外网` 应失败=隔离实证）→ 4. 双网络挂载验证 host MySQL 仍通 → 5. provision 接线（旗标开才走）→ 6. 端到端：一个假 API 项目（如 jsonplace-demo）在桩后跑全链路 → 7. 关态逐字节锁测试。

### 验收标准
- 旗标关=现有全量回归绿（逐字节不变）；旗标开=桩后任务全链路 PASS 且 `docker run --network mta-fakenet` 外发被拒（隔离实证留档）；故障注入 mapping 生效（SUT 收到 CONNECTION_RESET）。

### 坑
- **internal 网的 DNS**：容器名互相可解析=internal 网行为，别用 IP 硬编码。
- **Windows Docker Desktop**：network create 幂等用 try/except NotFound，别 shell out。
- 双网络 `connect` 是容器运行后调用（`client.networks.get("mta-fakenet").connect(c.id)`）——docker-py 的 connect 在容器 created/running 均可。
- 桩容器也要唯一名+任务结束清理（复用 runner.cleanup 同款）。

## 任务 3：per-test 粒度超时（半天，趁 bench3 死循环格热灶）

### 目标
修"一轮 1 条挂死用例丢整轮 10 条结果"的缺口：挂死只杀那一条（记 failed+Timeout 证据），其余用例结果保住，repair 下一轮不替挂死用例付时钟。
**活案例（第四轮实锤，做之前先读）**：`find_first_in_sorted` 格官方 bug=`while lo <= hi` 死循环边界（**类① buggy 独挂=最强检测信号形态**），但整轮 90s 超时杀 pytest 后 junit 未落盘 → buggy 侧 failed=0 → **挂死证据蒸发、判 not_detected**；同格 replay 67 条全过（用例本身健康）。即：整轮超时口径下"挂死即证人"落不了账——per-test 超时是唯一能把类①信号记进 junit 的机制。验证素材=该格 staging 现成（`data/benchmarks/staging/quix-find_first_in_sorted/`）。

### 对码现状
- Python 命令构造：`test_agent/graph/nodes.py:53` `build_run_cmd`（pytest，`--junitxml` 已有）；JS 版 :68 `build_run_cmd_js`。
- 轮超时：`config.DEFAULT_JOB_TIMEOUT_S=600`（config.py:83）被 `exec_in` 消费（nodes.py:1631 附近）；bench3 已实证驱动器侧可改写（`BENCH3_ROUND_TIMEOUT_S`，run_bench3.py）。
- junit 解析：`test_agent/skills/case_results.py`（`parse_junit_xml` :18）——pytest-timeout 超时的用例在 junit 里= `<failure type="Timeout …">`（走既有 failed 路径，解析器零改动预期）。

### 设计方案
1. **插件**：`pytest-timeout`（`--timeout=N --timeout-method=thread`；signal 方法与容器兼容性差，thread 稳）。**装进镜像**：`docker/python-test/Dockerfile` 加 `pip install pytest-timeout`（构建时联网）+ rebuild；离线验证=`docker run mta-test:py312 python -c "import pytest_timeout"`。
2. **命令注入**：`config.PER_TEST_TIMEOUT_S`（默认 0=关，零变化）；`build_run_cmd` 在 >0 时追加 `["--timeout", str(n), "--timeout-method", "thread"]`。
3. **关系约束**：per-test 必须 << 轮超时（建议 per_test=轮超时/10）；文档写明分层：per-test 杀单条 → 轮 timeout 兜底杀全轮 → worker 封顶杀整格（bench3 三层实战已验证后两层）。
4. JS 侧不做第一版（jest 无原生 per-test timeout CLI，`jest.setTimeout` 需改代码——挂账）。

### 验收标准
- 关态命令逐字节不变（测试锁）；开态：构造 1 条 `while True: pass` 挂死用例+9 条正常用例的单测 fixture——挂死那条 failed（Timeout 字样进 junit message），其余 9 条 passed 出现在 test_case_results；轮总耗时 ≈ per_test 超时而非整轮烧穿。真机验证直接复用 bench3 的 `wrap` 格 staging（两版共挂边界现成）。

### 坑
- `--timeout-method=thread` 下挂死线程可能残留到进程退出（文档如实注明：线程法不保证回收，但 junit 结果完整——证据优先）。
- pytest-timeout 与 `--cov` 共存无冲突（官方支持）。

## 任务 5：AgentLoop finish 引导迭代（~1 天，重测点火才花钱）

### 目标
修 2×2 实验的核心发现："deepseek-chat 单轮倾向重复观察调用而非 finish"（策略产物零出现=模型光看不下结论）。提升 DECIDE 节点输出 finish 的比率与质量。

### 对码现状
- 循环骨架：`test_agent/skills/tool_loop.py`（JSON action 协议 call/finish；:126/:204/:212 已有"预算耗尽强制 finish"硬闸+观察子预算；重复动作指纹闸已有——连续拒/重复停）。
- 提示词：`AGENT_DECIDE_SYSTEM`（prompt_library.py）——v0 只给了协议，没给"何时该 finish"的判定锚。
- 实验读数：`docs/AgentLoop-2x2实验报告-20261121.md`（B 臂策略产物零出现；agent 账本 denied=0=不是被拦，是不 finish）。

### 设计方案（v1 引导，预注册判据）
1. **finish 判定锚**（DECIDE 系统提示词加三问）：调 finish 前自问——①我已有的观察足够回答策略问题吗 ②再观察一次会改变结论吗（不会=必须 finish）③步数预算还剩多少。已有 :126 的 obs 尾注扩展成**每步都带**（"已用 X/Y 步，剩余观察 Z 次"——冒烟轮 1 修过步数提醒，但只在特定分支）。
2. **重复观察惩罚**：fingerprint 重复时 obs 里明示"该观察已看过（第 N 次重复），重复观察不再提供新信息"（现在 denied 留痕但下次提示词里看不到重复计数）。
3. **finish 示例锚定**：DECIDE 系统提示词加一个最小 finish 示例（对照示例强于负面清单——防御矩阵 P2 结论复用）。
4. **判据预注册（重测时用）**：①finish 比率（denied_for_repeat 计数↓）②策略产物非空率（B 臂核心读数）③步数分布（≤5 步自停维持）④检出不退化（J1 锚）。重测=2×2 的 B/D 臂各 3 格 ≈¥1.5（充值后）。
5. 实现+单测零 API；真机冒烟 1 格 ≈¥0.05 可延后到充值后与重测合并。

### 验收标准
- 提示词两态测试（引导开/关的 DECIDE 构造逐字节对比）；单测：重复计数进 obs/步数提醒全分支/finish 示例存在；`pytest tests/test_tool_loop.py` 全绿。

### 坑
- 提示词改动会影响 2×2 可比性——**必须版本戳**（prompt v1 标记进 llm_calls 元数据或报告注明），历史对照写清"v0 vs v1"。
- 别动 call 协议本身（JSON action 不走 function calling 是对码定论）。
