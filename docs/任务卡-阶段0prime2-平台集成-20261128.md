## 5. 判读结果（2026-11-28 下午，25 格三批）

**最终判读：I1/I4 过、I2 名义过实为空过、I3 不过——两个平台级缺口被本实验钉死。**

| 批 | 格 | 结果 |
|---|---|---|
| v1 整文件注入 | 15 | corpus-001 全过（I1 实质成立：7 条边界用例执行、0 NameError、2 条失败=根因 len=64、5/5 格疑似缺陷上报）；REST 全废（见缺口①） |
| v2 逐函数拆条注入 | 10 | coupon 8 条边界用例**全过零误报**（I2 实质成立）；corpus-003 注入用例 **0 条执行**（缺口②） |

**缺口①（A5 def 名对齐的适用边界）**：cases API 插入时无条件把代码里第一个 def 重写为用例名
（server.py:1293-1295）。多函数文件注入时第一个 def 恰是 fixture（REST v1 实锤：`def c():`→
`def test_boundary_auto():`，全部用例悬空）→ 被顺延收集闸整案废案。
**缺口②（"库为准"重建漏了 imported 用例）**：修复轮的布考场重建只重写 test_gen%（gen_tests
rebuild 范围），test_imported.py 不在重建清单 → 注入用例在第一次 repair_gen 后从工作区消失
（corpus-003 v2 实锤：0 条 bnd 行、ws 无 test_imported.py）。克隆路径有重建（nodes.py:855-866
仅 rmtree 重跑触发），修复轮路径没有。

**判读口径修正（应变记录）**：I3 v1 的"终态文件哈希"锚错（平台设计=库为准每轮重建，文件消失
≠内容被改写）；v2 改行为验证（三靶失败出现+零 NameError）。I2 首判为空过（0 行=0 失败的假
pass），v2 后有实质数据。

**总结论**：边界器内容本身全部成立（lib 注入真检出根因、REST 用例在干净项目全过、语义哈希
证明库内内容与注入源仅换行差异）；**卡点不在边界器，在平台的用例插入/重建机制**。两个缺口
都是真 bug（同样影响现有 fixture 机制在修复轮的行为——此前夹具格没暴露是因为没进修复轮）。

**修复方向（待拍板，均为小改）**：①A5 重写只作用于"单 def 用例"或仅重写 test_ 前缀 def；
②修复轮重建补调 _rebuild_imported_file（库为准哲学的自我修复）。修完重跑 0'' REST 十格
（≈¥0.4），全过即进假设单。

**修复方向（待拍板，下一会话 fresh context 执行）**：①顺延收集闸移到 install_deps 之后；
