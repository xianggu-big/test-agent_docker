## 二、测试发现并修复的 5 个真 bug

| # | 层 | bug | 根因 | 修复 | 回归锁 |
|---|---|---|---|---|---|
| 1 | 提取 | paths 非字典 → AttributeError 崩 | `spec["paths"].items()` 无类型守卫 | isinstance 守卫返回空 | test_spec_paths_not_dict_does_not_crash |
| 2 | 提取 | 204 无响应体端点 success_code 错回 200 | 只在有 JSON content 时记码 | 首个 2xx 即记码、schema 独立置空 | test_allof_and_missing_content… |
| 3 | L2 图 | skipped leg 终写为 failed | report 节点 `ok = verdict=="pass"` 二分法 | 三态映射 pass→done/skipped→skipped/else→failed | T3 真机覆盖 |
| 4 | **生成器** | **同名 def 静默覆盖前案（丢用例）**：两条必填缺失负例生成同名函数，后者覆盖前者——缺失 code 的用例从未被执行 | `_emit` 每次传 fresh `set()` 给 _sanitize_name，跨用例去重失效 | 三个渲染器各持持久 used_names | test_rendered_function_names_all_unique（生成物函数名两两不同） |
| 5 | **生成器** | 边界负例只测"第一个有边界的字段"：percent 上限失效（V1）因 code 的 maxLength 先占坑而漏检 | 负例选择策略单字段 | 逐字段边界越界（每个有界必填各一条，预算封顶内） | test_negative_variants_kinds_and_budget（percent=101 断言） |

**方法论教训（进论文可写）**：bug #4 的隐蔽性极强——DB 台账记录了 4 条负例（cases 落库在写盘前）、单测只验证"能编译"、首次真机冒烟"看起来 11 过 1 败很合理"——三层检查全被瞒过。是**注入已知缺陷的标定法**（mini-E6，期望 3 缺陷全被抓）暴露了"该失败的负例没失败"这一矛盾。**"期望检出清单"与"实际检出清单"做差集，是发现用例集静默缩水的唯一手段**——这与 L1 的 E4 变异标定同哲学：通过率/覆盖率不说谎的前提是用例集本身没缩水。

## 三、修复后的最终标定数字

- 干净 demo（含 1 个故意埋的订单不持久化缺陷）：**11 过 / 1 败**（埋的缺陷=唯一失败，0 误报）
- 变异体（3 个注入缺陷，订单正确实现）：**10 过 / 4 败**（3 缺陷全检出：V2 负例 1 + V1 负例 1 + V3 双轨 2，0 误报）
- 无 Key：12 条契约用例照跑、llm_calls=0、检出力不降（缺陷为契约级）
- 无 spec：诚实 skipped，不产生任何噪音用例

## 四、遗留与边界

- L2 需求断言轨对"自洽恒真型"计算缺陷（total=amount-discount 同源自洽）无检出力——需要 LLM 生成独立计算式断言（V7 断言独立性同源问题），列语料 v2/E6 设计输入
- API 下发路径（LEVELS_ENABLED=True → _run_worker）与 run_task_levels 内部等价（同一函数），未单独起服务测——界面四级视图属 P2 时一并 E2E
- spec 含 allOf/oneOf 组合 schema 时 example 生成退化（P1 边界，诚实路径=用例变少而非出错）
