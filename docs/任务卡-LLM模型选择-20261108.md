## 2. 设计定稿（已拍板）

### 2.1 Profile 数据模型

```
provider: "deepseek" | "qwen" | "local" | "custom"
base_url: 云端=预设值；custom=用户填（http/https 校验）
model:    云端=预设值可改（如 deepseek-chat / qwen-plus）；local=qwen3-4b-inst-test；custom=用户填
key_env:  key 所在环境变量"名字"（deepseek=DEEPSEEK_API_KEY，qwen=DASHSCOPE_API_KEY，
          local=空=不需要 key，custom=用户填变量名）
```

**铁律：数据库只存 key_env 变量名，永不存 key 本体**（SQLite 文件会进备份/交接，明文密钥=泄漏面）。key 解析 = `os.environ.get(key_env)`；未配置 → 现有"无 Key 诚实降级"路径照走，文案改为"未配置当前模型的 API Key（profile={provider}，环境变量 {key_env}）"。

### 2.2 存储：`app_settings` 第 32 表

```sql
CREATE TABLE IF NOT EXISTS app_settings (
  id INTEGER PRIMARY KEY AUTOINCREMENT,
  key TEXT NOT NULL UNIQUE,          -- 'llm_profile'
  value TEXT NOT NULL,               -- profile JSON（provider/base_url/model/key_env）
  updated_by TEXT,
  updated_at TEXT NOT NULL DEFAULT (datetime('now'))
);
```
- docs/layer5-data-schema.sql 增表 + `_MIGRATIONS` 老库自动补表；**守卫 module_check 表数契约 31→32 同步改**（这是验收项不是可选项）。
- 首次启动无该行 → 不应用任何覆盖，行为与现在完全一致（默认 deepseek = config 现值），老任务/老测试零感知。

### 2.3 接线：profile 应用 = 运行时改写 config 模块属性 + make_chat 兜底

新模块 `test_agent/skills/llm_profile.py`：
- `PRESETS`: 三档预设定义（qwen 预设 base_url 用 DashScope 兼容模式 `https://dashscope.aliyuncs.com/compatible-mode/v1`、模型名预设 `qwen-plus` 可改——以 DashScope 兼容模式文档为准）；
- `current(conn=None) -> dict`：读 app_settings（无行=默认 deepseek）；
- `apply(p, conn) -> None`：校验 → 写表 → **运行时改写 `config.DEEPSEEK_BASE_URL / DEEPSEEK_MODEL` 模块属性**（立即全局生效，不需重启；GIL 下赋值原子，调用点逐 invoke 读取）；
- `apply_saved_if_any()`：init_db 时调用（**延迟导入防循环依赖**——db.py 不能顶层 import skills），进程启动即恢复上次选择；
- `resolve_key(p) -> str | None`：按 key_env 读环境变量；local 恒返回 "ollama"（不校验）；
- `test_connection(p) -> dict`：60s 超时发一条 `输出 {"ok":true}` 的最小 JSON 指令，返回 `{ok, latency_ms, reply 或 error}`——local 无 ollama 时给可行动文案"请先启动 ollama serve"。

**调用点改造（本卡最大面积但纯机械）**：16 文件的 `make_chat(model=config.DEEPSEEK_MODEL, api_key=..., base_url=config.DEEPSEEK_BASE_URL, ...)` → `make_chat(temperature=..., ...)`（三件套不传）；`make_chat` 内部 `kwargs.setdefault("model", config.DEEPSEEK_MODEL)` / `setdefault("base_url", config.DEEPSEEK_BASE_URL)` / api_key 未传时 `llm_profile.resolve_key(current())`。**显式传参仍优先**（逃生口，ai_reviewer 的 per-role 模型因此零改动）。各调用点散落的 `os.environ.get("DEEPSEEK_API_KEY")` 无 Key 判空 → 改用 `resolve_key` 结果，文案按 §2.1 更新。

### 2.4 API 契约（server.py）

- `GET /api/llm-profile`（staff）：当前 profile + presets + `key_present`(bool，只报"已配置/未配置"不回显值) + updated_by/at；
- `POST /api/llm-profile`（**admin**）：切换并 apply；caller 403；返回应用后的完整 profile；
- `POST /api/llm-profile/test`（staff）：body 可带临时 profile（不落库）测连通性，返回 §2.1 的 test_connection 结果；
- `/api/config` 的 `llm_base_url/llm_model` 改为返回运行时现值；note 文案更新为"预算值仍冻结；LLM 模型可在设置页切换（实验数据以 llm_usage 台账记录的实际模型为准）"。

### 2.5 前端（设置页新卡）

"LLM 模型"卡：当前生效徽章（provider+model）+ 三张预设卡（点击选中，local 卡标注"需本机 ollama serve"）+ 自定义表单（base_url/model/key_env 三输入框）+【测试连通性】【应用】两按钮（结果就地显示，不弹窗——抽检反馈闭环的教训）；key 一律只显示"环境变量 {key_env} 已配置/未配置"徽章，永不回显值。

### 2.6 诚实纪律（不可妥协）

1. **切换留痕**：app_settings.updated_by/at + server log `[llm-profile] 切换 → provider/model`；实验数据口径以 `llm_usage` 台账实际 model 为准（已有字段，确认其记账路径在切换后确实取到新值——写一条单测锁）。
2. **备胎互斥**：当前 profile 为 local 时 `RobustChat._try_fallback` 直接跳过（同端点降级无意义）；其余 profile 备胎行为不变。
3. **预算值冻结不动**：只许改 LLM 三件套的运行时值；coverage_target 等预算的"只读"语义原样保留。
4. **冒烟先行**：真机验证顺序 = 先 POST /test 打通每档 → 本地 local 档跑一个最小任务（data/demo/场景A）全链路 → 查 llm_usage 与 agent_messages 确认模型实际生效。

### 4.1 验收后补丁：task 675 的 401 与内存漂移（用户实测抓出，已修复）

**现象**：674/675（deepseek 档建任务）死于 DashScope 401 invalid_api_key——deepseek key 发到了 qwen 端点。

**根因（apply 的运行时改写只作用于执行它的那个进程）**：673 切 qwen 经 server API → 长驻 server 进程内存 `config.DEEPSEEK_BASE_URL=DashScope`；随后验证脚本在自己进程里切回 deepseek（**表**回了 deepseek，server 内存没动）→ 674/675 的 make_chat 兜底 base_url 取**被污染的 server 内存**（DashScope）、api_key 兜底取**表**（deepseek key）→ key 与端点错配。

**修复（commit 见 git log）**：make_chat 三件套兜底统一走 `current()`（**app_settings 表=唯一真源**，无行=默认 deepseek config 现值），不再读进程内存 config——表与内存漂移从机制上消灭；单测新增漂移免疫回归（内存被污染为 qwen、表为 deepseek → 兜底必须取表值）。复现验证：task 676（deepseek 档 Go 项目 go-shop）五阶段 llm_usage 全记 deepseek-chat，401 消灭。

**遗留观察**：server 进程的 `[llm-profile] 切换` log.warning 未出现在 uvicorn 日志（logging handler 配置问题，切换留痕由 app_settings.updated_by/at 兜底满足卡纪律）；`os.environ.get("DEEPSEEK_API_KEY")` 残留 7 处（builder/builtin/evaluate/preflight/nodes repair——显式传参优先语义下无害，但 profile≠deepseek 时这些显式 key 会覆盖 profile key 与 profile 端点错配，**统一收敛为 effective_key() 属后续卫生轮**）。
