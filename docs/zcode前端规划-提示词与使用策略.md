# zcode 前端规划提示词：按设计图分析并规划前端开发（2026-10-31）

> 用途：把一张/一组界面设计图（或原型 HTML）交给强模型，让它先做**视觉解析**，
> 再对照现有前端与后端能力做**差距分析**，最后产出**可按图施工的前端计划 + 任务清单**。
> 关键：图片是设计权威，但不能让模型编造后端数据；缺 API 的要列为后端依赖。

## 一、先确认"图片"是哪一份

- 如果图片是外部设计稿/截图：在 zcode 任务里作为附件上传，提示词里写"以附件图片为准"。
- 如果指的是仓库里的 `docs/界面原型-四级测试平台.html`：把它当设计基准，先渲染/截图再分析。
- 如果两者都有：**以图片为准，HTML 原型只作交互参考**；冲突时在报告里列"设计冲突待确认"。

## 二、可直接粘贴的主提示词

```text
你是前端架构师 + 设计系统工程师 + 产品设计师。项目目录 D:\test agent_docker。
附件是我的前端设计图（若附件缺失，则以 docs/界面原型-四级测试平台.html 为准并先说明）。
任务：按图分析并制定前端开发计划，最终让现有系统界面尽可能贴近设计图，同时保持真数据、
不破坏现有功能。你要尽可能多做实际分析，不要只给风格建议。

【最终目标】
1. 逐页/逐区域还原设计图的布局、层级、间距、颜色、字体、组件与交互；
2. 所有展示数据来自现有后端真实接口；缺接口的列为后端依赖，禁止前端造假数据；
3. 保留现有 L1 界面能力（新建/工作台/任务列表/报告/设置）与四级视图；
4. 桌面/平板/手机三档可用，空态/错误态/加载态/无权限态齐全；
5. 用 Playwright 截图对照 + 0 控制台错误作为验收证据。

【硬约束】
- 本轮只做分析与规划，不改产品代码；允许写 3 个规划产物（见交付）。
- 不装前端框架/构建链；现有技术栈是 FastAPI + 原生 HTML/CSS/JS（test_agent/api/static/）。
  若设计图必须引入依赖，先给"最小依赖方案 + 不引入的替代方案"两套对比，不擅自决定。
- 不编造后端字段/接口；每个数据展示项必须映射到现有 API 或标"需后端新增"。
- 不破坏已有页面路由与鉴权；不把演示假数据写进前端。
- 只引用真实存在的文件；不确定的标"未验证"。

【必读】
1. 设计图/原型：附件图片 或 docs/界面原型-四级测试平台.html；
2. 现有前端：test_agent/api/static/index.html、app.js、style.css；
3. 后端能力：test_agent/api/server.py 的路由清单；docs/layer5-data-schema.sql；
4. 项目口径：README、AGENTS、docs/四级双轨测试框架研究规划.md §11、docs/论文写作蓝图；
5. 现有四级数据接口：GET /api/tasks/{tid}/levels、/trace、/report、/rtm、/scenarios。

【执行流程（必须按阶段产出）】
阶段 0 视觉解析（先只描述图，不规划）：
- 画布尺寸/栅格/断点；页面区域划分与层级；
- 颜色 token（背景/卡片/文字/主色/成功/失败/警告）、字号字重、圆角/阴影/间距；
- 组件清单：导航、任务头、级别卡、流水线、溯源链、缺陷表、指标条、按钮、徽章、空态；
- 交互与状态：hover/active/disabled/loading/empty/error、折叠/展开、响应式变化；
- 输出"设计规格表"：区域 → 尺寸/间距/颜色/字体/组件 → 备注。

阶段 1 现状对照（必须读代码）：
- 现有页面/路由/组件清单；每个设计元素对应到 index.html/app.js/style.css 的哪个位置；
- 数据映射：设计图每个数字/列表 → 现有 API 字段 或 "需后端新增"；
- 差距表：设计元素 → 当前实现 → 差距类型（缺/样式不符/交互不符/数据缺）→ 严重度；
- 明确哪些设计图元素当前后端给不了（例如某类缺陷分组/实时进度/多容器视图）。

阶段 2 前端计划（按图施工）：
- 组件拆分：复用/改造/新建；每个组件写文件位置、props/数据来源、状态；
- 页面与路由计划；响应式断点；设计 token 落到 CSS 变量；
- 任务粒度 ≤1 个 Agent 会话（2-3h）；每个任务写：
  ID、目标、涉及文件、依赖 API、完成判据、Playwright 验收脚本/截图对照、降级方案；
- 排序：先"不可砍"（四级卡/溯源链/报告页/真数据），再视觉打磨，最后动效/SSE；
- 明确"保答辩砍单清单"：时间不足时先砍哪些装饰性内容。

阶段 3 自检/红队：
- 图片里每个区域是否都有对应组件/任务？漏一个就补；
- 是否有任务在造假数据或依赖不存在的 API？
- 移动端是否会溢出/遮挡？空态/错误态是否覆盖？
- 现有页面是否会被破坏？鉴权/角色差异是否处理？
- 按 5 条修订后再交。

阶段 4 交付 3 个文件（只写这 3 个）：
1. docs/前端设计分析-20261031.md：设计规格表 + 组件清单 + 现状差距表 + 页面/路由计划 + 任务表 + 砍单清单 + 验收清单；
2. docs/前端任务清单.json：id/phase/title/files/apis/deps/acceptance/verify/estimate/priority；
3. docs/前端首3日执行包.md：未来 3 天逐任务可直接复制给下一轮 Agent。
最后对话只回：设计图关键信息、Top5 差距、首 3 日任务、3 个文件路径。

【质量门槛】
- 每个设计区域必须映射到组件与任务；每个任务必须有完成判据 + 截图/Playwright 验收；
- 每个数据项必须有 API 来源或"需后端新增"标记；
- 至少 20 个任务，至少 8 个 P0/P1；
- 不允许"美化一下/优化体验"这种无验收任务；
- 先给设计规格表，再给计划；顺序颠倒就重做。
```

## 三、如果模型只给"风格建议"，追加这段

```text
重做。你刚才没有按图施工。必须补：
1. 设计规格表：每个区域的宽高/间距/颜色/字号/组件；
2. 组件清单：复用/改造/新建，对应到 index.html/app.js/style.css 的具体位置；
3. 差距表：设计元素 → 当前实现 → 差在哪 → 任务 ID；
4. 每个数据项的 API 来源；缺接口的写"需后端新增"，不许编；
5. Playwright 截图验收：1440/1024/390 三档 + 0 控制台错误 + 空态/错误态。
按这 5 条重写，不要保留原来的空泛段落。
```

## 四、验收时看什么

- 有没有"设计规格表"（不是"现代简约/科技感"这种形容词）。
- 每个设计区域是否都有组件和任务；任务是否有文件、API、完成判据、截图验收。
- 是否明确列出"后端给不了的数据"，而不是前端硬编码。
- 是否有响应式三档与空态/错误态/加载态任务。
- 是否保护现有页面与鉴权，是否有"不引入框架"的替代方案。
- 首 3 日执行包是否能直接交给下一轮 Agent。
