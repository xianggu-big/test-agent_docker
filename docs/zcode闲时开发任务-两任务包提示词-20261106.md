# zcode 闲时开发任务：两任务包提示词与使用策略（2026-11-06）

> 目的：用 zcode 每日免费额度，无人值守推进《黑盒能力补齐任务包-20261106.md》与
> 《多语言工具链接入任务包-20261106.md》。每天跑一次，每次接续上次进度，验收闭环驱动：
> **实现 → 测试 → 验收 → 不过返工，直到通过或确认外部阻塞才允许停**。

## 一、与体检任务的关键区别（3 条）

1. 体检是只读，本任务是**写代码**——但护栏更严：每阶段独立 commit、真实库/工作区/实验数据零接触。
2. 两个任务包总量约 25 天工作量，一天额度跑不完 → **台账断点续跑是生命线**：进度、证据、阻塞全部落
   `.autonomous-loop/dev-ledger-20261106.md`，每天从台账恢复，禁止凭记忆或重读文档重新决策。
3. 用户要求"做完必须测、不过必须返工"→ 提示词内置**验收闭环**，同时设诚实出口：
   只有外部阻塞（拉镜像失败、需人工决策）允许挂起，禁止静默降级、禁止为过测试改断言。

```text

【单阶段执行流程（任务包里的六步/五步，一步都不许省）】
1. 前置调研：按任务包 S1 要求核验开源方案（报告格式/工具），结论写进台账该阶段条目。
2. 先写失败测试或最小 demo（证明"现在确实没有这个能力"），留"修复前失败"证据。
   黑包各阶段须对照任务包"测试矩阵"一节的清单补齐单测（正例+负例，负例先行）——
   测试矩阵列的每条单测都是该阶段交付物，缺一条不算完成。
3. 最小实现：严格按任务包方案，不顺手重构、不加任务包没要求的功能。
   任务包该阶段【方案】里点名的全部交付物（代码、表、skill、API 端点、demo、
   要求记录的成本/复验数据、写回任务卡的调研结论）都属于实现范围，缺一个就是没做完。
4. 测试三连：新测试通过 + python -m pytest -q 全绿 + python scripts/module_check.py 无失败。
5. 按任务包该阶段的【验收】条目逐条真机验证，证据（命令+关键输出路径）写进台账。

【验收闭环规则（核心，必须严格执行）】
- 验收任何一条不过 → 回到实现步修复 → 重跑测试三连 → 重验，循环直到通过。
- 返工上限：单阶段最多 4 轮；第 4 轮仍不过，停下分析根因：
  属外部阻塞（网络/镜像/需人工决策/额度耗尽）→ 台账记录阻塞详情并挂起，允许结束本轮；
  属自身能力不足 → 必须继续修，禁止挂起逃避。
- 判定"完成"的唯一标准：测试三连全绿 + 验收条目逐条通过 + 证据落台账 + commit 完成。
  四者缺一不可，禁止"基本完成/大致可用"之类的表述。

【额度管理】
- token 是免费额度，不要为"省着用"提前收尾：能多推进一个子步就多推进一个，
  持续跑到额度真正耗尽为止。
- 额度触顶信号（响应被截断/调用报错）出现时：立即在当前子步边界收尾——
  更新台账（含已完成步+下一步入口）、commit、结束本轮。
- 唯一禁止项：开了新子步却烂尾不记录。收尾纪律是防烂尾的，不是省钱的。
```

## 三、你每天怎么验收 zcode 干的活

1. 看台账 `.autonomous-loop/dev-ledger-20261106.md`：标记"已完成"的阶段必须有**证据路径**
   （验收命令+输出文件），没有证据的"已完成"视为作弊，打回重做。
2. 抽查 commit：`git log --oneline`，每个已完成阶段应有独立 commit，diff 范围与任务包方案吻合。
3. 亲自复跑一遍测试三连：`python -m pytest -q` + `python scripts/module_check.py`，
   绿了才算数（这是防"为过测试改断言"的最终防线）。
4. 对照任务包【验收】条目手工抽查 1-2 条（如：真机插一条用例→下发→真实执行通过）。
5. 发现静默降级（验收没过却标完成、阻塞没记录就跳阶段）→ 在台账写"打回"批注，
   下一天提示词开头 zcode 会读到并优先返工。

## 四、策略提醒

- **不要**在同一天让它跨阶段作业（"顺手把下个阶段也做了"）——烂尾风险远大于收益。
- 白包阶段 2（Java）最重（5 天），预计会跨 2-3 天额度，台账子步粒度就是为这个设计的。
- 黑包阶段 3（Playwright 镜像）和阶段 2（mariadb 镜像）依赖 docker 拉镜像，若 zcode 环境
  网络受限会自动触发挂起机制，属预期行为，不算失败。
- 两包全部完成后：删掉 zcode 里的这个每日任务，台账归档。
