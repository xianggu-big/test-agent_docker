> **位置**：检查 → 设计 → 测试 的第三步。依据 `docs/AgentLoop-设计报告-20261126.md`。

## 0. 流程

```
阶段 T  实现修复项 + 写脚本和驱动器（零 API，随时可做）
   │
18:00 闸  没到 18:00 就起一个等待进程；到了立即点火
   │
点火    P0 冒烟 → P1 诊断夹具 → P2 策略规模化 → P1b 三闸对照 → P3 多语言抽样

自动分析  跑指标脚本 → 写结果报告 → 逐条判预注册判据 → 默认开或保持关
```

## 3. 18:00 闸

**点火时刻** = 同时满足两条的最早时刻：

- 不早于任务四开工当天的 18:00:00；
- 处于低价窗（00:30–09:00、12:00–14:00、18:00–次日 00:30）。

**轮到任务四时按这个顺序做**

1. 先做阶段 T。这些不花钱，随时可以做。
2. 阶段 T 做完时看时间。已过 18:00 且在低价窗，立即点火。否则算出距点火时刻的秒数 N，**起一个后台等待进程**（`python scripts/wait_until.py --hhmm 18:00`，内部就是算出 N 然后 `time.sleep(N)`，用后台方式运行，结束时会被通知），并在台账记一行"等待中，将于 HH:MM:SS 点火"。
3. 等待结束了但阶段 T 还没做完，做完立即点火。
4. 等待进程被会话中断杀掉，新会话读台账，重新执行第 2 步（N 重新算）。

**四条禁令**

- 不用轮询空转来等。
- 不用前台 sleep。25 秒以上的前台等待会被拦。
- 不为了省等待而提前点火。
- 等待期间不并行做别的任务。

## 4. 点火序列

**启动生产 server**：以 `MTA_AGENT_LOOP=1 MTA_RUN_LEDGER=1` 启动（当前 server 未运行；若在运行，确认无在途任务后重启）。放格前自检 `GET /api/runs` 返回账本已开。

| 级 | 内容 | 格数 | 估费 |
|---|---|---|---|
| P0 | 冒烟：黄金演示 live 1 格，加诊断夹具 D1 1 格 | 2 | ≈¥0.15 |
| P1 | 诊断夹具：3 类 × 3 次，js-calc | 9 | ≈¥0.45 |
| P2 | 策略规模化：js-calc、go-api-book、coupon-api 各 15 格，需求逐字复用基线 #1156、#1159、#1155 | 45 | ≈¥2.0–2.7 |
| P1b | 同样的 9 个夹具，开着归因三闸再跑一遍（`MTA_ENV_GATE=1 MTA_DIFF_GATE=1 MTA_FLAKY_RERUNS=3`，需要再重启一次 server） | 9 | ≈¥0.45 |
| P3 | bench3 语料分层抽样 | ≤30 | ≈¥1.2–1.5 |

按 P0、P1、P2、P1b、P3 的顺序放。后两级是尽力而为：预算不够就不跑，报告里如实写。

### 4.1 P0 冒烟的放行检查

全部满足才放量。不满足就修，修完重跑 P0，最多 2 轮：

- 黄金演示那一格：驱动器原有判据全过；账本四表齐。
- 策略循环的 finish 摘要里，点名了至少一个被测源码里真实存在、且需求原文里没有的符号。这一条证明模型真的看到了代码。
- 夹具 D1 那一格：第一轮判定是补测，账本里有诊断循环，诊断类别是 `scaffold_error`。

### 4.2 诊断夹具

| 代号 | 植入什么 | 设计类别 | 期望 |
|---|---|---|---|
| D1 脚手架错 | 用例体里 `require` 一个不存在的模块 `./calc_nope` | `scaffold_error` | 类别对；置信 medium 或 high |
| D2 预期存疑 | 对正确的行为断言一个错误的预期，依据标"常识" | `expectation_dispute` | 类别对 |
| D3 零执行 | 植入的用例全是 skip，文件里没有可收集的用例 | `scaffold_error`（收集失败） | 类别对；置信 medium 或 high |

**做法**：建两阶段任务（js-calc，需求用基线 #1156 原文）→ 确认 → 等阶段一停在待审查 → 用接口把 AI 出的用例全部停用，植入夹具用例 → 放行阶段二 → 等终态 → 读账本。标签写在 `data/reports/agentloop_scale/fixture_labels.json`。

**路由自检**：每一格先确认第一轮判定确实是补测、账本里确实有诊断循环。两条不满足，这格记"夹具未触发"，不进分母也不算失败。

**夹具调形态**：P0 里 D1 没触发诊断，允许在同一设计类别内调整植入形态，最多 2 次。仍不触发，这一类记"无法构造"，准确率的分母相应减少，报告里写明。

### 4.3 每一格的完整性判据

与测量批一致，外加一条：运行行齐全；`agent_steps` 行数等于循环步数；循环的 `llm_calls` 行 100% 能经 `llm_call_id` 关联；`duration_ms` 非 0；至少一条步骤的证据文件确实存在。

### 4.4 什么时候算"跑完"

P0 到 P2 全部终态，或者被停车线、402 熔断、高峰闸终止。满足即进入自动分析，不等待。高峰闸的规则：次日 09:00 起不再放新格，在途的跑完。

## 5. 自动分析

最后一批格子终态、队列空了之后立即做，不等任何人。

1. 跑 `python scripts/agentloop_kpi.py`，范围是点火时刻之后的全部格子，基线取 v1 测量批（2026-11-25 03:00–05:00 的 30 格）。产出数据附件 JSON。
2. 按下面的模板写 `docs/AgentLoop-大规模测试-结果报告-<日期>.md`：
   1. 概览：格数、花费、时长
   2. 放量过程：每一级放了多少、停在哪里、有没有事故
   3. 预注册判据逐条判定表
   4. strategy：S-K1 到 S-K6，附 10 条样例策略（好 5 条、差 5 条）
   5. diagnose：D-K1 到 D-K5，附逐格判定表
   6. 成本与耗时：v3 对 v1 盲跑
   7. P1b 的三闸触发分布，以及它与诊断类别的对照
   8. 决定：默认开，还是不开，理由是什么
   9. 遗留与建议
3. 按 §6 逐条判定。
4. 执行决定（见 §6 末尾）。
5. 写 AGENTS.md 状态行，提交。

**样本不足**：某一轨没跑够，这一轨的判据记"未验证"。有"未验证"就不放行默认开，除非用户开工前在提示词的空格里预先授权过。

**决定怎么执行**

- **全部通过**：把 `config.py:236` 的默认值翻成开；默认关态的测试改成显式关（做法同 Q1 落地）；全量 pytest 绿；单独提交。生产 server 恢复为无旗标启动，并确认循环在默认情况下生效。
- **有任何一条不过**：保持默认关。生产 server 恢复为无旗标启动。报告里写明哪条没过、差多少、建议下一步。

## 7. 预算

- **停车线**：默认是 ¥4.00 和"实测余额减 ¥1.00"两者中较小的那个。用户可以在提示词的空格里改。
- 单格预估不超过 ¥0.08。按 ¥4 算，够跑 P0 到 P2，P1b 看情况，P3 多半跑不了。
- 每次烧钱前在台账写一行预期；每格结算；触线即停，然后进入自动分析。
- 402 熔断：用已经跑完的数据分析，报告写明实际样本量。

## 8. 应急

| 情形 | 处理 |
|---|---|
| 生产 server 无响应 | 确认无在途任务后重启，断点续跑 |
| 容器残留 | 清掉同名容器后重试该格（容器名必须唯一） |
| 账本四表不齐 | 停火，取证，修。最多 2 轮，仍不齐就写卡点报告 |
| 同一个问题修 2 轮没好 | 停火写卡点报告。涉及花钱，比默认的 3 轮更保守 |
| 余额不足 | 熔断，用已有数据分析 |
| 批量期间 | 不并行做别的任务 |

其余按 `docs/AI执行应变协议.md` 的六步循环。
